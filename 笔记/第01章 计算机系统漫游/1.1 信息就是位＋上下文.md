# 1.1 信息就是位＋上下文

> **📖 本节定位**　第 1 章「计算机系统漫游」· 教材 P1–P3
> **一句话**：计算机里的一切——程序、数据、图片、声音——最终都只是**一串比特**；它们代表什么，完全由**上下文**决定。

> [!IMPORTANT] 本节要回答的三个问题
> 1. 计算机里的"信息"到底是什么？为什么说它只是**一串 0 和 1**？
> 2. 同一个字节 `0x90`，凭什么既能是数字 144、又能是字符、还能是一条指令？
> 3. 为什么"这是个二进制文件，打不开"这句话本身就说不通？

**读之前你需要会**：二进制与十六进制怎么互相换算（见 [2.1 信息存储](../第02章%20信息的表示和处理/2.1%20信息存储.md) 的 2.1.2 节）。如果还不会也没关系——本节只用到一个事实：**1 个字节 = 8 个位**。

## 🎯 核心结论

| # | 结论 | 为什么重要 |
| :-: | :--- | :--- |
| 1 | 所有信息都是**位（bit）+ 上下文** | 同一个字节 `0x90`，可以是整数 144、可以是字符、也可以是一条指令 |
| 2 | 8 个位组成 1 个**字节（byte）**，字节是存储的最小寻址单位 | 后面讲地址、指针、数组，全部以字节为单位 |
| 3 | 源程序也是**比特**，只不过恰好按 ASCII 编码 | 所以"文本文件"和"二进制文件"没有本质区别，只有编码约定之别 |
| 4 | 区分数据对象的唯一办法是**看上下文** | 同一段内存，按 `int` 读和按 `float` 读结果完全不同（第 2 章会反复验证） |

## 1.1.1 从一段 hello 程序说起

### 先建立一个画面

计算机内部只有导线上的**电压高**和**电压低**两种稳定状态。把"高"记作 1、"低"记作 0，于是一条导线在某一时刻的状态就是一个**位**。

这就是全部家当：**没有字母、没有数字、没有颜色，只有 0 和 1**。你看到的一切"内容"，都是人给它规定好的读法。

```text
真实世界                          计算机里
─────────                        ─────────
字母 h        ── 编码规则 ──▶     0 1 1 0 1 0 0 0   (0x68)
数字 104      ── 另一种规则 ──▶   0 1 1 0 1 0 0 0   (0x68)
像素的某个分量 ── 又一种规则 ──▶   0 1 1 0 1 0 0 0   (0x68)
                                       ↑
                                  同一串位，三种含义
```

### 教材的开篇程序

```c
#include <stdio.h>

int main()
{
    printf("hello, world\n");
    return 0;
}
```

它看起来是"文字"，但在机器眼里，它只是一串**字节序列**：

```text
  #    i    n    c    l    u    d    e       <    s    t    d    i    o    .    h    >
0x23 0x69 0x6e 0x63 0x6c 0x75 0x64 0x65 0x20 0x3c 0x73 0x74 0x64 0x69 0x6f 0x2e 0x68 0x3e
```

为什么 `#` 会变成 `0x23`？因为现代计算机用 **ASCII 标准**给每个字符编了号。

#### 一起算一遍

把 `Hi` 这两个字符亲手编成字节，你就再也不会觉得"编码"抽象了：

| 步骤 | 动作 | 结果 |
| :-: | :--- | :--- |
| ① | 查 ASCII 表：`H` 的编号是 72，`i` 的编号是 105 | 72、105 |
| ② | 十进制转十六进制：72 = 4×16 + 8 | `0x48` |
| ③ | 105 = 6×16 + 9 | `0x69` |
| ④ | 每位十六进制展开成 4 位二进制 | `0100 1000`、`0110 1001` |
| ⑤ | 连起来，就是文件里真实的 2 个字节 | `48 69` |

反过来读也一样：看到文件里的 `48 69`，查表得 `H`、`i`——**这就是"解码"**。所谓"打开文件"，本质是**用某套编码规则去解释字节**。

> [!NOTE] 换个角度想
> 如果当年定的不是 ASCII，而是另一套编号（比如让 `#` = 1、`i` = 2），同样这串字节读出来就是完全不同的文本。**字节没变，规则变了，含义就变了。**"上下文"指的就是这套规则。

> [!TIP]
> 每个 ASCII 字符占 **1 个字节**。所以 `hello.c` 在磁盘上占多少字节，一个粗算办法就是数一数字符个数（再算上换行符 `\n`，其 ASCII 码为 `0x0a`）。

<details>
<summary>✅ 检查点 1：字符 `A` 的 ASCII 码是 65，那它在文件里长什么样？</summary>

一个字节 `0x41`，二进制 `0100 0001`。注意"65"只是给人看的十进制写法，磁盘上存的是那 8 个位。
</details>

## 1.1.2 文本文件与二进制文件

### 先给直觉

想象同一张写满点的纸：戴"字母眼镜"看，它是文章；戴"音符眼镜"看，它是乐谱。纸没变，**眼镜变了**。

文件也是这样：`hello.c` 和编译出来的 `hello` 都是字节，区别只在**我们约定用哪套规则读它**。

### 教材的划分

| 文件类型 | 定义 | 例子 |
| :--- | :--- | :--- |
| **文本文件** | 只由 ASCII 字符（或某种字符编码）构成的文件 | `hello.c`、`.txt`、`.html` |
| **二进制文件** | 所有其他文件 | 编译出的 `hello` 可执行文件、`.jpg`、`.mp3` |

```text
                    同一块字节        0x68 0x65 0x6C 0x6C 0x6F
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
  按 ASCII 解释                     按别的规则解释
  "hello"                         一段机器指令 / 一个像素 / 一个采样点
        │                                 │
     文本文件                          二进制文件
```

> [!IMPORTANT]
> "文本 / 二进制"不是字节本身的属性，而是**我们解释字节的方式**。把 `hello.c` 改名成 `hello.bin` 不会让它变成二进制文件——改变不了它里面的 `0x23 0x69 …`。

> [!NOTE] 换个角度想
> 那为什么还要分这两类？因为**约定不同，工具就不同**。文本文件可以被 `cat`、`diff`、`git` 逐行处理；二进制文件用这些工具会显示乱码，甚至被改动（例如自动转换换行符）。分类是为了**选对工具**，不是给字节贴标签。

<details>
<summary>✅ 检查点 2：`hello.c` 改名成 `hello.bin`，它变成二进制文件了吗？用记事本还能读吗？</summary>

没有变，里面仍是 ASCII 字节，记事本照样能读。反过来，把可执行文件改名成 `hello.txt`，用记事本打开只会看到乱码——因为字节没按文本规则编码。
</details>

## 1.1.3 "位 + 上下文"的三个经典陷阱

> [!WARNING]
> 下面三个例子在第 2 章会给出严格解释，这里先建立直觉：

**① 同样的字节，不同的类型**

```c
// 假设内存里这 4 个字节是 00 00 00 3F
int  i = 63;      // 按 int   → 63
float f = 1.75f;  // 按 float → 1.75   （IEEE 754 编码，见 2.4）
```

**② 同样的字节，不同的字节序**

```text
地址:      0x00  0x01  0x02  0x03
内容:      0x12  0x34  0x56  0x78
小端机器读成 int: 0x78563412
大端机器读成 int: 0x12345678      （见 2.1.3）
```

**③ 同样的字节，代码还是数据**

```text
可执行文件 hello  =  [ 机器指令 ][ 只读数据 ][ 未初始化数据 ][ 符号表 … ]
                       ↑ 这份字节被 CPU 当"指令"执行
```

这三个陷阱其实是同一件事的三个侧面：**给同一串位换一套解释规则，结果就完全不同**。

## 📌 重点速记

| 关键词 | 记法 |
| :--- | :--- |
| 位（bit） | 0 或 1，最小信息单位 |
| 字节（byte） | 8 位，**存储与寻址的最小单位** |
| ASCII | 用一个字节给字符编号，`#`=`0x23`，`i`=`0x69`，`\n`=`0x0a` |
| 文本文件 | 只含 ASCII（字符编码）字节 |
| 二进制文件 | 其他一切文件 |
| 核心命题 | **信息 = 位 + 上下文** |

> [!TIP]
> 记忆口诀：**"字节本身不表意，谁解释谁说了算。"** 后面看到 `int`/`float`/指针/指令，都先问一句："这里用的是哪套解释规则？"

---

## ⚠️ 易错点

1. **以为"文件后缀"决定文件类型。** 后缀只是给人看的约定，机器只看字节。
2. **把"位"和"字节"混用。** 说带宽常说 Mbps（位/秒），说容量常说 MB（字节），差 8 倍。
3. **以为字符一定是 1 字节。** ASCII 是 1 字节，但 UTF-8 的汉字通常占 3 字节；CSAPP 讨论的都是 ASCII 场景。
4. **以为"看上下文"是玄学。** 它其实是**类型系统 + 编码标准**在起作用，第 2 章会把它变成公式。

## ❓ 常见困惑

**Q：既然都是 0 和 1，计算机怎么知道哪里是"一个数的开头"？**
A：它不知道，也不需要知道——是**程序**（也就是同一串位中被当作指令解释的那部分）在决定"从哪个地址开始、按几个字节、按什么类型读"。硬件只负责按指令搬字节、做运算。

**Q：那为什么有时双击一个文件会提示"无法打开"？**
A：不是文件坏了，而是系统**找不到它的解释规则**（缺对应程序，或后缀没关联）。给了正确的程序，同一串字节立刻"能看"了。

**Q：`0x23` 里的 `0x` 是什么意思？**
A：只是告诉人和编译器"后面的数字是十六进制"。它本身不占存储、也不是数据的一部分。

**Q：既然都是字节，为什么 `hello.c` 能被 `git` 显示改动，`hello` 却不能？**
A：`git` 按**文本规则**逐行比对。可执行文件里没有"行"的概念，逐行比对毫无意义。工具不同，是因为解释规则不同。

## 🛠 动手试试

1. 看一个文件的真实字节（Linux / macOS）：

   ```bash
   echo -n "Hi" > t.txt      # -n 表示不加换行
   xxd t.txt                 # 应看到 48 69
   ```

   对照前面的算例：`H`=0x48、`i`=0x69。把 `-n` 去掉再跑一次，末尾会多出 `0a`（换行符）。

2. 亲手验证"改名不改变含义"：把 `t.txt` 改名为 `t.bin`，再用文本编辑器打开——内容一模一样。

3. 数一数：把 `hello` 五个字符存成文件，它占多少字节？答案是 5；若在编辑器里敲了回车，则 6（多一个 `0a`）。

## ✅ 自测

1. 字符 `A` 的 ASCII 码是 65，它在文件中占几个字节？换成十六进制是多少？
2. `hello` 这个词用 ASCII 存下来占几个字节？写出其十六进制串。
3. 一段内存字节是 `00 00 80 3F`，按 IEEE 754 单精度解释是多少？按小端 `int` 解释又是多少？
4. 为什么说"文本文件 / 二进制文件"的划分不是字节的固有属性？

<details>
<summary>参考答案</summary>

1. 1 个字节；`0x41`。
2. 5 个字节；`0x68 0x65 0x6C 0x6C 0x6F`。
3. 按 IEEE 754 单精度是 `1.0`（阶码 `0x7F`、尾数全 0）；按小端 `int` 是 `0x3F800000` = 1065353216。
4. 因为字节序列本身没有"含义"，是解释规则（ASCII / 机器码 / 图像格式…）决定了它看起来像文本还是二进制。

</details>
