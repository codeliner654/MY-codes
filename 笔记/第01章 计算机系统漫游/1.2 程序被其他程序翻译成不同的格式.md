# 1.2 程序被其他程序翻译成不同的格式

> **📖 本节定位**　第 1 章「计算机系统漫游」· 教材 P3–P4
> **一句话**：`hello.c` 是人能读的文本，机器只认 0/1；把前者变成后者的不是"一次编译"，而是**预处理器、编译器、汇编器、链接器**四个程序接力翻译。

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | C 程序要过四道工序：**预处理（cpp）→ 编译（cc1）→ 汇编（as）→ 链接（ld）** |
| 2 | 文件形态按序变化：`hello.c → hello.i → hello.s → hello.o → hello`，前三个还是**文本**，后两个是**二进制** |
| 3 | **编译器输出汇编语言（文本），汇编器才输出机器指令（二进制）** ——这是全节最容易记反的一处 |
| 4 | 链接器不是可有可无的一步：`hello` 用到的 `printf` 根本不在 `hello.c` 里，而在库文件 `printf.o` 中，必须被**合并**进来 |
| 5 | 链接器只干两件事：**符号解析**（`printf` 到底在哪个目标文件里）与**重定位**（把最终地址填进指令的字节里） |
| 6 | `gcc` 本身只是个"驱动程序"，它按文件后缀决定调用哪个子程序 |

> [!IMPORTANT]
> 这四个程序各管一段，**每一段的输入输出格式都是明确定义的**。看懂这张"格式转换表"，比背命令更有用——后面第 3 章、第 7 章反复回到这里。

## 1.2.1 编译系统：四个程序，一条传送带

教材开篇的 `hello.c` 只有 7 行，却要被四个程序依次加工；下面这条流水线标明了每一步"谁在干活、干了什么"：

```text
  hello.c     源程序（文本，人写的）
     │
     │  ① 预处理器 cpp
     │     展开 #include、替换 #define、处理条件编译、删注释
     ▼
  hello.i     修改后的 C 源程序（文本，被撑大了几十倍）
     │
     │  ② 编译器 cc1
     │     词法/语法/语义分析 → 中间代码 → 优化 → 生成汇编
     ▼
  hello.s     汇编程序（文本，一条汇编 ≈ 一条机器指令）
     │
     │  ③ 汇编器 as
     │     把汇编语句逐条翻译成机器指令的字节，打包成目标文件
     ▼
  hello.o     可重定位目标文件（二进制，printf 还是空的）
     │
     │  ④ 链接器 ld  ◀── printf.o（来自标准 C 库 libc）
     │     合并同名段、符号解析、重定位
     ▼
  hello       可执行目标文件（二进制，可以 ./hello 运行）
```

*图 1-2-1：从 `hello.c` 到 `hello` 的四级流水线。注意只有 ② 是"翻译语言"，③ 才是"翻译成机器码"。*

| 阶段 | 程序（GNU） | 单独执行的命令 | 输入 | 输出 | 输出形态 |
| :-: | :---: | :--- | :--- | :--- | :-: |
| 预处理 | `cpp` | `gcc -E hello.c -o hello.i` | `hello.c` | `hello.i` | 文本 |
| 编译 | `cc1` | `gcc -S hello.i -o hello.s` | `hello.i` | `hello.s` | 文本 |
| 汇编 | `as` | `gcc -c hello.s -o hello.o` | `hello.s` | `hello.o` | 二进制 |
| 链接 | `ld` | `gcc hello.o -o hello` | `hello.o` + `printf.o` | `hello` | 二进制 |

> [!NOTE]
> 表里的"程序名"是 GCC 内部实际调用的子程序：`cpp`、`cc1`、`as`、`ld`。你在终端敲的 `gcc` 只是外壳（driver），它读完命令行、看后缀、再把这些家伙一个个叫起来。

## 1.2.2 第一步：预处理阶段（cpp）

预处理器**只认 `#` 开头的行**，它做的全是"文本替换"，不理解 C 语法：

| 指令 | 预处理器的动作 |
| :--- | :--- |
| `#include <stdio.h>` | 把 `stdio.h` 的全文**原样插入**到这一行的位置（可以层层嵌套） |
| `#define N 100` | 把后文出现的 `N` 全部换成 `100` |
| `#ifdef` / `#if` … `#endif` | 按条件保留或删掉整段代码 |
| `/* … */`、`//` | 删除注释（替换为一个空格） |

所以 `hello.i` 里已经没有 `#include` 了，取而代之的是 `stdio.h` 里成百上千行的函数声明，例如：

```c
extern int printf (const char *__restrict __format, ...);
extern int puts (const char *__s);
/* …还有几百个声明、typedef、宏… */

int main()
{
    printf("hello, world\n");
    return 0;
}
```

> [!TIP]
> 一个 7 行的 `hello.c`，`hello.i` 往往膨胀到**几十万字节**——多出来的 99.9% 都是头文件里的声明。这就是"编译一个 hello 为什么要几百毫秒"的原因之一。

---

## 1.2.3 第二步：编译阶段（cc1）

编译器是四个程序里最复杂的一个，它把 C 变成**汇编语言**。粗略分四步：

```text
hello.i ──▶ 词法分析 ──▶ 语法分析 ──▶ 语义分析 ──▶ 中间代码 ──▶ 优化 ──▶ hello.s
           切成 token    建成语法树    类型检查      (IR/GIMPLE)   寄存器分配
```

产物 `hello.s` **仍然是文本**，用 `cat` 就能看：

```asm
        .section  .rodata            # 只读数据段
.LC0:
        .string   "hello, world\n"   # 字符串常量，汇编器会自动补 '\0'
        .text                        # 代码段
        .globl    main               # main 是全局符号，链接器要能看见
main:
        subq      $8, %rsp           # 让栈指针对齐到 16 字节
        leaq      .LC0(%rip), %rdi  # ① 字符串地址 → %rdi（第 1 个参数）
        call      puts               # ② 调 puts（gcc 把 printf 优化成它）
        movl      $0, %eax           # ③ 返回值 0 → %eax
        addq      $8, %rsp
        ret
```

*图 1-2-2：`hello.s` 的骨架（省略 `.cfi` 调试伪指令）。`%rdi` 传第一个参数、`%eax` 存返回值，是 x86-64 的调用约定。*

两个值得注意的细节：

1. **`printf("…\n")` 被换成了 `puts`**——因为"只输出一个字符串再加换行"时 `puts` 更快，这是编译器做的优化，不是教材写错；
2. 这一层特意保留成**文本**而不是直接出机器码，是为了让人能读、能手改、能让不同机器共用同一个编译器前端。

---

## 1.2.4 第三步：汇编阶段（as）

汇编器把每条汇编语句翻译成一条机器指令的**字节**，并打包成 **ELF 可重定位目标文件**（relocatable object file）：

```text
        leaq  .LC0(%rip), %rdi   ──▶   48 8d 3d 00 00 00 00
        call  puts               ──▶   e8 00 00 00 00
        movl  $0, %eax           ──▶   b8 00 00 00 00
```

看出问题了吗？**所有地址都是 0**。因为此刻汇编器根本不知道：

字符串最终落在哪个地址（`48 8d 3d …` 的后 4 字节）、`puts` 最终落在哪个地址（`e8 …` 的后 4 字节），此刻都还是未知数。

用 `objdump -d hello.o` 反汇编，看到的是这样：

```asm
0000000000000000 <main>:
   0:   48 83 ec 08             sub    $0x8,%rsp
   4:   48 8d 3d 00 00 00 00    lea    0x0(%rip),%rdi     # ← 目标地址待定
   b:   e8 00 00 00 00          call   10 <main+0x10>     # ← 目标地址待定
  10:   b8 00 00 00 00          mov    $0x0,%eax
  15:   48 83 c4 08             add    $0x8,%rsp
  19:   c3                      ret
```

再用 `readelf -r hello.o` 看**重定位表**，就明白这些 0 是留给谁填的：

```text
重定位节 '.rela.text' 包含 2 项：
  偏移        类型             符号名            说明
  000000000008  R_X86_64_PC32   .rodata - 4      ① 填字符串地址
  00000000000c  R_X86_64_PLT32  puts - 4         ② 填 puts 的地址
```

> [!WARNING]
> `hello.o` **不能直接运行**（`./hello.o` 会报 `Permission denied` 或 `Exec format error`）。它是一个"半成品"：代码齐了，地址还空着。

## 1.2.5 第四步：链接阶段（ld）——为什么它必不可少

`hello.c` 里根本没写 `printf` 的函数体，只用了一行声明 `extern int printf(const char *__restrict, ...);`（来自 `stdio.h`）。**函数体在标准 C 库（libc）预先编译好的 `printf.o` 里**，链接器要做的是把两个目标文件拼在一起：

```text
   hello.o（未解析）              printf.o（库中已有）
   ┌──────────────────┐          ┌──────────────────┐
   │ .text:   main    │          │ .text:   printf  │
   │ .rodata: "hello" │          │ 符号:    printf  │
   │ 符号:    main  T │          │          已定义  │
   │ 符号:    puts  U │          │                  │
   └────────┬─────────┘          └────────┬─────────┘
            │                             │
            └──────────────┬──────────────┘
                           │
                           ▼   ld：符号解析 + 重定位 + 合并同名段
   ┌──────────────────────────────────────────────────┐
   │ hello（ELF 可执行文件）                          │
   │   ELF 头: 入口点 0x401136                        │
   │   .text:   main / puts / printf 依次排好         │
   │   .rodata: 所有字符串常量                        │
   │   .data / .bss                                   │
   │   符号表 / 重定位信息（调试用，可删）            │
   └──────────────────────────────────────────────────┘
```

*图 1-2-3：链接的本质是"拼接 + 填地址"。左边空着的洞，右边正好有对应的定义。*

链接之后再看 `objdump -d hello`，`call` 后面不再是 `00 00 00 00`，而是一个**真实的相对偏移**：

```asm
0000000000401136 <main>:
  401136:   48 83 ec 08             sub    $0x8,%rsp
  40113a:   48 8d 3d c3 0e 00 00    lea    0xec3(%rip),%rdi   # 404004 <_IO_stdin_used+0x4>
  401141:   e8 ca fe ff ff          call   401010 <puts@plt>
  401146:   b8 00 00 00 00          mov    $0x0,%eax
```

> [!IMPORTANT]
> **链接器解决的两类问题**：① **符号解析**——找到 `puts` / `printf` 的定义到底在哪个 `.o` 里；② **重定位**——把这个定义最终落在可执行文件里的地址，写回那 4 个字节。第 7 章会展开讲这两步。

## 1.2.6 一条命令串起四步

平时我们只敲一条 `gcc -o hello hello.c`，它等价于把四个程序依次叫起来：

```bash
cpp hello.c -o hello.i            # ① 预处理
cc1 hello.i -o hello.s            # ② 编译
as  hello.s -o hello.o            # ③ 汇编
ld  hello.o -o hello -lc …        # ④ 链接（-lc 表示链接 libc）
```

| 想停在哪一步 | 命令 | 留下的文件 |
| :--- | :--- | :--- |
| 只要预处理结果 | `gcc -E hello.c -o hello.i` | `hello.i` |
| 只要汇编代码 | `gcc -S hello.c` | `hello.s` |
| 只要目标文件（不改动其他 `.o`） | `gcc -c hello.c` | `hello.o` |
| 想把中间文件全留下 | `gcc -save-temps -o hello hello.c` | `.i`、`.s`、`.o` 都在 |
| 完整可执行 | `gcc -o hello hello.c` | `hello` |

改一行代码就要重新 `gcc` 整个工程吗？不需要。**每个 `.c` 单独 `-c` 成 `.o`，只有被改动的那个重编，最后统一 `ld`**——这正是 `make` 存在的原因，也是"分四步"最大的工程收益。

---

## 1.2.7 为什么非要分成四步

| 理由 | 说明 |
| :--- | :--- |
| **分工** | 每层只关心一种抽象：cpp 管文本、cc1 管语法与优化、as 管编码、ld 管地址 |
| **可复用** | `.o` 可以缓存、可以打包成静态库 `.a`，改一个文件不必重编全工程 |
| **可移植** | 换 CPU 只需换编译器后端与汇编器，前端和链接器还能复用 |
| **可组合** | 语言前端（C/C++/Fortran）可以共享同一套汇编器与链接器 |
| **可调试** | 想改汇编？直接改 `hello.s` 再 `as`，不必碰 C |

## 📌 重点速记

```text
流水线   : cpp → cc1 → as → ld
后缀     : .c → .i → .s → .o → (无) hello
形态     : 文本  文本  文本  二进制  二进制
文本/二进制分界 : 汇编器 as 之后（.o 开始是二进制）
预处理   : 只做文本替换：#include 展开、#define 展开、删注释
编译     : C → 汇编；printf("...\n") 常被优化成 puts
汇编     : 汇编 → 机器指令；地址先填 0，留重定位项
链接     : 合并 .o + libc；符号解析 + 重定位；把 0 换成真地址
一条命令 : gcc -o hello hello.c
看中间件 : gcc -save-temps -o hello hello.c
```

## ⚠️ 易错点

1. **"编译"一词有两种含义。** 广义指整条流水线（"编译一个程序"），狭义只指 ② 那一步（`.i → .s`）。教材说"编译器把 C 转成汇编"，用的是狭义。
2. **以为 `.s` 是二进制。** `.s` 是**纯文本汇编**，`cat` 得出来；`.o` 才是二进制。判断标准是"能不能直接被 CPU 执行"，不是"看不看得懂"。
3. **以为 `#include` 是"导入一个模块"。** 它是**文本插入**——`stdio.h` 被逐字粘进来，所以头文件写多了会显著拖慢编译，也会让 `hello.i` 巨大。
4. **以为链接器只是"打包"。** 它必须先做**符号解析**：如果只给了 `hello.o` 而漏掉库（比如忘写 `-lm`），就会出现 `undefined reference to 'sqrt'`——这不是编译错误，是**链接错误**。
5. **`hello.o` 当成可执行文件。** 它里面的 `call` 目标还是 0，一执行就会跳到地址 0 崩溃（或直接被内核拒绝）。
6. **`gcc hello.c` 不加 `-o` 也能出可执行文件**（默认叫 `a.out`），但很多新手以为没生成——它就在当前目录。

## ✅ 自测

1. 按顺序写出四个阶段、对应的程序名和产物后缀。
2. 哪一步之后产物从文本变成二进制？为什么 `hello.s` 不算二进制？
3. `hello.i` 里为什么找不到 `#include <stdio.h>`？它多出来的几十万字节是什么？
4. `hello.o` 用 `objdump -d` 看，`call` 后面的 4 个字节为什么全是 0？谁来填？
5. 为什么说"链接器不是可有可无的"？如果去掉链接这一步，`hello.o` 能运行吗？

<details>
<summary>参考答案</summary>

1. 预处理 `cpp` → `.i`；编译 `cc1` → `.s`；汇编 `as` → `.o`；链接 `ld` → 无后缀的 `hello`。
2. **汇编阶段之后**。`.s` 里每条语句仍是人可读的助记符（`call`、`movl`），要由 `as` 编码成字节，所以 `.s` 是文本。
3. 因为预处理器把 `stdio.h` 的全文**原地展开**了；多出来的内容是头文件里的函数声明、宏、typedef。
4. 因为此时还不知道 `puts` 和字符串的最终地址，汇编器先填 0 并生成一条**重定位记录**，由链接器 `ld` 在合并完所有目标文件后回填。
5. 不能。`hello` 用到的 `printf`/`puts` 定义在库的 `printf.o` 里，不链接就没有函数体，且 `call` 目标地址为 0，执行即崩。

</details>
