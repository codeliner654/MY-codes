# 1.3 了解编译系统如何工作是大有益处的

> **📖 本节定位**　第 1 章「计算机系统漫游」· 教材 P4–P5
> **一句话**：编译器不是黑盒——懂它怎么翻译，你才能让程序跑得更快、看懂链接期那些莫名其妙的报错、不写出被一个输入字符串就攻破的程序。

> [!IMPORTANT] 本节要回答的三个问题
> 1. 我写的是 C，为什么非得去懂编译器、汇编和链接这些"底层的东西"？
> 2. 循环条件里写 `strlen(s)` 到底慢在哪？改一下能快多少？
> 3. 那些 `undefined reference` 的报错到底在说什么？为什么它连行号都不肯给我？

**读之前你需要会**：函数"声明"和"定义"的区别（声明只说长相，定义才有函数体）、数组名与指针的基本用法；知道 `for` 循环和 `strlen` 是干什么的。都不会也没关系——本节三个例子都会从头讲起。

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | 会看汇编，才知道**一行 C 究竟变成了几条指令、几次访存**，优化才有靶子 |
| 2 | 循环条件里反复调 `strlen`，会让 O(n) 的算法退化成 O(n²)——编译器**不敢**替你改 |
| 3 | 链接错误（`undefined reference`）不是语法错，而是**"有人引用、没人定义"** |
| 4 | `static` 让符号变成**局部符号**（`t`/`d`），别的目标文件永远看不见；不加就是全局符号（`T`/`D`） |
| 5 | C 的数组**不做边界检查**，`gets` 也**不限长度**，多写的字节会顺着栈冲掉返回地址 |
| 6 | 安全漏洞的根源往往只有一句话：**程序把"数据"当成了"指令"** |

## 1.3.1 理由一：优化程序性能

### （1）一个"看起来没问题"的函数

**先说它想解决什么问题**：同一段逻辑，写成两种样子，CPU 实际要执行的指令数可能差几百倍。**不看汇编，你根本不知道一行 C 花了几条指令、访存几次**——所谓"优化"就只能靠猜。

```c
void lower(char *s)                 /* 把字符串里的大写字母转成小写 */
{
    for (size_t i = 0; i < strlen(s); i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] += 'a' - 'A';
}
```

逻辑完全正确，但在 `-O0` 下它是**平方复杂度**的：

```text
  s ──▶  "hello, world"  '\0'
          ↑
 i = 0 :  strlen ────────────────────────────▶  一路扫到 '\0'，12 次
 i = 1 :      strlen ────────────────────────▶  又从 s[1] 扫到 '\0'，11 次
 i = 2 :          strlen ────────────────────▶  再扫一遍，10 次
  ⋮
 合计 ≈ n + (n-1) + … + 1 = n(n+1)/2 次字符比较，而真正需要的只有 n 次
```

*图 1-3-1：每次都从当前位置重新扫描到串尾。字符串越长，浪费越惊人。*

| 字符串长度 n | `strlen` 被调用次数 | 实际字符比较次数 ≈ n²/2 | 相对 n = 1000 的耗时 |
| ---: | ---: | ---: | ---: |
| 1 000 | 1 000 | 5 × 10⁵ | 1× |
| 10 000 | 10 000 | 5 × 10⁷ | ≈ 100× |
| 100 000 | 100 000 | 5 × 10⁹ | ≈ 10 000× |

#### 一起算一遍

拿图 1-3-1 里那个 `"hello, world"`（$n = 12$）真数一遍：

| 步骤 | 动作 | 结果 |
| :-: | :--- | ---: |
| ① | `i = 0` 时 `strlen` 从 `s[0]` 扫到 `'\0'`，比较 12 次 | 12 |
| ② | `i = 1` 时从 `s[1]` 重新扫到 `'\0'`，比较 11 次 | 11 |
| ③ | 一路递减，`i = 11` 时只剩 1 次 | 1 |
| ④ | 总比较次数 $12 + 11 + \dots + 1 = 12 \times 13 / 2$ | 78 |
| ⑤ | 真正必要的比较（从头扫一遍） | 12 |
| ⑥ | 浪费比例 $(78 - 12) / 78$ | ≈ 85% |

n 小的时候看不出来：78 次和 12 次都是纳秒级。把 n 放大到 100 000，总比较次数变成 $100000 \times 100001 / 2 \approx 5 \times 10^{9}$。按每次比较约 1 ns 估，**光比较就要 5 秒**；正确写法只要约 0.1 毫秒——差 5 万倍。这就是"懂不懂编译"和"会不会优化"的实际差距。

### （2）正确的写法

```c
void lower(char *s)
{
    size_t n = strlen(s);           /* 只算一次，O(n) */
    for (size_t i = 0; i < n; i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] += 'a' - 'A';
}

/* 更好：连 strlen 都不用，直接找 '\0' */
void lower2(char *s)
{
    for (; *s; s++)                 /* *s 为 '\0' 时循环结束 */
        if (*s >= 'A' && *s <= 'Z')
            *s += 'a' - 'A';
}
```

> [!NOTE]
> 为什么编译器**不**自动把 `strlen(s)` 提到循环外？因为 C 的函数调用可能带副作用——编译器无法证明 `strlen` 每次返回同一个值（理论上它可能读全局变量）。`gcc -O2` 会把 `strlen` 当内建函数（builtin）来特殊处理，但这是**编译器的善意，不是语言保证**。

<details>
<summary>✅ 检查点 1：既然 `-O2` 常常会自动优化掉这个循环里的 `strlen`，那还需要自己改吗？</summary>

需要。`-O2` 能提走 `strlen` 是"碰巧识别出来了"，不是语言承诺：一旦循环体里调用了别的函数、或者 `-O0` 调试构建、或者换个编译器，退化就会回来。**性能不能建立在"编译器应该会帮我"的假设上**，写对写法是一行代码的事。
</details>

### （3）"懂编译"能回答的几类性能问题

| 你观察到的现象 | 需要哪一层知识 |
| :--- | :--- |
| 少一次函数调用，快了好几倍 | 汇编：一次 `call` 要压栈、跳转、建立栈帧 |
| 同样的循环，改一行就快了 3 倍 | 编译器优化：强度削弱、公共子表达式、寄存器分配 |
| 数组比链表快一个数量级 | 存储层次（1.5、1.6 节）：连续访问命中 cache |
| `-O2` 反而更慢 | 编译器可能过度展开，导致指令 cache 溢出 |

## 1.3.2 理由二：理解链接时出现的错误

### （1）三类必考的链接错误

**先说它想解决什么问题**：一个 `.o` 只知道"我用了 `foo`"，不知道 `foo` 在哪；另一个 `.o` 说"我这儿定义了 `foo`"。**链接器就是那个负责对上号的介绍人**——一旦对不上，它手里没有任何补救手段，只能喊 `undefined reference`。

| 报错信息 | 真正含义 | 常见原因 |
| :--- | :--- | :--- |
| `undefined reference to 'foo'` | **有人引用，没人定义** | 忘了把 `foo.o` 加进命令；忘了 `-lm`；名字拼错 |
| `multiple definition of 'x'` | 多个 `.o` 都定义了同一个**全局符号** | 在头文件里写 `int x = 0;` 并被多个 `.c` 包含 |
| `cannot find -lxxx` | 库文件本身没找到 | 没装库，或缺 `-L` 路径 |

### （2）一个最小复现

```c
/* main.c */
#include <stdio.h>
int foo(int);                       /* 只有声明，没有函数体 */
int main(void) { printf("%d\n", foo(3)); return 0; }
```

```console
$ gcc -o prog main.c
/usr/bin/ld: /tmp/cc8Kd2x.o: in function `main':
main.c:(.text+0x1a): undefined reference to `foo'
collect2: error: ld returned 1 exit status
```

**注意报错的是 `ld` 而不是 `cc1`**——语法检查早就通过了，缺的是"定义"。

```c
/* foo.c */
int foo(int x) { return x * 2; }
```

```console
$ gcc -o prog main.c foo.c        # 把定义交给链接器
$ ./prog
6
```

> [!WARNING]
> `gcc -c main.c` 单独编译 `main.c` **永远不会**报 `undefined reference`——因为汇编器只需要"名字"，不需要"地址"。这类错误**只在链接那一刻**才暴露。

<details>
<summary>✅ 检查点 2：那 `gcc -c main.c` 到底检查了什么？它凭什么说"成功"？</summary>

它只检查到**汇编**为止：语法对不对、类型对不对、`foo` 的**声明**在不在。至于 `foo` 的**定义**在哪个 `.o` 里、地址是多少，那是链接器的事。所以 `-c` 成功只能说明"这个文件本身没毛病"，不能说明"整个程序能跑"。
</details>

### （3）`static` 改变了符号的可见性

```c
/* a.c */   int  counter = 0;          /* 全局符号，别的 .o 可以 extern 引用 */
/* b.c */   static int counter = 0;   /* 局部符号，只属于 b.o，撞名也不冲突 */
```

```text
$ nm a.o                      $ nm b.o
0000000000000004 T g          0000000000000004 T g      # T = .text 里的全局符号
0000000000000000 D counter    0000000000000000 d counter # d = 本文件私有的数据
                 U printf                       U printf # U = 未定义，等链接器给
```

*图 1-3-2：`nm` 的大小写就是可见性——大写全局、小写局部，`U` 表示未定义。*

| `nm` 字母 | 含义 | 可见性 |
| :-: | :--- | :--- |
| `T` / `t` | 在 `.text`（代码） | 大写全局 / 小写局部 |
| `D` / `d` | 已初始化的数据段 | 同上 |
| `B` / `b` | 未初始化的 `.bss` | 同上 |
| `U` | **未定义**，要靠别人提供 | — |

### （4）`-l` 的顺序真的会决定成败

```bash
gcc main.o -lm -o prog      # ✓ 库放在引用它的 .o 之后
gcc -lm main.o -o prog      # ✗ 可能报 undefined reference
```

链接器是**从左到右**扫描的：扫到 `main.o` 时发现需要 `sqrt`，后面正好有 `-lm` 就记下来；顺序反过来，扫 `-lm` 时还没人需要它，`main.o` 里的 `sqrt` 就永远没人管了。

#### 一起算一遍

设 `main.o` 用到 `sqrt`，而 `sqrt` 的定义在 `-lm` 里。链接器**单趟从左往右**扫，看它手里"还欠着的符号"怎么变：

| 顺序 | 扫到谁 | 扫完后的欠账 | 链接器的动作 |
| :-: | :--- | :--- | :--- |
| ① | `main.o` | `sqrt` | 记下"欠 sqrt"，继续往后走 |
| ② | `-lm` | `sqrt` | 库里有定义 → 划掉欠账 ✓ |
| ③ | 扫描结束 | 空 | 链接成功 |

命令顺序反过来（`gcc -lm main.o`）：

| 顺序 | 扫到谁 | 扫完后的欠账 | 链接器的动作 |
| :-: | :--- | :--- | :--- |
| ① | `-lm` | 空 | **此刻没人需要它** → 整个库被跳过（甚至不打开） |
| ② | `main.o` | `sqrt` | 记下欠账，可后面已经没有库了 ✗ |
| ③ | 扫描结束 | `sqrt` | `undefined reference to 'sqrt'` |

一句话：**链接器不回头**。所以规则是"**谁用谁在前，库放最后**"——`gcc main.o -lm` 而不是 `gcc -lm main.o`。

> [!NOTE] 换个角度想
> 为什么不先给所有库建一张全局符号表，再慢慢查？因为 1970 年代的机器只有几十 KB 内存，装不下索引；"单趟扫描 + 顺序规则"是**在极小内存下也能工作的设计**。今天内存早不是瓶颈，但 ABI 和工具链已经定型，这条"祖传规矩"就一直留到了现在。

## 1.3.3 理由三：避免安全漏洞

### （1）一个 8 字节的数组能毁掉整个系统

```c
void echo(void)
{
    char buf[8];
    gets(buf);          /* 读一整行，完全不看 buf 有多长 */
    puts(buf);
}
```

输入 `AAAAAAAAAAAAAAAAAAAAAAAA` 时，多出来的字节会顺着栈往上写：

```text
   高地址
   ┌────────────────────┐
   │ 调用者的栈帧       │
   ├────────────────────┤
   │ 返回地址           │  ◀── 先被冲掉：ret 一执行就跳到攻击者给的地址
   ├────────────────────┤
   │ 保存的 rbp         │  ◀── 接着被冲掉
   ├────────────────────┤
   │ char buf[8]        │  ◀── gets 从这里开始写，不限长度
   └────────────────────┘
   低地址
```

*图 1-3-3：栈从高地址向低地址"生长"，但数组是从低地址向高地址"填充"的——所以溢出方向正好冲着返回地址去。*

#### 一起算一遍

把 `char buf[8]` 的栈帧摊开，数一数 24 个 `A` 加上 `gets` 补的结尾 `'\0'`（共 25 个字节）分别落到哪（`-O0`、无栈保护时的典型布局，地址示意）：

| 写入的第几个字节 | 落到哪里 | 内容 | 后果 |
| :-: | :--- | :--- | :--- |
| 1 ~ 8 | `buf[0]` ~ `buf[7]` | `0x41` × 8 | 正常，本来就是它的地盘 |
| 9 ~ 16 | 保存的 `%rbp` | `0x4141414141414141` | 调用者的栈帧指针被毁 |
| 17 ~ 24 | **返回地址** | `0x4141414141414141` | `ret` 时 PC ← 这个值 |
| 25 | 返回地址上方 | `0x00`（补的 `'\0'`） | 顺手多踩一个字节 |

于是函数执行 `ret` 时，CPU 把栈顶那 8 个字节弹进 PC，得到一个**不存在的地址** `0x4141414141414141` → 段错误。如果攻击者把这 8 字节换成一个**真实存在的地址**（比如栈上 shellcode 的地址），程序就会乖乖跳过去执行——这就是缓冲区溢出攻击的完整算术。

> 上表省略了**对齐填充**：真实的 `-O0` 编译常在 `buf` 和保存的 `%rbp` 之间再留 8 字节（让 `%rsp` 保持 16 字节对齐），于是要多写 8 个字节才够到返回地址。这也解释了一个常见现象——**"我明明溢出了，程序却没崩"**：多出来的字节先被填充区吃掉了。精确偏移永远要用 `objdump` 或调试器实测，不能靠数。

### （2）攻击是怎么完成的

```text
 ①  攻击者准备一段字节：
     [ 88 个填充字节 ][ 伪造的返回地址 ][ 恶意指令（shellcode）]
 ②  gets 把它全部写进栈，返回地址被改写成"恶意指令所在地址"
 ③  函数执行 ret → CPU 把栈顶值弹出到 PC → 开始执行攻击者的代码
 ④  程序"合法地"跳到了不该去的地方，拿到 shell
```

> [!IMPORTANT]
> 教材反复强调的一点：**漏洞的本质是"数据"和"代码"的边界被打破了。** 用户输入本来只是数据，溢出后却变成了要执行的地址。

### （3）正确的写法与三道现代防线

```c
char buf[8];
fgets(buf, sizeof buf, stdin);      /* 最多写 sizeof(buf)-1 个字符，再补 '\0' */
```

| 防线 | 做法 | 挡住什么 |
| :--- | :--- | :--- |
| 栈随机化（ASLR） | 每次运行栈地址都不同 | 攻击者猜不准跳转地址 |
| 栈保护（`-fstack-protector`） | 返回地址前放"金丝雀值"，被改就 `abort` | 覆盖返回地址本身 |
| 不可执行栈（NX / DEP） | 栈段标记为不可执行 | 直接执行栈上的 shellcode |

`gets` 因为**无法安全使用**，已在 C11 中被正式从标准里删除。

<details>
<summary>✅ 检查点 3：栈金丝雀（`-fstack-protector`）挡住的到底是哪一步？</summary>

挡的是"**返回地址被改写**"这一步：编译器在返回地址**前面**塞一个随机值（金丝雀），函数返回前检查它有没有变。变了说明有人越界写，直接 `abort`，攻击链在第 ③ 步（`ret` 跳转）之前就被掐断。但它挡不住"只改局部变量"的溢出，也挡不住 ASLR 被绕过。
</details>

```text
编译器   : 不敢随便移动函数调用（可能有副作用）
链接错误 : undefined reference = 有人引用没人定义
符号可见 : static → 局部符号(t/d)；非 static → 全局符号(T/D)
nm 字母  : T/t 代码  D/d 已初始化数据  B/b 未初始化  U 未定义
链接顺序 : 库要放在引用它的 .o 之后
安全     : 数组不检查边界；gets 不限长度；返回地址在栈上

防线     : ASLR + 栈金丝雀 + NX(不可执行栈)
```

## ⚠️ 易错点

1. **以为 `gcc -c main.c` 成功就万事大吉。** `-c` 只到汇编为止，不做链接；`undefined reference` 一定在最后一步才出现。
2. **把 `undefined reference` 当成"函数名写错了"。** 更常见的是**忘了把对应的 `.o` / 库加进命令**，或 `-l` 顺序放反。
3. **以为 `static` 只是"让变量活得更久"。** 在**文件作用域**（函数外）的 `static` 改变的是**链接属性**（外部 → 内部），跟生命周期无关；函数内的 `static` 才管生命周期。
4. **用 `char *p = "abc";` 再 `p[0] = 'x';`** —— 字符串字面量在 `.rodata`（只读段），写入直接段错误。这也是一种"懂链接才懂"的错误。
5. **以为 `strlen` 是 O(1)。** 它必须走到 `'\0'` 才知道长度，是 O(n)；把它写进循环条件就是 O(n²)。
6. **用 `gets` 然后"输入短一点就没事"。** 安全性不能靠调用者守规矩——库函数必须自己限长。

## ❓ 常见困惑

**Q：我加了 `-O2`，是不是就不用管 `strlen` 这种事了？**
A：不能这么想。`-O2` 把它提出循环属于"编译器恰好能证明这是安全的"，不是语言保证；循环体里多一次函数调用、换个编译器、或者用 `-O0` 调试，退化立刻回来。**写对写法只要一行，赌编译器永远聪明风险太大。**

**Q：报错里的 `collect2` 是什么？一会儿 `ld` 一会儿 `collect2`，到底谁在骂我？**
A：真正的报错者是 **`ld`**；`collect2` 是 gcc 调来"代管链接"的小程序，它只是把 `ld` 的抱怨原样转述并补一句 `ld returned 1 exit status`。所以看到 `collect2: error` 时，眼睛要往上看一行，那才是真原因。

**Q：`undefined reference` 为什么不告诉我在第几行？**
A：因为它根本不知道。链接器手里只有**符号表**——"某个 `.o` 里有个 `U foo`，但没人给 `T foo`"——它没有源码行号这种信息。想知道"谁引用了 `foo`"，得用 `nm`/`objdump` 去查，而不是等报错。

**Q：本地编译运行都正常，拷到服务器上就 `undefined reference`，为什么？**
A：典型是**库和顺序**问题：本地可能装了某个库、或者 `Makefile` 里 `-l` 顺序恰好对；服务器上库没装（`cannot find -lxxx`）或顺序反了。先比两边的 `gcc -v` 链接命令，再看 `-l` 是否都在 `.o` 之后。

## 🛠 动手试试

1. 把 1.3.1 的 `lower` 存成 `lower.c`，亲眼看到"循环里每次都在调 `strlen`"：

   ```bash
   gcc -O0 -S lower.c -o - | grep -n 'call.*strlen'
   ```

   预期：输出 **1 行**，位置在循环体内部（`-O0` 下 `strlen` 每轮都被调用）。把 `-O0` 换成 `-O2` 再跑，这一行通常消失——`call` 被提到了循环外。

2. 复现一次链接错误，再看符号表：

   ```bash
   gcc -o prog main.c          # 只有声明，没有定义
   gcc -c main.c && nm main.o | grep foo
   gcc -o prog main.c foo.c && ./prog
   ```

   预期：第一条报 `undefined reference to 'foo'`；`nm` 显示 `U foo`（U = 未定义）；第三条输出 `6`。

3. 把 1.3.3 的 `echo` 补上 `int main(void){ echo(); }` 存成 `echo.c`，让栈保护替你"抓住"一次溢出：

   ```bash
   gcc -fstack-protector-all -o echo echo.c
   printf 'AAAAAAAAAAAAAAAAAAAAAAAA\n' | ./echo
   ```

   预期：打印 `*** stack smashing detected ***: terminated` 后异常退出——金丝雀发现返回地址被踩，在 `ret` 之前就 `abort` 了。把 `-fstack-protector-all` 去掉再跑，可能只是**安静地**段错误，甚至看起来"正常"（更危险）。

## ✅ 自测

1. 为什么 `for (i = 0; i < strlen(s); i++)` 是 O(n²)？改成哪种写法能降到 O(n)？
2. `undefined reference to 'foo'` 是哪一步报的？列出至少三种可能原因。
3. 同一个名字 `counter` 在两个 `.c` 里都定义，什么时候报 `multiple definition`，什么时候不报？为什么？
4. `gets(buf)` 为什么会覆盖返回地址？栈的增长方向和数组的填充方向各是什么？
5. 说出三种防御缓冲区溢出的机制，各自挡住攻击链的哪一环。

<details>
<summary>参考答案</summary>

1. 每轮循环都要从 `s[i]` 重新扫描到 `'\0'`，总比较次数为 n+(n-1)+…+1 = n(n+1)/2。改成先 `size_t n = strlen(s);` 再循环，或用 `for (; *s; s++)` 边走边判。
2. 报在**链接**阶段（`ld`）。原因：没把定义所在的目标文件加入命令；忘了链接对应库（如 `-lm`）；`-l` 顺序错误；符号被 `static` 修饰导致外部不可见；C++ 名字修饰未加 `extern "C"`。
3. 两个都是**全局**定义时会在链接期报 `multiple definition`；其中一个加了 `static` 就是**局部符号**，链接器根本看不到，因此不冲突。
4. `gets` 不做长度检查，输入超过 `buf` 容量后继续向**高地址**写；而栈帧中返回地址正好位于 `buf` 的高地址一侧，于是被覆盖。函数 `ret` 时把被改写的值弹入 PC。
5. ASLR（让攻击者猜不中地址）、栈金丝雀（检测返回地址是否被改）、NX/DEP（让栈不可执行）；分别对应"猜地址""改返回地址""执行 shellcode"三环。

</details>
