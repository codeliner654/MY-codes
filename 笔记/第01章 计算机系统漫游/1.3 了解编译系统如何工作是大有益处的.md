# 1.3 了解编译系统如何工作是大有益处的

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | 会看汇编，才知道**一行 C 究竟变成了几条指令、几次访存**，优化才有靶子 |
| 2 | 循环条件里反复调 `strlen`，会让 O(n) 的算法退化成 O(n²)——编译器**不敢**替你改 |
| 3 | 链接错误（`undefined reference`）不是语法错，而是**"有人引用、没人定义"** |
| 4 | `static` 让符号变成**局部符号**（`t`/`d`），别的目标文件永远看不见；不加就是全局符号（`T`/`D`） |
| 5 | C 的数组**不做边界检查**，`gets` 也**不限长度**，多写的字节会顺着栈冲掉返回地址 |
| 6 | 安全漏洞的根源往往只有一句话：**程序把"数据"当成了"指令"** |

## 1.3.1 理由一：优化程序性能

### （1）一个"看起来没问题"的函数

```c
void lower(char *s)                 /* 把字符串里的大写字母转成小写 */
{
    for (size_t i = 0; i < strlen(s); i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] += 'a' - 'A';
}
```

逻辑完全正确，但在 `-O0` 下它是**平方复杂度**的：

```text
  s ──▶  "hello, world"  '\0'
          ↑
 i = 0 :  strlen ────────────────────────────▶  一路扫到 '\0'，12 次
 i = 1 :      strlen ────────────────────────▶  又从 s[1] 扫到 '\0'，11 次
 i = 2 :          strlen ────────────────────▶  再扫一遍，10 次
  ⋮
 合计 ≈ n + (n-1) + … + 1 = n(n+1)/2 次字符比较，而真正需要的只有 n 次
```

*图 1-3-1：每次都从当前位置重新扫描到串尾。字符串越长，浪费越惊人。*

| 字符串长度 n | `strlen` 被调用次数 | 实际字符比较次数 ≈ n²/2 | 相对 n = 1000 的耗时 |
| ---: | ---: | ---: | ---: |
| 1 000 | 1 000 | 5 × 10⁵ | 1× |
| 10 000 | 10 000 | 5 × 10⁷ | ≈ 100× |
| 100 000 | 100 000 | 5 × 10⁹ | ≈ 10 000× |

### （2）正确的写法

```c
void lower(char *s)
{
    size_t n = strlen(s);           /* 只算一次，O(n) */
    for (size_t i = 0; i < n; i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] += 'a' - 'A';
}

/* 更好：连 strlen 都不用，直接找 '\0' */
void lower2(char *s)
{
    for (; *s; s++)                 /* *s 为 '\0' 时循环结束 */
        if (*s >= 'A' && *s <= 'Z')
            *s += 'a' - 'A';
}
```

> [!NOTE]
> 为什么编译器**不**自动把 `strlen(s)` 提到循环外？因为 C 的函数调用可能带副作用——编译器无法证明 `strlen` 每次返回同一个值（理论上它可能读全局变量）。`gcc -O2` 会把 `strlen` 当内建函数（builtin）来特殊处理，但这是**编译器的善意，不是语言保证**。

### （3）"懂编译"能回答的几类性能问题

| 你观察到的现象 | 需要哪一层知识 |
| :--- | :--- |
| 少一次函数调用，快了好几倍 | 汇编：一次 `call` 要压栈、跳转、建立栈帧 |
| 同样的循环，改一行就快了 3 倍 | 编译器优化：强度削弱、公共子表达式、寄存器分配 |
| 数组比链表快一个数量级 | 存储层次（1.5、1.6 节）：连续访问命中 cache |
| `-O2` 反而更慢 | 编译器可能过度展开，导致指令 cache 溢出 |

## 1.3.2 理由二：理解链接时出现的错误

### （1）三类必考的链接错误

| 报错信息 | 真正含义 | 常见原因 |
| :--- | :--- | :--- |
| `undefined reference to 'foo'` | **有人引用，没人定义** | 忘了把 `foo.o` 加进命令；忘了 `-lm`；名字拼错 |
| `multiple definition of 'x'` | 多个 `.o` 都定义了同一个**全局符号** | 在头文件里写 `int x = 0;` 并被多个 `.c` 包含 |
| `cannot find -lxxx` | 库文件本身没找到 | 没装库，或缺 `-L` 路径 |

### （2）一个最小复现

```c
/* main.c */
#include <stdio.h>
int foo(int);                       /* 只有声明，没有函数体 */
int main(void) { printf("%d\n", foo(3)); return 0; }
```

```console
$ gcc -o prog main.c
/usr/bin/ld: /tmp/cc8Kd2x.o: in function `main':
main.c:(.text+0x1a): undefined reference to `foo'
collect2: error: ld returned 1 exit status
```

**注意报错的是 `ld` 而不是 `cc1`**——语法检查早就通过了，缺的是"定义"。

```c
/* foo.c */
int foo(int x) { return x * 2; }
```

```console
$ gcc -o prog main.c foo.c        # 把定义交给链接器
$ ./prog
6
```

> [!WARNING]
> `gcc -c main.c` 单独编译 `main.c` **永远不会**报 `undefined reference`——因为汇编器只需要"名字"，不需要"地址"。这类错误**只在链接那一刻**才暴露。

### （3）`static` 改变了符号的可见性

```c
/* a.c */   int  counter = 0;          /* 全局符号，别的 .o 可以 extern 引用 */
/* b.c */   static int counter = 0;   /* 局部符号，只属于 b.o，撞名也不冲突 */
```

```text
$ nm a.o                      $ nm b.o
0000000000000004 T g          0000000000000004 T g      # T = .text 里的全局符号
0000000000000000 D counter    0000000000000000 d counter # d = 本文件私有的数据
                 U printf                       U printf # U = 未定义，等链接器给
```

*图 1-3-2：`nm` 的大小写就是可见性——大写全局、小写局部，`U` 表示未定义。*

| `nm` 字母 | 含义 | 可见性 |
| :-: | :--- | :--- |
| `T` / `t` | 在 `.text`（代码） | 大写全局 / 小写局部 |
| `D` / `d` | 已初始化的数据段 | 同上 |
| `B` / `b` | 未初始化的 `.bss` | 同上 |
| `U` | **未定义**，要靠别人提供 | — |

### （4）`-l` 的顺序真的会决定成败

```bash
gcc main.o -lm -o prog      # ✓ 库放在引用它的 .o 之后
gcc -lm main.o -o prog      # ✗ 可能报 undefined reference
```

链接器是**从左到右**扫描的：扫到 `main.o` 时发现需要 `sqrt`，后面正好有 `-lm` 就记下来；顺序反过来，扫 `-lm` 时还没人需要它，`main.o` 里的 `sqrt` 就永远没人管了。

## 1.3.3 理由三：避免安全漏洞

### （1）一个 8 字节的数组能毁掉整个系统

```c
void echo(void)
{
    char buf[8];
    gets(buf);          /* 读一整行，完全不看 buf 有多长 */
    puts(buf);
}
```

输入 `AAAAAAAAAAAAAAAAAAAAAAAA` 时，多出来的字节会顺着栈往上写：

```text
   高地址
   ┌────────────────────┐
   │ 调用者的栈帧       │
   ├────────────────────┤
   │ 返回地址           │  ◀── 先被冲掉：ret 一执行就跳到攻击者给的地址
   ├────────────────────┤
   │ 保存的 rbp         │  ◀── 接着被冲掉
   ├────────────────────┤
   │ char buf[8]        │  ◀── gets 从这里开始写，不限长度
   └────────────────────┘
   低地址
```

*图 1-3-3：栈从高地址向低地址"生长"，但数组是从低地址向高地址"填充"的——所以溢出方向正好冲着返回地址去。*

### （2）攻击是怎么完成的

```text
 ①  攻击者准备一段字节：
     [ 88 个填充字节 ][ 伪造的返回地址 ][ 恶意指令（shellcode）]
 ②  gets 把它全部写进栈，返回地址被改写成"恶意指令所在地址"
 ③  函数执行 ret → CPU 把栈顶值弹出到 PC → 开始执行攻击者的代码
 ④  程序"合法地"跳到了不该去的地方，拿到 shell
```

> [!IMPORTANT]
> 教材反复强调的一点：**漏洞的本质是"数据"和"代码"的边界被打破了。** 用户输入本来只是数据，溢出后却变成了要执行的地址。

### （3）正确的写法与三道现代防线

```c
char buf[8];
fgets(buf, sizeof buf, stdin);      /* 最多写 sizeof(buf)-1 个字符，再补 '\0' */
```

| 防线 | 做法 | 挡住什么 |
| :--- | :--- | :--- |
| 栈随机化（ASLR） | 每次运行栈地址都不同 | 攻击者猜不准跳转地址 |
| 栈保护（`-fstack-protector`） | 返回地址前放"金丝雀值"，被改就 `abort` | 覆盖返回地址本身 |
| 不可执行栈（NX / DEP） | 栈段标记为不可执行 | 直接执行栈上的 shellcode |

`gets` 因为**无法安全使用**，已在 C11 中被正式从标准里删除。

```text
优化性能 : 看汇编才知道指令数/访存次数；strlen 别放循环条件里
复杂度   : for (i=0; i<strlen(s); i++) 是 O(n²)
编译器   : 不敢随便移动函数调用（可能有副作用）
链接错误 : undefined reference = 有人引用没人定义
符号可见 : static → 局部符号(t/d)；非 static → 全局符号(T/D)
nm 字母  : T/t 代码  D/d 已初始化数据  B/b 未初始化  U 未定义
链接顺序 : 库要放在引用它的 .o 之后
安全     : 数组不检查边界；gets 不限长度；返回地址在栈上
修复     : fgets(buf, sizeof buf, stdin)
防线     : ASLR + 栈金丝雀 + NX(不可执行栈)
```

## ⚠️ 易错点

1. **以为 `gcc -c main.c` 成功就万事大吉。** `-c` 只到汇编为止，不做链接；`undefined reference` 一定在最后一步才出现。
2. **把 `undefined reference` 当成"函数名写错了"。** 更常见的是**忘了把对应的 `.o` / 库加进命令**，或 `-l` 顺序放反。
3. **以为 `static` 只是"让变量活得更久"。** 在**文件作用域**（函数外）的 `static` 改变的是**链接属性**（外部 → 内部），跟生命周期无关；函数内的 `static` 才管生命周期。
4. **用 `char *p = "abc";` 再 `p[0] = 'x';`** —— 字符串字面量在 `.rodata`（只读段），写入直接段错误。这也是一种"懂链接才懂"的错误。
5. **以为 `strlen` 是 O(1)。** 它必须走到 `'\0'` 才知道长度，是 O(n)；把它写进循环条件就是 O(n²)。
6. **用 `gets` 然后"输入短一点就没事"。** 安全性不能靠调用者守规矩——库函数必须自己限长。

## ✅ 自测

1. 为什么 `for (i = 0; i < strlen(s); i++)` 是 O(n²)？改成哪种写法能降到 O(n)？
2. `undefined reference to 'foo'` 是哪一步报的？列出至少三种可能原因。
3. 同一个名字 `counter` 在两个 `.c` 里都定义，什么时候报 `multiple definition`，什么时候不报？为什么？
4. `gets(buf)` 为什么会覆盖返回地址？栈的增长方向和数组的填充方向各是什么？
5. 说出三种防御缓冲区溢出的机制，各自挡住攻击链的哪一环。

<details>
<summary>参考答案</summary>

1. 每轮循环都要从 `s[i]` 重新扫描到 `'\0'`，总比较次数为 n+(n-1)+…+1 = n(n+1)/2。改成先 `size_t n = strlen(s);` 再循环，或用 `for (; *s; s++)` 边走边判。
2. 报在**链接**阶段（`ld`）。原因：没把定义所在的目标文件加入命令；忘了链接对应库（如 `-lm`）；`-l` 顺序错误；符号被 `static` 修饰导致外部不可见；C++ 名字修饰未加 `extern "C"`。
3. 两个都是**全局**定义时会在链接期报 `multiple definition`；其中一个加了 `static` 就是**局部符号**，链接器根本看不到，因此不冲突。
4. `gets` 不做长度检查，输入超过 `buf` 容量后继续向**高地址**写；而栈帧中返回地址正好位于 `buf` 的高地址一侧，于是被覆盖。函数 `ret` 时把被改写的值弹入 PC。
5. ASLR（让攻击者猜不中地址）、栈金丝雀（检测返回地址是否被改）、NX/DEP（让栈不可执行）；分别对应"猜地址""改返回地址""执行 shellcode"三环。

</details>
