# 1.4 处理器读并解释储存在内存中的指令

> **📖 本节定位**　第 1 章「计算机系统漫游」· 教材 P5–P9

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | 一台计算机的硬件只有四件：**总线、I/O 设备、主存、处理器** |
| 2 | 总线是**共享的电子管道**，一次搬一个字（x86-64 上是 8 字节）；地址、数据、控制都走它 |
| 3 | 主存是**线性的字节数组**，每个字节有唯一地址；它存放的是"正在运行的程序 + 数据" |
| 4 | 处理器 = **PC（程序计数器）+ 寄存器堆 + ALU**，它的全部工作就是不断重复"取指—译码—执行" |
| 5 | PC **始终指向主存中的某条指令**；所谓"运行程序"，就是 CPU 沿着 PC 指的地址一条条往下走 |
| 6 | 磁盘数据进入主存靠 **DMA**——**不经过 CPU 的寄存器**，CPU 只是下达命令和接收中断 |

## 1.4.1 系统的硬件组成

**先说它想解决什么问题**：CPU 再快，也得有人把指令和数据递到它手上。整台机器的硬件，说到底就是一套"把字节从 A 搬到 B、顺手算一下"的物流系统。

类比一个快递分拣中心：

```text
   分拣员（CPU）         传送带（总线）        货架（主存）        卸货口（I/O 设备）
   ─────────────         ─────────────         ─────────────       ─────────────
   只看单子干活           全中心共用一条         格子货架             收货 / 发货都在这
   手边几个暂存格         一次只送一箱           每格一个编号         键盘、屏幕、磁盘
   （寄存器）             （一次 8 字节）        （一格 1 字节）
```

**把类比换成术语**：分拣员 = **处理器（CPU）**；手边的暂存格 = **寄存器堆**；他正盯着的单号 = **PC**；传送带 = **总线**；格子货架 = **主存**；卸货口 = **I/O 设备**。教材把硬件分成四类——总线、I/O 设备、主存、处理器；把 I/O 里的磁盘和显示器拆开数，就是常说的"五大件"。下面逐个说清。

### （1）总线（bus）

总线是贯穿整个系统的**一组电子管道**，负责在部件之间搬运字节。它通常被设计成传送**定长的字节块**，这个长度叫**字（word）**。

| 项目 | 典型值 | 说明 |
| :--- | :--- | :--- |
| 字长（字的大小） | 4 字节（32 位）/ **8 字节（64 位）** | 一次总线事务搬多少 |
| 地址总线宽度 | 与字长相关 | 决定能寻址多少内存 |
| 三类信号 | 数据 / 地址 / 控制 | 合起来叫"系统总线" |

> [!NOTE]
> 这里的"字"是**硬件字长**，和 C 里的 `word` 不是一回事；和 2.1.3 讲的"字长决定指针宽度"是同一个概念。x86-64 的字长是 8 字节。

### （2）I/O 设备

I/O 设备是系统与外界的通道，每个设备都通过**控制器（controller）**或**适配器（adapter）**连到总线上：

| 设备 | 连接部件 | 作用 |
| :--- | :--- | :--- |
| 键盘 / 鼠标 | 控制器 | 输入字符与坐标 |
| 显示器 | 适配器（显卡） | 把内存里的像素/字符显示出来 |
| 磁盘 | 控制器 | 长期存放程序与数据 |

- **控制器**：设备自带的芯片（如磁盘控制器），是设备的一部分；
- **适配器**：插在主板插槽上的卡（如显卡），把总线协议翻译成设备能懂的电信号。

二者对 CPU 而言没有区别：**都是一组可由 CPU 读写的寄存器（端口/内存映射）**。

### （3）主存（main memory）

主存是一个**临时存储设备**，物理上是 DRAM 芯片，逻辑上是**一个线性的字节数组**，每个字节有唯一地址（从 0 开始）。

```text
   地址:   0        1        2        3        4     …    n-1
         ┌────────┬────────┬────────┬────────┬────────┬───┬────────┐
         │ 1 字节 │ 1 字节 │ 1 字节 │ 1 字节 │ 1 字节 │ … │ 1 字节 │
         └────────┴────────┴────────┴────────┴────────┴───┴────────┘
             ↑
         CPU 访存时给的就是这个编号（地址）
```

*图 1-4-1：主存的抽象模型。程序和数据都住在这里，断电即失。*

### （4）处理器（CPU）

CPU 的核心是**程序计数器（PC, Program Counter）**，它永远指向主存中的**下一条要执行的指令**。围绕 PC 还有三件东西：

| 部件 | 全称 | 干什么 |
| :--- | :--- | :--- |
| **PC** | Program Counter | 存下一条指令的**地址**（x86 里叫 `%rip`） |
| **寄存器堆** | register file | 16 个 64 位通用寄存器，存放临时数据与地址 |
| **ALU** | 算术逻辑单元 | 做整数加减、位运算、地址计算 |

CPU 的工作循环只有四步，周而复始：

| 步骤 | 动作 | 一句话 |
| :-: | :--- | :--- |
| ① 取指 | 按 PC 的地址从主存读若干字节 | 读到的字节就是一条指令 |
| ② 译码 | 判断这是 `lea`、`call` 还是 `mov`，取出操作数 | 指令编码决定做什么 |
| ③ 执行 | ALU 运算，或再发起一次访存 | 真正"算"的一步 |
| ④ 更新 PC | PC ← 下一条指令地址 | 顺序则 +长度，跳转则取目标 |

> [!IMPORTANT]
> CPU 眼里**没有"变量""数组""函数"**，只有"从某地址读若干字节、算一算、再写回某地址"。所有高级语言概念，最终都要落到这个循环上。

### （5）四件东西合起来看

```text
   ┌────────────────────────────────────────────────────────────┐
   │  CPU：PC（下一条指令地址）                                 │
   │       寄存器堆（16 个 64 位通用寄存器）                    │
   │       ALU（算术逻辑单元）                                  │
   └──────────────────────────────┬─────────────────────────────┘
                                                                │
   ═══════════════════════════════╪══════════════════════════════
          │               │               │                     │
   ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐
   │  主存      │  │ 键盘/鼠标  │  │  显示器    │  │   磁盘     │
   │  DRAM      │  │  控制器    │  │  适配器    │  │  控制器    │
   └────────────┘  └────────────┘  └────────────┘  └────────────┘
```

*图 1-4-2：教材图 1.4 的骨架。注意：所有设备都挂在**同一条总线**上，这是后面讲"总线是瓶颈"的伏笔。*

<details>
<summary>✅ 检查点 1：PC 里存的是"正在执行"的那条指令地址，还是"下一条"的？</summary>

是**下一条**。取指动作一开始，CPU 就把 PC 更新成"当前地址 + 本条指令长度"（或跳转目标）；等到这条指令真正执行完，PC 早已指向后面了。所以"PC 指向正在执行的指令"只在取指那一瞬间近似成立。
</details>

## 1.4.2 运行 hello 程序

### （1）第 0 步：shell 在等什么

终端里那个 `>` 提示符背后，是一个叫 **shell** 的程序，它正在循环执行 `read` 系统调用，等键盘送来字符：

```text
 键盘 ──扫描码──▶ 键盘控制器 ──总线──▶ CPU ──▶ 主存（shell 的输入缓冲区）
                                              │
                                    一路攒到用户按下回车
                                              │
                                              ▼
                          shell 得到字符串 "./hello"，判断：不是内建命令
```

### （2）第 1 步：加载（loading）

**先说它想解决什么问题**：CPU 只会"按地址取指令"，它不认识"文件名"。所以想让 `hello` 跑起来，第一步必须是**把文件里的字节按地址摆进内存**——这件"摆位"的活就叫**加载（loading）**。

shell 要执行它，于是调用 `fork` + `execve`，真正干活的是**内核里的加载器（loader）**：

```text
   磁盘：hello（ELF 文件 = 文件头 + 若干"节"）
                                                         │
      │  ① shell 调 execve，内核的加载器接手
      ▼
   ┌─────────────────────────────────────────────────────┐
   │  0x400000   .text / .rodata / .data  ← 从文件复制   │
   │  0x7fff…    运行时栈  ← 压入 argv、envp、返回地址   │
   │  0x7f…      共享库 libc 的映射                      │
   └─────────────────────────────────────────────────────┘
                                                         │
      │  ② PC ← 入口点 _start（不是 main！）
      ▼
   libc 启动代码做完初始化，才 call main
```

*图 1-4-3：加载的本质是"把文件里的段搬到内存里，再把 PC 指过去"。教材为了简洁直接说"PC 设为 main"，实际上中间隔着一层 `_start`。*

> [!NOTE] 换个角度想
> 为什么不让内核直接跳到 `main`？因为 C 程序的运行环境得有人先布置好：`argc/argv` 要摆到栈上、libc 要初始化（`stdio` 缓冲区就在这一步建好）、退出处理要登记。这些是**运行时库的职责**，不该塞进内核。`_start` 就是那个"先把场地铺好，再请 `main` 上场"的角色。

<details>
<summary>✅ 检查点 2：既然 `main` 不是入口，那 `main` 里的 `return 0` 返回到哪里去了？</summary>

返回到 `_start` 调 `main` 的那条 `call` 之后，紧接着由 libc 调用 `exit(0)`（或 `exit_group`），才真正结束进程。所以 `main` 的返回值不是"给操作系统"的，而是**给 libc 启动代码**的。
</details>

### （3）第 2 步：取指—译码—执行

`main` 编译出来大概是这样（地址为示意）：

```asm
00000000004004e6 <main>:
  4004e6:   55                    push   %rbp
  4004e7:   48 89 e5              mov    %rsp,%rbp
  4004ea:   48 8d 3d 9f 00 00 00  lea    0x9f(%rip),%rdi   # 400590: "hello, world\n"
  4004f1:   e8 fa fe ff ff        call   4003f0 <puts@plt>
  4004f6:   b8 00 00 00 00        mov    $0x0,%eax
  4004fb:   5d                    pop    %rbp
  4004fc:   c3                    ret
```

CPU 就这么一条条走：

| 时刻 | PC | 做的事 |
| :-: | :--- | :--- |
| t1 | `0x4004e6` | 取指 `push %rbp`，压栈，PC ← `0x4004e7` |
| t2 | `0x4004e7` | 取指 `mov %rsp,%rbp`，建立栈帧，PC ← `0x4004ea` |
| t3 | `0x4004ea` | `lea` 算出 `0x400590` 放进 `%rdi`——**字符串的地址进了寄存器** |
| t4 | `0x4004f1` | `call`：把返回地址 `0x4004f6` 压栈，PC ← `0x4003f0` |
| t5 | `0x4003f0` | PLT 桩：间接跳到 libc 里真正的 `puts` |
| t6 | libc 内部 | `puts` 逐字节把 `hello, world\n` 写出去 |
| t7 | `0x4004f6` | `ret` 返回，`main` 结束，进程退出 |

#### 一起算一遍

把上面那段 `main` 的**指令长度**和 **PC 变化**逐条对上（指令长度 = `objdump` 相邻两行地址之差）：

| 步骤 | 指令地址 | 机器码字节数 | 指令 | 执行后 PC | 栈 / 寄存器变化 |
| :-: | :--- | :-: | :--- | :--- | :--- |
| ① | `0x4004e6` | 1 | `push %rbp` | $0x4004e6 + 1 = 0x4004e7$ | `%rsp -= 8`，旧 `%rbp` 入栈 |
| ② | `0x4004e7` | 3 | `mov %rsp,%rbp` | $+ 3 = 0x4004ea$ | `%rbp = %rsp`（栈帧建好） |
| ③ | `0x4004ea` | 7 | `lea 0x9f(%rip),%rdi` | $+ 7 = 0x4004f1$ | `%rdi = 0x400590`（字符串地址） |
| ④ | `0x4004f1` | 5 | `call 4003f0` | **`0x4003f0`**（跳转，不是 +5） | `%rsp -= 8`，压入 `0x4004f6` |
| ⑤ | `0x4004f6` | 5 | `mov $0x0,%eax` | $+ 5 = 0x4004fb$ | `%eax = 0`（`main` 的返回值） |
| ⑥ | `0x4004fb` | 1 | `pop %rbp` | $+ 1 = 0x4004fc$ | 恢复 `%rbp`，`%rsp += 8` |
| ⑦ | `0x4004fc` | 1 | `ret` | **弹出栈顶**（`_start` 里的地址） | `%rsp += 8`，`main` 结束 |

两个容易看漏的点：

1. **只有 `call` / `ret` / `jmp` 会让 PC "跳"**，其余一律是"当前地址 + 本条指令长度"。所以"PC 自动加 1"是错的——x86 指令变长（1~15 字节），必须加**长度**。
2. 第 ③ 步的 `lea` 用的是 `%rip` **相对寻址**，基址是**下一条指令**的地址 `0x4004f1`，不是 `0x4004ea`：$0x4004f1 + 0x9f = 0x400590$，正好是字符串地址。

> [!WARNING]
> `call` 压栈的是**返回地址**（`0x4004f6`），不是参数。参数早在 `t3` 就通过 `%rdi` 传过去了。这一点和 1.3.3 的缓冲区溢出直接相关——**返回地址就在栈上，且紧挨着局部数组**。

### （4）第 3 步：输出到屏幕

`puts` 不是直接点像素，它只是把一串**字节**（`'h','e','l','l','o',…,'\n'`）交给操作系统，走的是一条固定的路：

```text
  puts ──write(1, buf, 13)──▶ 内核
                                │  按文件描述符 1 找到"标准输出"
                                ▼
                        显示适配器（显卡 / 终端模拟器）
                                │  把字符码 → 字模 → 像素
                                ▼
                            显示器（一串像素）
```

教材的措辞是：**这些字节被直接复制到显示适配器**，适配器再把它们显示在屏幕上。整个过程对程序完全不透明——程序只知道"我交出去一串字节"。

> [!NOTE]
> 别把**字符数**和**占用字节数**搞混：`"hello, world\n"` 是 **13 个字符**，`write` 交出去的正是 13 个字节；但它在内存里还要多占 1 个字节放结尾的 `'\0'`，所以 `sizeof("hello, world\n")` 是 **14**。`write` 不写那个 `'\0'`——它只按你给的长度搬字节。

### （5）DMA：为什么数据不经过 CPU

前面说"从磁盘加载"，很多人会脑补成"磁盘 → CPU → 内存"。**不是的。**

**先说它想解决什么问题**：如果每个字节都要 CPU 亲手从磁盘搬到内存，CPU 就成了搬运工——传 1 MB 数据要执行几十万次"读—写"，这期间什么正事都干不了。

```text
  ① 程序控制 I/O（PIO）：每个字节都要过 CPU
     磁盘 ──▶ 磁盘控制器 ──总线──▶ CPU 寄存器 ──总线──▶ 主存
                                    （CPU 全程当搬运工，累且慢）

  ② DMA（Direct Memory Access）：CPU 只下命令，数据自己走
     CPU ──①"把 hello 的 4 KB 搬到 0x400000"──▶ 磁盘控制器
     磁盘控制器 ──② 直接写主存（不经 CPU）──────▶ 主存
     磁盘控制器 ──③ 完成后发中断 ──────────────▶ CPU
```

*图 1-4-4：DMA 把"搬字节"这件事从 CPU 手里拿走，CPU 只在开头和结尾出现两次。*

**换个说法**：PIO 是"调度室主任亲自下楼搬货"；DMA 是"主任给搬运工一张地址单，货直接进仓库，搬完按铃通知"。主任只在**开头下单**和**结尾验收**时出现两次，中间的时间可以继续调度别的车。

**形式化定义**：**DMA（Direct Memory Access，直接存储器访问）** 指 I/O 设备控制器在**不经过 CPU 寄存器**的前提下直接读写主存；CPU 只负责初始化这次传输（源、目的、长度）并在结束时处理**中断**。

> [!IMPORTANT]
> 教材明确写着：**磁盘控制器直接把字节从磁盘送到主存，不经过处理器。** 这是理解"为什么 I/O 可以和计算重叠"的关键——DMA 干活时 CPU 可以继续算别的东西。

#### 一起算一遍

加载 `hello` 的一个 4 KB 段，把 PIO 和 DMA 两种搬法摆在一起比（数字为量级估算）：

| 步骤 | 在干什么 | PIO（CPU 当搬运工） | DMA（控制器搬） |
| :-: | :--- | :--- | :--- |
| ① | 总线一次搬 8 字节，4 KB 要搬几次 | 512 次 | 512 次 |
| ② | CPU 要执行多少条指令 | ≈ 4 条/字节 × 4096 = 16384 条 | 设置源/目的/长度，约 10 条 |
| ③ | 折成 CPU 时间（3 GHz，约 1 条指令/周期） | ≈ 5.5 µs，**期间 CPU 被绑住** | ≈ 0.003 µs，之后 CPU 去跑别的 |
| ④ | 谁来收尾 | CPU 全程盯着搬完 | 控制器发中断，CPU 处理一次 |

关键不是 5.5 µs 这个数，而是**这 5.5 µs 里 CPU 在不在场**：PIO 把它全耗在搬字节上，DMA 则把它花在别的事情上。段越大差距越值钱——加载一个 100 MB 的程序，这笔账就是 $25600 \times 5.5\,\mu s$ ≈ 140 ms 的差别。

<details>
<summary>✅ 检查点 3：DMA 搬运期间，CPU 在干什么？它怎么知道搬完了？</summary>

CPU 在**继续执行别的指令**（比如另一个进程的代码），不空等。搬完后磁盘控制器发一个**中断**，CPU 暂停手头工作，跳进内核的中断处理程序，把"数据已就绪"这件事记下来，然后回到原来的地方继续跑。
</details>

```text
四部件   : 总线 / I/O 设备 / 主存 / 处理器
总线     : 共享电子管道，一次搬一个字（x86-64 = 8 字节）
主存     : 线性字节数组，每字节一个地址，DRAM，断电即失
处理器   : PC + 寄存器堆（16×64 位）+ ALU
工作循环 : 取指 → 译码 → 执行 → 更新 PC
PC       : 始终指向下一条指令；x86 里就是 %rip
加载     : loader 把 ELF 的段复制到内存，PC ← 入口点 _start
call     : 压栈的是返回地址，不是参数（参数走 %rdi, %rsi, …）
输出     : puts → 内核 → 显示适配器 → 显示器
DMA      : 磁盘控制器直接写主存，不经过 CPU 寄存器
```

---

## ⚠️ 易错点

1. **以为"内存 = 硬盘"。** 主存是 DRAM，断电内容全丢；磁盘才是长期存储。程序必须**先被加载到主存**才能运行。
2. **以为磁盘数据要经过 CPU。** 那是 PIO；现代系统用 **DMA**，数据从磁盘控制器直接进主存，CPU 只发命令、收中断。
3. **把"字长"理解成 C 的 `word`。** 硬件字长是总线一次搬运的位数（8 字节），C 的 `int` 是 4 字节，两者无关。
4. **以为 PC 指向"正在执行"的指令。** 取指之后 PC 就已经更新了，所以严格说 PC 指向**下一条**指令的地址。
5. **以为 `main` 是程序的入口。** 真正的入口是 `_start`，它初始化 libc 后才调用 `main`；`main` 的 `ret` 也是返回到 libc，由它调 `exit`。
6. **把 `call` 和 `jmp` 混为一谈。** `call` 会压入返回地址，`jmp` 不会——这决定了函数能不能 `ret` 回来。

## ❓ 常见困惑

**Q：CPU 一次只执行一条指令，为什么电脑能同时开几十个程序？**
A：靠**分时**。单核上任何时刻确实只有一条指令在执行，但操作系统每隔几毫秒就换一个进程上场（上下文切换），切换得足够快，人就感觉在"同时"跑。真正的并行要多个核，见第 8 章异常控制流与第 12 章并发。

**Q：程序里的地址 `0x400000` 是谁定的？为什么不是从 0 开始？**
A：那是**链接器**按链接脚本定下的虚拟地址；从 0 开始的一段留给空指针陷阱和内核，用户程序从 `0x400000` 起是 x86-64 的惯例。程序看到的是虚拟地址，真正的物理内存在哪由操作系统和 MMU 映射（第 9 章）。

**Q：`call` 会往栈里压返回地址，那参数会不会被覆盖？**
A：不会，两者在不同的地方。x86-64 的参数走**寄存器**（`%rdi`、`%rsi`、`%rdx`…，超过 6 个才上栈），和 `call` 压入的返回地址互不干扰。正因为参数在寄存器里，被调函数想改也得先存到自己的栈帧里。

**Q：DMA 直接写主存，CPU 的 cache 里不是留着旧数据吗？**
A：现代系统不会。DMA 设备走的是**cache 一致**的互连（PCIe 设备通过 IOMMU/探听机制参与一致性协议），写主存时会顺带让相关 cache 行失效。只有很老的、非一致的 DMA 才需要驱动手动刷 cache——那正是"设备驱动难写"的经典原因之一。

## 🛠 动手试试

1. 用地址差验证"指令是变长的"：

   ```bash
   objdump -d hello | sed -n '/<main>:/,+8p'
   ```

   预期：每行最左边是地址，相邻两行地址之差 = 上一行机器码的字节数。`push %rbp` 占 1 字节、`lea` 占 7 字节——和「一起算一遍」的表对得上。

2. 看 `puts` 到底交给了内核什么：

   ```bash
   strace -e trace=write ./hello
   ```

   预期：出现一条 `write(1, "hello, world\n", ...)`，返回值就是写出的字节数。这说明程序只负责"把字节交给内核"，屏幕上的像素不归它管。

3. 确认入口点不是 `main`：

   ```bash
   readelf -h hello | grep Entry
   objdump -d hello | grep -A1 '<_start>:'
   ```

   预期：`Entry point address` 是 `0x4010f0` 之类，和 `objdump` 里 `<main>` 的地址**不一样**；`_start` 里能看见 `call` 到 `__libc_start_main`，`main` 的地址是作为参数传进去的。

## ✅ 自测

1. 组成计算机硬件的四大部分是什么？各自的作用？
2. 处理器内部最小的一套部件是哪三个？PC 里存的是什么？
3. 描述 CPU 的四步工作循环。
4. `./hello` 是怎样从磁盘进入内存的？这个过程里 CPU 参与了哪些环节？
5. 为什么说 DMA 让 I/O 与计算可以重叠？
6. `call` 指令执行时，压入栈的是参数还是返回地址？

<details>
<summary>参考答案</summary>

1. 总线（部件间传递字节的共享电子管道）、I/O 设备（与外界交互的通道）、主存（存放运行中的程序与数据的临时存储）、处理器（解释并执行内存中的指令）。
2. PC（程序计数器）、寄存器堆、ALU。PC 存放**下一条要执行指令的地址**。
3. 取指（按 PC 地址从主存读指令字节）→ 译码（判断指令类型、取操作数）→ 执行（ALU 运算或访存）→ 更新 PC（顺序或跳转到目标地址）。
4. shell 通过 `fork`+`execve` 请求内核；内核的加载器把 ELF 的各段从磁盘复制到主存，建立栈并把 PC 设为入口点。数据搬运由磁盘控制器通过 **DMA 直接写入主存**，CPU 只负责发命令、设 PC、接收完成中断。
5. 因为搬运字节的工作由磁盘控制器完成，CPU 在 DMA 进行期间可以继续执行别的指令，只在开始时下命令、结束时处理中断。
6. 返回地址。参数通过寄存器（`%rdi`、`%rsi` 等）传递。

</details>
