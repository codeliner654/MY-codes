# 1.5 高速缓存至关重要

> **📖 本节定位**　第 1 章「计算机系统漫游」· 教材 P9
> **一句话**：CPU 和主存的速度差了一两个数量级，于是人们在两者之间塞进一块小而快的 **cache**；而 cache 之所以有用，靠的是程序天生具有的**局部性**。

> [!IMPORTANT] 本节要回答的三个问题
> 1. CPU 明明很快，为什么程序还是慢？它到底在等什么？
> 2. `cache` 是什么东西？为什么加了它，同一个程序能快十倍？
> 3. 为什么有些代码"把循环顺序换一下"就快好几倍？我写代码时该顺着什么写？

**读之前你需要会**：内存（主存）是"一排带编号的格子"、`int` 占 4 字节、数组元素在内存里连续存放（见 [1.4 处理器读并解释储存在内存中的指令](1.4%20处理器读并解释储存在内存中的指令.md) 的主存模型）。都不会也没关系——本节只需要"格子"这个画面。

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | 处理器与主存之间有**巨大速度差**：一条算术指令 1 个周期，一次访存要上百个周期 |
| 2 | **cache（高速缓存）**是一块小而快的临时存储，存放 CPU **最近可能会用**的指令与数据 |
| 3 | 现代 CPU 一般有 **L1**（几万字节）和 **L2**（几十万字节）两级，都在 CPU 芯片上 |
| 4 | cache 有效的前提是**局部性**：时间局部性（刚用过的还会用）+ 空间局部性（挨着的会一起用） |
| 5 | 命中（hit）快、未命中（miss）慢；未命中时按**块**（通常 64 字节）从主存整批搬入 |
| 6 | L1/L2 用 **SRAM**，主存用 **DRAM**——快、贵、占面积，所以只能做小 |

## 1.5.1 处理器与主存之间的鸿沟

教材在 1.4 节介绍了 `hello` 的运行，随后立刻泼了一盆冷水：

> 系统花费了大量时间把信息从一个地方挪到另一个地方。

程序里一条 `movq 0x0(%rbp), %rax` 看起来和 `addq %rax, %rbx` 差不多，实际代价却差了两个数量级：

| 操作 | 典型延迟 | 相当于 |
| :--- | ---: | :--- |
| 寄存器访问 | < 1 个周期 | 从口袋里掏东西 |
| L1 cache 命中 | ≈ 4 个周期 | 从桌上拿 |
| L2 cache 命中 | ≈ 10 个周期 | 从抽屉里拿 |
| 主存访问 | ≈ 100 个周期 | 去楼下仓库搬 |

```text
   CPU 执行一条指令约 0.3 ns      主存访问约 30~100 ns
        │                              │
        └────────── 相差 100 倍 ────────┘
                     │
                     ▼
        如果每条指令都要等主存，CPU 99% 的时间都在发呆
```

> [!IMPORTANT]
> 这个差距不是"优化一下"就能补上的，它是**物理规律**：CPU 越快，差距越大。整个第 6 章都在讲人们如何用层次结构来掩盖这个鸿沟。

## 1.5.2 高速缓存（cache）是什么

**先说它想解决什么问题**：你写作业时，不会每查一个字就跑一趟图书馆书库。手边是**书桌**（只放正在写的几页），身后是**书架**（这一章要用的书），走廊尽头才是**仓库**（全部藏书）。取一趟书的路上，够你写一百个字——所以"把可能用到的搬到近处"是唯一可行的办法。

```text
   书桌     伸手就拿到     只放当前那几页      ← 寄存器（小于 1 个周期）
   书架     起身走几步     放这一章要用的      ← L1 / L2 cache（4 ~ 10 个周期）
   仓库     走几分钟       放全部藏书          ← 主存（约 100 个周期）
```

**形式化定义**：cache 是一个**小而快**的存储设备，作为更大、更慢设备中部分数据的**暂存区**。

一次命中到底省多少？把 1.5.1 那张延迟表的数字直接相减：

| 对比 | 省下 | 折成时间（3 GHz，1 周期 ≈ 0.33 ns） |
| :--- | ---: | ---: |
| L1 命中 vs 直接访存 | $100 - 4 = 96$ 个周期 | ≈ 32 ns |
| L2 命中 vs 直接访存 | $100 - 10 = 90$ 个周期 | ≈ 30 ns |

单看 32 ns 微不足道。但如果一个循环要访问 $10^9$ 次内存：全命中约 $4 \times 10^9$ 个周期 ≈ 1.3 秒，全未命中约 $100 \times 10^9$ 个周期 ≈ 33 秒——**省周期这件事，乘上亿次才显出威力**。

在 `hello` 这个例子里：

```text
   ① 程序启动时
      磁盘上的 hello ──▶ 主存（一大片 DRAM）
   ② 执行过程中
      主存里的指令与数据 ──▶ 复制到 CPU 芯片上的 cache
   ③ 之后 CPU 取指/取数
      先问 L1 → 再问 L2 → 都没有才去主存
```

```text
   寄存器     ──  1 个周期        容量：几百字节
     ▲
     │  快约 4 倍
   L1 cache  ──  约 4 个周期      容量：32 KB 左右
     ▲
     │  慢约 2~3 倍
   L2 cache  ──  约 10 个周期     容量：256 KB ~ 1 MB
     ▲
     │  慢约 10 倍
   主存(DRAM) ──  约 100 个周期   容量：8 GB ~ 64 GB
```

*图 1-5-1：处理器侧的三级"近身存储"。越往上越快、越贵、越小。*

**一次访存的完整判断流程**：

```text
   CPU 要读地址 A 的 8 个字节
        │
        ▼
   ① L1 里有 A 所在的那个"块"吗？
        ├── 有（hit）──▶ 约 4 个周期拿到数据，结束
        └── 没有（miss）
              ▼
   ② L2 里有吗？
        ├── 有（hit）──▶ 约 10 个周期，把块搬进 L1，返回
        └── 没有（miss）
              ▼
   ③ 去主存取整块（64 字节）→ 先装 L2 → 再装 L1 → 返回，约 100 个周期
```

> [!NOTE]
> 注意"**块（block）**"这个词：cache 和主存之间不是按字节交换，而是按**固定大小的块**（x86 上通常 64 字节）整批搬运。这一点是空间局部性能够生效的硬件基础。

#### 一起算一遍

假设 `./hello` 这一趟（`main` 加上 `puts` 内部的循环）一共发起 $N = 1000$ 次访存，CPU 主频 3 GHz（1 个周期 ≈ 0.33 ns）。

**先算没有 cache 的情况**：

| 步骤 | 在干什么 | 结果 |
| :-: | :--- | ---: |
| ① | 每次访存都走到主存：$1000 \times 100$ | 100 000 个周期 |
| ② | 折成时间：$100\,000 \div (3 \times 10^{9})$ | ≈ 33 µs |

**再算有 cache、命中率 95% 的情况**：

| 步骤 | 在干什么 | 结果 |
| :-: | :--- | ---: |
| ① | 平均每次访存 = 命中比 × 命中代价 + 未命中比 × 未命中代价 = $0.95 \times 4 + 0.05 \times 100$ | 3.8 + 5.0 = 8.8 个周期 |
| ② | 1000 次：$1000 \times 8.8$ | 8 800 个周期 |
| ③ | 折成时间：$8\,800 \div (3 \times 10^{9})$ | ≈ 2.9 µs |

**结论**：33 µs → 2.9 µs，快了约 **11 倍**。注意命中率只有 95%（听起来不算高），平均代价却从 100 掉到 8.8——因为**每次命中省下的 96 个周期，把少数几次未命中的代价摊平了**。就算命中率掉到 80%，平均代价也只有 $0.8 \times 4 + 0.2 \times 100 = 23.2$ 个周期，仍比 100 快 4 倍多。**"大多数访问命中"比"每次都快"更现实、也更重要。**

<details>
<summary>✅ 检查点 1：命中率从 95% 提到 99%，值得大动干戈去优化吗？</summary>

值得。平均代价从 $0.95\times4 + 0.05\times100 = 8.8$ 降到 $0.99\times4 + 0.01\times100 = 4.96$ 个周期，**接近再快一倍**；因为未命中那 100 个周期是"权重极大"的少数。反过来说，命中率从 99% 掉到 95%，性能就掉一半——这就是"少数未命中很贵"的含义。
</details>

## 1.5.3 局部性：cache 为什么有用

如果程序的下一条指令、下一个数据完全随机，cache 一点用都没有。但真实程序有**局部性（locality）**：

| 类型 | 含义 | 典型来源 |
| :--- | :--- | :--- |
| **时间局部性** | 刚被访问过的数据，很可能马上再被访问 | 循环变量、循环体、反复调用的函数 |
| **空间局部性** | 地址相邻的数据，很可能接连被访问 | 数组、顺序执行的指令、结构体成员 |

```c
int sum(int a[N])
{
    int s = 0;
    for (int i = 0; i < N; i++)
        s += a[i];          /* a[0] a[1] a[2] … 地址连续 */
    return s;
}
```

```text
   a[0] a[1] a[2] … a[15] │ a[16] … a[31] │ …
   └────── 一个 64 字节块（16 个 int）──────┘
        ▲
        └─ 首次访问 a[0] 未命中，硬件把整块搬进 cache
           → 接着访问 a[1]…a[15] 全部命中

   平均未命中率 ≈ 1/16 ≈ 6.25%，而不是 100%
```

*图 1-5-2：顺序访问 `int` 数组时，一次未命中换来 15 次命中。这就是空间局部性的价值。*

对比一下"反例"：

| 写法 | 局部性 | 后果 |
| :--- | :--- | :--- |
| `for (i…) s += a[i];` | 空间局部性好 | 未命中率 ≈ 1/16 |
| 链表逐节点 `p = p->next` | 空间局部性差（节点散落） | 几乎每次都未命中 |
| 二维数组按列遍历 `a[i][j]`（内层 j 固定 i） | 跨行跳 4 KB，浪费整块 | 未命中率高得多 |

> [!NOTE] 换个角度想
> 局部性不是硬件的运气，而是**程序写法的产物**：只要有循环，同一条指令就会被反复取（时间局部性）；只要用数组，相邻元素就会挤在同一块里（空间局部性）。反过来，链表、哈希表、指针追逐天生局部性差——**这是数据结构选型里很少有人提、但实测能差 10 倍的一条暗线**。

> [!WARNING]
> `for (i = 0; i < N; i++) for (j = 0; j < N; j++) sum += a[j][i];` 和把 `i`、`j` 换过来的写法**结果相同、速度差好几倍**——差别只在 cache。写代码时"顺着内存走"是个好习惯。

<details>
<summary>✅ 检查点 2：`for (i…) for (j…) sum += a[j][i];` 慢在"跳"还是慢在"读"？</summary>

慢在**跳**。元素总量一样、读的次数完全一样，区别是每次访问 `a[j][i]` 都要跨过一整行（$N \times 4$ 字节）去拿同一列的下一个元素——刚搬进来的 64 字节块里只有 1 个元素用得上，其余 15 个全被浪费。把 `i`、`j` 换过来，一次搬块就能连用 16 个元素。
</details>

## 1.5.4 `hello` 程序的 cache 之旅

回到那一小段 `main`：

```asm
  4004e6:   push   %rbp
  4004e7:   mov    %rsp,%rbp
  4004ea:   lea    0x9f(%rip),%rdi     # 字符串地址
  4004f1:   call   4003f0 <puts@plt>
```

| 阶段 | 数据从哪到哪 | 靠什么局部性 |
| :--- | :--- | :--- |
| 加载 | 磁盘 → 主存 | —（DMA，见 1.4） |
| 首次取指 | 主存 → L2 → L1 | 空间：后面几条指令就在同一块里 |
| 顺序执行 | 全部 L1 命中 | 空间：指令地址连续 |
| 读字符串 | 主存 → L2 → L1 | 空间：`"hello, world\n"` 是连续字节 |
| 循环/重复调用 | L1 直接命中 | 时间：同一条指令反复执行 |

> [!TIP]
> 教材的一句话可以背下来：**`hello` 程序中的指令和数据在运行过程中被"复制"到 cache 里，CPU 之后就直接和 cache 打交道，而不是主存。** 程序本身完全不知道这件事——这是硬件自动完成的透明优化。

## 1.5.5 为什么 cache 能比主存快：SRAM 与 DRAM

cache 用的是 **SRAM（静态 RAM）**，主存用的是 **DRAM（动态 RAM）**。差别在存储单元的构造：

| 对比项 | SRAM | DRAM |
| :--- | :--- | :--- |
| 每bit 元件 | **6 个晶体管**（双稳态触发器） | **1 个电容 + 1 个晶体管** |
| 是否需要刷新 | 不需要，通电即保持 | 需要周期性刷新（电容漏电） |
| 速度 | 快（1~4 周期） | 慢（~100 周期） |
| 集成度 | 低（占面积大） | 高（同样面积容量大） |
| 成本 | 贵 | 便宜 |
| 典型用途 | 寄存器、L1/L2/L3 | 主存 |

```text
   SRAM 单元（6T）   DRAM 单元（1T1C）
   ┌────────────┐    ┌────────────┐
   │ 6 个晶体管 │    │ 电容 + 1T  │
   └────────────┘    └────────────┘
    稳定、快、占地方  简单、密、会漏电
```

#### 一起算一遍

算一下"把 8 GB 主存做成 SRAM"到底有多离谱：

| 步骤 | 在干什么 | 结果 |
| :-: | :--- | ---: |
| ① | 32 KB 的 L1 = $32 \times 1024 \times 8$ bit，每个 SRAM bit 要 6 个晶体管：$262144 \times 6$ | ≈ 157 万个晶体管 |
| ② | 8 GB 主存 = $8 \times 1024^{3} \times 8$ bit，若也用 SRAM，再乘 6 | ≈ $4.1 \times 10^{11}$ 个晶体管 |
| ③ | ② 是 ① 的多少倍 | ≈ 26 万倍 |

一颗存储芯片能塞十几亿个晶体管已经很吃力，而 4000 亿个**单是面积和成品率就不可能**。反过来用 DRAM（1 个电容 + 1 个晶体管），8 GB 只要 $6.87 \times 10^{10}$ 个单元——这才做得出来。**"快"和"大"在物理上不可兼得，唯一出路是分层。**

> [!NOTE]
> 一句话总结取舍：**SRAM 快但贵，所以只能做小（几 MB）；DRAM 慢但便宜，所以能做大（几十 GB）。**"既要大又要快"的唯一出路就是**层次结构**——这正是下一节 1.6 的内容。

<details>
<summary>✅ 检查点 3：既然 SRAM 快 100 倍，为什么 CPU 里不做一块 1 GB 的 SRAM 当主存？</summary>

三个原因叠加：**面积**（6 个晶体管才存 1 bit，见上面的算例）、**成本**（同样容量贵几十倍）、**速度反而会降**（容量越大，译码和比较电路越复杂、连线越长，命中延迟从 4 个周期涨上去）。所以工程上的最优解是**小而快的 L1 + 大一点的 L2 + 更大的主存**，靠层次结构而不是靠一块巨无霸。
</details>

## 📌 重点速记

```text
问题     : CPU 与主存速度差约 100 倍
cache    : 小而快的暂存区，存"最近可能用到"的数据
层次     : 寄存器 → L1(32KB,~4周期) → L2(256KB,~10周期) → 主存(~100周期)
单位     : 按"块"搬运，x86 通常 64 字节（= 16 个 int）
命中/未命中: hit 快；miss 则从下一层整块搬上来
局部性   : 时间局部性（反复用同一份）+ 空间局部性（用相邻的）
数组遍历 : 一次 miss 换来 15 次 hit，miss 率 ≈ 1/16
SRAM     : 6 个晶体管，快、贵、不刷新 → 做 cache
DRAM     : 1 电容 + 1 晶体管，慢、便宜、要刷新 → 做主存
结论     : 程序对 cache 完全无感，这是硬件自动做的
```

---

## ⚠️ 易错点

1. **以为 cache 是软件管理的。** 对程序员透明，硬件自动搬运；你能做的只是**写出局部性好的代码**。
2. **以为 cache 按字节缓存。** 它按**块**（64 字节）搬运，所以读 1 个字节也会顺带把邻居都拉进来。
3. **把"命中率"和"未命中率"弄反。** 命中率 95% 意味着未命中率 5%，不是反过来。
4. **以为 L1 越大越好。** L1 越大越慢（寻址与比较电路更复杂），所以 L1 小、L2 大，靠层次配合。
5. **以为数组遍历"反正都要读一遍"，快慢无所谓。** 顺序 vs 跳跃访问的差距可以到 10 倍以上，这是第 6 章反复验证的结论。

## ❓ 常见困惑

**Q：cache 里的数据和主存会不会"对不上"？谁负责同步？**
A：硬件负责。写命中时用**写回（write-back）**：只改 cache，并给这一行打"脏"标记，等它被换出时才写回主存；读别的地址时如果撞上脏行，也先写回。多核之间还有一致性协议（MESI 一类）保证大家看到同一份数据——**程序员不需要写任何同步 cache 的代码**。

**Q：既然 cache 按 64 字节整块搬，我只读 1 个字节也要搬 64 个，不浪费吗？**
A：单看这一次是浪费 63 字节；但设计赌的是**你马上会读旁边那些**。顺序遍历数组时这个赌注几乎必赢（1 次未命中换 15 次命中）；指针乱跳时它会输——这就是"局部性差的代码在 cache 上特别吃亏"的另一面。

**Q：我需要手动把数据搬进 cache 吗？`volatile` 是不是干这个的？**
A：都不需要。搬运完全由硬件自动完成，程序结果和没有 cache 时**一模一样**，只是快慢不同。`volatile` 是告诉编译器"别把这个变量优化进寄存器、每次都去内存读"，它管的是**编译器优化**，不是 cache——而且它也不会让访问变快，只会变慢。

**Q：数组"反正都要读一遍"，顺序读和乱序读真能差那么多？**
A：能，差 5~10 倍很常见。因为瓶颈不是"读了多少字节"，而是"发生了多少次 100 周期的未命中"。顺序读 16 个 `int` 只欠 1 次；跨行读 16 个 `int` 欠 16 次——同样的字节数，等待时间差一个数量级。

   ```bash
   #include <stdio.h>
   static int a[4096][4096];               /* 64 MB，放得进内存 */
   int main(void){ long s=0; for (int i=0;i<4096;i++) for (int j=0;j<4096;j++) s+=a[i][j]; printf("%ld\n", s); return 0; }
   EOF
   gcc -O2 m.c -o m && time ./m
   ```

   预期：约几十毫秒。把内层改成 `a[j][i]`（列优先）再编译运行，通常会慢 **5~10 倍**——代码量一样、加法次数一样，差别只在每次访问是不是落在同一个块里。

3. 用 `perf` 直接看未命中率：

   ```bash
   perf stat -e cache-references,cache-misses ./m
   ```

   预期：顺序版的 `cache-misses / cache-references` 通常在几个百分点；换成列优先后会明显升高。**这就是"局部性变差"在硬件计数器上的样子。**

## ✅ 自测

1. 为什么要在 CPU 和主存之间加 cache？不加会怎样？
2. 时间局部性和空间局部性各是什么意思？各举一个代码例子。
3. 遍历一个 `int a[1000]` 的数组（64 字节块），大致会未命中多少次？未命中率约多少？
4. SRAM 和 DRAM 的本质区别是什么？为什么缓存用 SRAM 而主存用 DRAM？
5. "cache 对程序员透明"具体指什么？

<details>
<summary>参考答案</summary>

1. 因为 CPU 与主存速度相差约两个数量级，每次访存都等主存会让 CPU 大部分时间空转。cache 把最近可能用到的数据放在近处，使绝大多数访问在 4~10 个周期内完成。
2. 时间局部性：刚访问过的数据很可能马上再访问（如循环体里的变量 `s`、反复执行的指令）；空间局部性：地址相邻的数据很可能接连访问（如 `a[0]`、`a[1]`、`a[2]` 或顺序执行的指令）。
3. `1000 × 4 = 4000` 字节，每块 64 字节装 16 个 int，共约 `4000/64 ≈ 63` 次未命中，未命中率 ≈ 1/16 ≈ 6.25%。
4. SRAM 用 6 个晶体管构成双稳态触发器，不需刷新、速度快但占面积、成本高；DRAM 用 1 个电容 + 1 个晶体管，密度高、便宜但需刷新、速度慢。因此 SRAM 只适合做小容量的 cache。
5. 编译器与程序员都不需要显式地把数据搬进 cache；硬件自动判断命中/未命中并完成块搬运，程序结果与不加 cache 时完全一致，只是快慢不同。

</details>
