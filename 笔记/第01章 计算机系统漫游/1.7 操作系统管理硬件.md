# 1.7 操作系统管理硬件

> **📖 本节定位**　第 1 章「计算机系统漫游」· 教材 P10–P14
> **一句话**：程序不能直接操作硬件——中间隔着一层**操作系统**，它用**进程、虚拟内存、文件**三个抽象，把"一堆芯片"包装成程序员熟悉的世界。

> 2. 只有一个 CPU，凭什么能"同时"跑浏览器、音乐播放器和终端？
> 3. 机器只有 8 GB 内存，为什么每个进程都以为自己有 4 GB 可用？

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | 操作系统是**应用程序与硬件之间的软件层**，所有程序对硬件的请求都必须经过它 |
| 2 | **进程**是操作系统对"正在运行的程序"的抽象；CPU 看似同时跑多个进程，其实是**交替执行** |
| 3 | **上下文切换**保存/恢复一个进程的全部运行状态，是"并发假象"的实现机制 |
| 4 | **虚拟内存**为每个进程提供一个**独立、一致**的地址空间，并负责虚拟地址到物理地址的翻译 |
| 5 | **文件**就是**字节序列**；"一切皆文件"让所有 I/O 设备共享 `read` / `write` 这一套接口 |
| 6 | 三大抽象的分工：**文件→I/O 设备，虚拟内存→主存+磁盘，进程→处理器+主存+I/O** |

## 1.7.1 进程

**先说它想解决什么问题**：一颗 CPU、一片内存，而你想同时开浏览器、听歌、编译代码。没有一层管理者，会立刻出现三个致命问题：

```text
   ① 浏览器在跑 → 终端永远拿不到 CPU（除非浏览器主动让出）
   ② 编译器写错一个指针 → 直接覆盖浏览器的内存，两个一起崩
   ③ 每个程序都要自己算"数据在物理内存第几号字节" → 换台机器地址全变
```

操作系统的回答分别是 **进程**（谁用 CPU）、**虚拟内存**（谁能看哪段内存）、**文件**（怎么碰设备）。生活版：一家餐厅只有一个厨房，老板给每桌发号、轮流上菜（进程），每桌只看得到自己的桌子（隔离），后厨的灶台冰箱对客人统一叫"点菜"（文件）。

### （1）操作系统在哪儿

```text
   应用程序（hello、shell、浏览器 …）

   操作系统内核（进程调度 / 虚拟内存 / 文件系统 / 设备驱动）

   硬件（处理器 + 主存 + I/O 设备）
```

应用程序**没有权限**直接读写磁盘、直接改页表；它只能通过**系统调用**请内核代劳。

### （2）进程是什么

**进程（process）**是操作系统对一个**正在运行的程序**的一种抽象。

- 程序（program）是磁盘上的静态文件（`hello`）；
- 进程（process）是它在内存中"活起来"的样子——有 PC、有栈、有打开的文件。

当我们在 shell 里敲下 `./hello`，shell 通过 `fork` + `execve` 创建了一个新进程；`hello` 运行结束后，shell 继续运行。在用户看来，两个程序"同时存在"。

### （3）并发运行的假象

现代操作系统让**一个 CPU 看起来在同时执行多个进程**，靠的是**交错执行**：

```text
   时间 ───────────────────────────────────────────────▶

   CPU  │ shell │ hello │ shell │ hello │ shell │ hello │ …
         └───────┴───────┴───────┴───────┴───────┴───────┘
           每个进程都以为自己独占 CPU，其实是被切成了碎片
```

*图 1-7-1：并发（concurrency）不是"同时"，而是"快速轮流"。真正的"同时"要等到 1.9.2 的多核。*

### （4）上下文与上下文切换

内核要能随时"暂停"一个进程，就必须把它当时的**全部状态**存下来，这个状态叫**上下文（context）**：

| 上下文包含 | 说明 |
| :--- | :--- |
| PC | 下一条要执行的指令在哪 |
| 通用寄存器 | 中间计算结果、函数参数 |
| 栈指针与栈内容 | 局部变量、返回地址 |
| 页表基址等控制寄存器 | 这个进程的地址空间 |

**上下文切换（context switch）**的完整过程：

```text
 ① shell 正在运行，PC 指向 shell 的指令
 ② 触发切换：shell 请求读磁盘（阻塞）/ 时间片用完 / 来了中断
 ③ 内核把 shell 的上下文存进它的"进程控制块"（PCB）
 ④ 内核挑出 hello，把它的上下文装回 CPU
 ⑤ CPU 从 hello 上次停下的 PC 继续执行
    —— hello 完全感觉不到自己曾被"暂停"过
```

> [!IMPORTANT]
> **内核（kernel）**是操作系统常驻内存的那部分代码。它**不是**一个独立进程，而是"所有进程共用的一段管理者代码"——进程切换、系统调用、中断处理，都是内核在跑。

<details>
<summary>✅ 检查点 1：上下文切换时，内核要把这个进程的 8 GB 内存也复制一份保存起来吗？</summary>

不用。内存内容**留在原处不动**，内核只保存"运行状态"：PC、通用寄存器、栈指针、页表基址，总共几十到几百字节。所谓"恢复上下文"，就是把这些值装回 CPU、让 MMU 换上这个进程的页表；内存里的数据一直都在。
</details>

## 1.7.2 线程

**先说它想解决什么问题**：进程隔离得太彻底了。两个进程要协作，只能走管道、共享内存这些 IPC，每次都要陷入内核、复制数据；而创建一个进程要配一整套地址空间，太贵。于是有了更轻的一层：**在同一进程内再切出多条执行流，共享地址空间，只保留各自的栈和寄存器**。

一个进程可以由**多个线程（thread）**组成，每个线程都运行在这个进程的上下文中：

| 资源 | 进程内是否共享 |
| :--- | :--- |
| 代码（`.text`） | **共享** |
| 全局数据（`.data` / `.bss`） | **共享** |
| 堆（`malloc` 来的内存） | **共享** |
| 打开的文件 | **共享** |
| 栈、PC、寄存器 | **各自独立** |

```text
   ┌──────────────────────────────────────────────┐
   │  一个进程（.text / .data / 堆 全部共享）     │
   │   线程 1    线程 2    线程 3    线程 4       │
   │   [ 栈 ]    [ 栈 ]    [ 栈 ]    [ 栈 ]       │
   └──────────────────────────────────────────────┘
```

*图 1-7-2：线程 = 独立的栈和寄存器 + 共享的地址空间。*

> [!TIP]
> 教材强调：**线程比进程更容易共享数据**，因为线程本来就住在同一个地址空间里，不需要 IPC、不需要复制。代价是要自己加锁——这是第 12 章的主题。

## 1.7.3 虚拟内存

**先说它想解决什么问题**：如果没有虚拟内存，`mov 0x4004e6, %rax` 里的 `0x4004e6` 就是**物理地址**，于是有四个躲不开的麻烦：

```text
   ① 地址不固定：链接器无法在编译时写死地址
   ② 互相踩踏：两个程序都从 0x400000 起步，后加载的覆盖先加载的
   ③ 无法隔离：一个野指针能改掉别人甚至内核的数据
   ④ 装不下：程序 16 GB、内存 8 GB，物理地址不够编
```

虚拟内存一次解决四个问题：给每个进程一张**自己的地图**（页表），地图上的地址（虚拟地址）由 MMU 现场翻译成真实地址（物理地址）。程序只看地图，从不看真实世界。

### （1）一个"骗局"

每个进程都以为自己**独占整台机器的内存**：

```text
   hello 看到：  0x400000 起是代码，0x7fff… 是栈
   shell 看到：  0x400000 起是代码，0x7fff… 是栈
   浏览器看到：  0x400000 起是代码，0x7fff… 是栈
        ↑ 三者的虚拟地址一模一样，对应的物理内存完全不同
```

这个假象叫**虚拟内存（virtual memory）**，它给每个进程提供一个**一致的、私有的线性地址空间**。

### （2）虚拟地址空间的布局

```text
   0x7fff_ffff_ffff  ┌────────────────────────────────┐
                     │  内核虚拟内存                  │   ← 用户程序不可访问
                     │  （内核代码、数据结构）        │
                     ├────────────────────────────────┤
                     │  用户栈（向低地址增长）        │
                     │  …                             │
                     ├────────────────────────────────┤
                     │  共享库（libc.so 等）          │
                     ├────────────────────────────────┤
                     │  堆（向高地址增长）            │
                     │  …                             │
                     ├────────────────────────────────┤
                     │  .bss   未初始化数据           │
                     │  .data  已初始化数据           │
                     │  .text / .rodata（只读）       │
   0x0000_0000_0000  └────────────────────────────────┘
```

*图 1-7-3：Linux 进程的虚拟地址空间。注意**栈往下长、堆往上长**，中间留出大片空洞。*

| 区域 | 放什么 | 特点 |
| :--- | :--- | :--- |
| `.text` / `.rodata` | 机器指令、字符串常量 | 只读、可共享 |
| `.data` | 已初始化的全局/静态变量 | 可读写 |
| `.bss` | 未初始化的全局/静态变量 | 不占文件空间，运行时清零 |
| 堆 | `malloc` 分配的内存 | 向上（高地址）增长 |
| 共享库 | `printf` 等库函数代码 | 多个进程可映射同一份物理页 |
| 栈 | 局部变量、返回地址 | 向下（低地址）增长 |
| 内核区 | 内核代码与数据结构 | 用户态不可访问 |

**为什么堆和栈要"相向"增长？** 代码段、数据段固定在低地址，内核区固定在高地址，中间只剩一整段连续空闲。栈从高往低吃、堆从低往高吃，这段空闲就能**同时被两边利用**，不必预先划界。

```text
   0x7fff_ffff_ffff ┌──────────────────┐
                    │  内核虚拟内存     │  ← 用户不可访问
                    │  栈        ↓      │  push 让 %rsp 变小
                    │  空闲空洞（共享）  │  ← 两边相向而行
                    │  堆        ↑      │  malloc 让 brk 变大
   0x0000_0000_0000 └──────────────────┘
```

反过来想：栈若向上长会先撞数据段，堆若向下长会先撞内核区；相向增长把"可增长空间"最大化了。

### （3）地址翻译

CPU 发出的地址是**虚拟地址**，必须经过翻译才能变成**物理地址**：

```text
   CPU 执行 mov 0x4004e6, %rax
        │
        ▼
   ① 拆开虚拟地址  页号 VPN = 0x400  │  页内偏移 VPO = 0x4e6
        │
        ▼
   ② 用 VPN 查页表（页表在主存里，由内核维护）
        │  得到物理页号 PPN = 0x1a4
        ▼
   ③ 拼回物理地址  PPN ｜ VPO  =  0x1a44e6
        │
        ▼
   ④ 用物理地址访问主存，取回那 8 个字节
```

翻译由 CPU 里的 **MMU（内存管理单元）** 硬件完成，内核只负责**建立和维护页表**。

| 虚拟内存的三大好处 | 说明 |
| :--- | :--- |
| **一致的地址空间** | 每个进程的代码都从 `0x400000` 开始，链接器不必关心实际物理位置 |
| **隔离与保护** | 一个进程无法读写另一个进程的内存，越界就触发段错误 |
| **把磁盘当内存用** | 主存是磁盘的缓存，程序可以比物理内存大（第 9 章） |

> [!NOTE]
> 教材的说法是：**虚拟内存把主存看成一个存放在磁盘上的地址空间的缓存。** 这句话把 1.6 节的层次结构直接搬到了"内存—磁盘"这一层。

#### 一起算一遍

题目：物理内存只有 4 GB，两个进程却各自以为自己有 4 GB。取页大小 4 KB（$2^{12}$ B）、页表项 8 B。

| 步骤 | 动作 | 结果 |
| :-: | :--- | :--- |
| ① | 物理页帧数：$4\ \text{GB}\div4\ \text{KB}=2^{32}\div2^{12}$ | $2^{20}=$ **1,048,576 帧** |
| ② | 每个进程的虚拟页数：同样除以 4 KB | **1,048,576 页** |
| ③ | 若两个进程把 4 GB 全装入 | 需 $2\times2^{20}$ 帧，是物理量的 2 倍，**装不下** |
| ④ | 实际只装热数据：A 100 MB + B 80 MB | 25,600 + 20,480 = **46,080 页 ≈ 180 MB** |
| ⑤ | 同一个 VPN 各查各的页表 | A：`0x00042`→`0x1A3F2`；B：同 VPN→`0x7F204` |

```text
   A 进程                          B 进程
   虚拟地址 0x0004_2ABC            虚拟地址 0x0004_2ABC
        │ 查 A 的页表                 │ 查 B 的页表
        ▼                              ▼
   物理 0x1A3F2ABC               物理 0x7F204ABC
        └─────► 两段不同的内存 ◄─────┘
```

所以"每个进程有 4 GB"不是"分配了 4 GB 物理内存"，而是**发了一张能把 4 GB 虚拟地址翻译到任意物理页的地图**；物理内存只在真正访问时才被占用。没装下的页在页表里 valid=0——要么未分配（访问即段错误），要么指向磁盘文件（缺页再调入）。

<details>
<summary>✅ 检查点 2：两个进程访问同名虚拟地址，物理上一定是两段内存吗？</summary>

不一定。默认是两段（页表各管各的），但如果两块虚拟页映射到**同一个物理页帧**——共享库代码、`fork` 后的写时复制、`mmap` 共享内存——它们就真的是同一段物理内存。虚拟内存保证的是"地址空间互相独立"，不是"物理页绝不共享"。
</details>

## 1.7.4 文件

**先说它想解决什么问题**：硬盘、键盘、显示器、网卡、打印机的寄存器布局和命令字都不一样。程序若直接操作它们，"写一段字节到屏幕"和"写到磁盘"就是两套代码，换个型号就得重写。类比：墙上全是不同形状的插头时什么电器都用不了；统一成一种插座后，电器只管"插进去"。

**文件（file）就是字节序列**，仅此而已。没有格式、没有记录、没有类型——所有"格式"都是应用程序自己约定的。

操作系统的态度是：**一切皆文件**。

| 你眼中的东西 | 内核眼中的东西 | 怎么用 |
| :--- | :--- | :--- |
| 磁盘上的 `hello.c` | 一个文件 | `open` / `read` / `write` / `close` |
| 键盘输入 | 文件描述符 0（stdin） | `read(0, buf, n)` |
| 屏幕输出 | 文件描述符 1（stdout） | `write(1, buf, n)` |
| 一块磁盘 | `/dev/sda` | 同样是 `read` / `write` |
| 网络连接 | socket（也是文件描述符） | `read` / `write` |

```text
   应用程序
      │  read(fd, buf, n)  /  write(fd, buf, n)
      ▼
   操作系统：把"文件描述符"翻译成具体的设备操作
      │
      ├──▶ 磁盘驱动     ──▶ 磁盘
      ├──▶ 键盘驱动     ──▶ 键盘
      ├──▶ 显示适配器驱动 ──▶ 显示器
      └──▶ 网络驱动     ──▶ 网卡
```

*图 1-7-4：文件是 I/O 设备的统一接口。因为接口统一，`cat file` 和 `cat /dev/sda` 用的是同一份代码。*

> [!IMPORTANT]
> **文件是对 I/O 设备的抽象。** 它的价值不在于"能存数据"，而在于**用一个简单的字节序列接口，屏蔽掉了成百上千种设备的差异**。

<details>
<summary>✅ 检查点 3：为什么 `cat file` 和 `cat /dev/sda` 可以是同一份程序？</summary>

因为 `cat` 只调 `read` / `write`，不关心 fd 背后是普通文件还是块设备。`/dev/sda` 被打开后同样返回一个 fd，内核把它翻译成磁盘驱动。**接口统一，程序就能复用**；读出来是文本还是乱码，那是数据本身的问题，不是接口的问题。
</details>

## 1.7.5 抽象：计算机科学的核心

教材在 1.7 末尾给出了整章的"抽象总表"：

| 抽象 | 建立在什么之上 | 隐藏了什么 | 提供什么 |
| :--- | :--- | :--- | :--- |
| **文件** | I/O 设备 | 设备的寄存器、协议、时序 | 统一的字节序列读写 |
| **虚拟内存** | 主存 + 磁盘 | 物理地址、页框、换入换出 | 每个进程一致的线性地址空间 |
| **进程** | 处理器 + 主存 + I/O | 上下文切换、调度、并发细节 | 一个"独占机器"的运行程序 |
| 指令集（ISA） | 处理器微体系结构 | 流水线、乱序、分支预测 | 一组确定的机器指令 |
| 虚拟机 | 整台计算机（OS+硬件） | 真实硬件资源 | 一台"完整"的计算机 |

```text
   应用程序看到的       ←  抽象  ←       内核/硬件实际做的
   一堆文件            ←──────────       上千种设备 + 驱动 + 中断
   一整片私有内存       ←──────────       分页、页表、换页、缺页中断
   一个独占的 CPU       ←──────────       时间片、上下文切换、多核
```

*图 1-7-5：抽象的代价是"看不见真相"，收益是"可以不去看真相"。*

> [!WARNING]
> 抽象不是"骗人"：一旦越界（写只读段、访问未映射地址、除以零），硬件立刻抛异常，把真相摔在你脸上——这就是"段错误"的来源。

> [!NOTE] 换个角度想
> 抽象会"漏"。虚拟内存承诺"你有连续的 4 GB"，但一旦你按随机顺序跳着访问散落的上百万个页，每一次都可能触发缺页中断去读磁盘，程序会慢上千倍——这叫**抽象泄漏（leaky abstraction）**。好的工程师不是相信抽象永远成立，而是知道**它在什么条件下不成立**：局部性好的程序享受抽象，局部性差的程序被抽象惩罚。

## 📌 重点速记

```text
操作系统 : 应用程序与硬件之间的软件层，一切硬件访问都要过它
进程     : 正在运行的程序；CPU 靠"交替执行"制造并发假象
上下文   : PC + 寄存器 + 栈 + 页表基址；切换时保存/恢复
内核     : 常驻内存的管理代码，不是独立进程
线程     : 共享代码/全局数据/堆，独享栈与寄存器
虚拟内存 : 每个进程一个私有、一致的地址空间
地址翻译 : 虚拟地址 →（页表 / MMU）→ 物理地址
三大好处 : 一致、隔离、把磁盘当内存用
文件     : 字节序列；一切皆文件
抽象总结 : 文件→I/O；虚拟内存→主存+磁盘；进程→处理器+主存+I/O
```

## ⚠️ 易错点

1. **以为"并发"就是"同时"。** 单核上的并发是**交替执行**，只有多核才能真并行。教材用词很严格：concurrency vs parallelism。
2. **以为内核是一个进程。** 内核是常驻内存的代码，所有进程共用；它没有独立的 PID（`kthreadd` 这类内核线程另说）。
3. **以为上下文就是"内存内容"。** 严格说包括 PC、通用寄存器、栈指针、控制寄存器（页表基址）等**运行状态**，内存本身并不复制。
4. **以为每个进程有独立的物理内存。** 物理内存是共享的，虚拟内存只是让每个进程**以为**自己独占。
5. **把"虚拟地址 = 物理地址"当成默认。** 只有在裸机或关闭 MMU 的环境才成立；用户态程序拿到的 `&x` 永远是虚拟地址。

## ❓ 常见困惑

**Q：进程和线程到底怎么选？**
A：要隔离、要独立崩溃域、要跨机器 → 进程；要共享大量数据、创建销毁频繁 → 线程。工程上的默认套路是"多进程 + 进程内少量线程"（浏览器、nginx 都这么干）：进程负责隔离，线程负责并发。

**Q：时间片只有几毫秒，上下文切换的开销不大吗？**
A：一次切换约 1–10 μs（算上 cache/TLB 污染可能到几十 μs），相对 1–10 ms 的时间片只占千分之一，可以接受。但每秒切换几万次就会明显掉性能，所以调度器追求"少切、每次切久一点"。

**Q：虚拟内存是不是就是拿硬盘当内存，8 GB 能当 16 GB 用？**
A：不是"当"，是"借"。缺页时要真的读写磁盘（10 ms 级），工作集一旦超过物理内存，系统会陷入**抖动（thrashing）**，慢到几乎不能用。虚拟内存的主业是隔离和一致的地址空间，"扩容"只是附赠。

**Q：为什么说"一切皆文件"，网络 socket 也算文件？**
A：因为 socket 也返回 fd，也能 `read` / `write` / `close`。它不是磁盘文件，但**接口形状一样**，所以可以用同一套 `select` / `epoll` 事件循环管几万个连接（第 12 章）。这里的"文件"指"fd 指向的内核对象"，不是"磁盘上的东西"。

## 🛠 动手试试

1. 数一数一个进程里有几个线程：`ps -eLf | head -20`（`-L` 展开线程）。预期：浏览器、编译器会出现**相同 PID、不同 LWP** 的多行记录，说明一个进程含多个线程。
2. 看自己的虚拟地址空间：`cat /proc/self/maps | head -20`。预期：能看到 `r-xp` 代码段、`rw-p` 堆、`[stack]`、`[vdso]` 和 `libc.so` 的映射，地址从低到高，和 1.7.3 的布局图对得上。
3. 观察缺页：`/usr/bin/time -v ./a.out 2>&1 | grep -i page`。预期：看到 `Minor` 与 `Major` 两个页错误计数；`Major` 一旦变大，就是工作集超出内存、开始抖动的信号。

## ✅ 自测

1. 进程和程序有什么区别？操作系统为什么要提供"进程"这个抽象？
2. 上下文切换要保存哪些东西？为什么保存了这些就能让进程"接着跑"？
3. 线程之间共享什么、独享什么？为什么线程比进程更容易共享数据？
4. 虚拟内存给进程带来哪三个好处？
5. "一切皆文件"具体是什么意思？它带来了什么好处？
<details>
<summary>参考答案</summary>

1. 程序是磁盘上的静态可执行文件；进程是它在内存中运行的实例（有 PC、栈、打开的文件）。操作系统提供进程抽象，才能实现"多个程序并发运行"且互不干扰。
2. PC、通用寄存器、栈指针与栈内容、页表基址等控制寄存器。恢复了这些，CPU 的执行状态就与暂停前完全一致，因此能从断点继续。
3. 共享代码、全局数据、堆、打开的文件；独享栈、PC、寄存器。因为线程本就在同一地址空间，不需要跨进程复制或 IPC。
4. 一致的地址空间（每个进程布局相同）、隔离与保护（互不可见）、把磁盘当作主存的缓存（可运行大于物理内存的程序）。
5. 所有 I/O 设备都被抽象成"字节序列"，统一用 `open/read/write/close` 操作；好处是同一套代码能处理磁盘、键盘、终端、网络，驱动差异被内核屏蔽。
</details>
