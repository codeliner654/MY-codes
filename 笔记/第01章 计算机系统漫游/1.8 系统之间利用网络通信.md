# 1.8 系统之间利用网络通信

> **📖 本节定位**　第 1 章「计算机系统漫游」· 教材 P14–P16
> **一句话**：把网卡插进 I/O 总线，一台机器就能读写另一台机器的内存——**网络只是又一种 I/O 设备**，于是 `hello` 可以在一台机器上敲、在另一台机器上跑。

> [!IMPORTANT] 本节要回答的三个问题
> 1. 网卡只是插在 I/O 总线上的一块板子，CPU 根本不知道"网络"是什么，它凭什么把字节送到另一台机器？

> 3. 为什么服务器能同时服务成千上万个客户端，而客户端只要知道"地址 + 端口"就够了？

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | 对主机而言，**网络就是一种 I/O 总线**：网卡插在 I/O 总线上，和磁盘控制器地位相同 |

## 1.8.1 网络就是一种 I/O 总线

**先说它想解决什么问题**：两台机器各有 CPU 和内存，**没有共享内存**。要让 A 的一个字节出现在 B 的内存里，最直接的想法是"拉根线让 CPU 直接写"——但那样 CPU 得懂电信号、冲突检测、重传，还得为每种网络标准改指令集。

工程上的解法很狡猾：**不新增任何机制，把网络伪装成一块普通 I/O 设备**。CPU 早就会跟设备打交道——往设备寄存器写数据、读状态、等中断。

```text
   CPU 眼里只有一件事：写数据到设备地址 → 设备自己发 → 发完中断我
              │                          │
              ▼                          ▼
        磁盘控制器                   以太网适配器
     （写进扇区里）              （打包发到网线上）
              │                          │
              ▼                          ▼
          本地磁盘                  另一台机器
```

*（网络没有引入新的编程模型，只是给"设备"这个词增加了一个成员。）*

回忆 1.4 节的硬件图：CPU 通过**系统总线**连到**I/O 总线**，再连到各种适配器。以太网适配器（网卡）就插在这条 I/O 总线上。

```text
   CPU ── 系统总线 ── I/O 总线 ──┬── 磁盘控制器
                                 ├── 显示适配器
                                 └── 以太网适配器 ── 网线 ──▶ 另一台机器
                                          ▲
                       从 CPU 的角度看，网卡和磁盘控制器没有本质区别：
                       都是"往某个地址写一串字节，然后等它完成"
```

*图 1-8-1：网络被"降格"成了一种 I/O 设备。这正是本节标题"系统之间利用网络通信"的技术基础。*

| 对比项 | 磁盘 | 网络 |
| :--- | :--- | :--- |
| 连接方式 | 磁盘控制器插在 I/O 总线 | 以太网适配器插在 I/O 总线 |
| CPU 如何操作 | 写寄存器、读寄存器 | 写寄存器、读寄存器 |
| 数据单位 | 扇区 / 文件块 | 数据包（packet / frame） |
| 传输方向 | 到本地存储介质 | 到另一台主机 |

> [!IMPORTANT]
> 教材的原话是：**对主机而言，网络只是一种 I/O 设备。** 一旦接受这个观点，"远程登录"就不再神秘——它只是"从另一台机器的内存里读写字节"。

<details>
<summary>✅ 检查点 1：CPU 往网卡寄存器里写的数据，和它往磁盘控制器寄存器里写的，有区别吗？</summary>

从 CPU 的角度没有区别：都是一次总线写（store）到某个设备映射的地址。区别在**设备内部**：磁盘控制器把字节写进扇区，网卡把它塞进以太网帧、算校验、调制成电信号发出去。所以"网络是一种 I/O 设备"说的是**接口相同**，不是**内部相同**。
</details>

但这种 I/O 的代价比磁盘还大，量级要对清楚：

| 访问对象 | 典型延迟 | 说明 |
| :--- | ---: | :--- |
| L1 cache | ~1 ns | 对照用 |
| 主存 | ~100 ns | 对照用 |
| 同机房的另一台机器 | ~0.05–0.5 ms | 一次往返（RTT） |
| 跨城 | ~10–30 ms | 光速 + 路由跳数 |
| 跨洲 | ~100–200 ms | 光纤中光速约 20 万 km/s |

> [!TIP]
> 一次跨洲往返的时间里，CPU 能执行上千万条指令。所以高性能服务器的一条铁律是**少说话**：把多次小请求合并成一次大请求，省下的时间远超任何代码优化。

## 1.8.2 一台机器怎样连到另一台

从你的笔记本到机房里的服务器，中间通常要过这么几道关：

四段链路，三次转发：

```text
   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
   │ 笔记本 │──▶│ 路由器 │──▶│ 路由器 │──▶│ 服务器 │
   └────────┘   └────────┘   └────────┘   └────────┘
     局域网         广域网         局域网
```

*图 1-8-2：一次跨网络的通信要穿过"适配器—局域网—路由器—广域网—路由器—局域网—适配器"。*

> [!NOTE]
> 教材只画了"以太网段 + 路由器 + 广域网"三层。真实网络还有交换机、NAT、防火墙、CDN，但对"数据怎么从 A 到 B"这个问题，教材的简化模型已经够用。

## 1.8.3 远程运行 hello：五步数据流

假设你在客户端敲：

```bash
ssh user@server          # 或 telnet server（不安全，已淘汰）
server$ ./hello
hello, world
```

这短短几行，背后是两台机器的完整协作：

| 步 | 发生在哪 | 做了什么 |
| :-: | :--- | :--- |
| ① | 客户端 | 键盘输入的字符进入客户端内存，`ssh` 把它们打包 |
| ② | 客户端 → 服务器 | 数据包经网卡 → 局域网 → 路由器 → 广域网 → 服务器网卡 |
| ③ | 服务器内核 | 拆包，把字节交给 `sshd`；`sshd` 启动一个 shell |
| ④ | 服务器 | shell 执行 `./hello`，加载器把程序装入内存，CPU 开始跑 |
| ⑤ | 服务器 → 客户端 | `hello, world\n` 原路返回，显示在客户端屏幕上 |

```text
   ┌──────────────────────────────┐         ┌──────────────────────────────┐
   │ 客户端（你）                 │         │ 服务器（远端）               │
   │ 键盘 → 内存 → ssh 进程       │══网络══ │ sshd → shell → ./hello       │
   │ 以太网适配器                 │         │ 以太网适配器                 │
   └──────────────────────────────┘         └──────────────────────────────┘
     ▶─── 输入（按键、命令）───────────────────────
     ◀─── 输出（hello, world 原路返回）───────
```

*图 1-8-3：计算结果全部在服务器上产生，客户端只负责"送输入、接输出"。*

> [!WARNING]
> 不要以为"远程运行"是客户端在跑程序。**程序在服务器上执行**，客户端只是一个"远程终端"。你在本地看到的每个字符，都是网络另一头送过来的。

<details>
<summary>✅ 检查点 2：`ssh server` 之后运行 `./hello`，`hello` 是在你的笔记本上跑，还是在服务器上跑？</summary>

在**服务器**上跑。笔记本只运行 `ssh` 客户端：它把键盘字节加密后发出去，把收到的字节写到终端。程序加载、CPU 执行、`printf` 全部发生在服务器；你看到的 `hello, world` 是服务器通过网络送回来的字符串。
</details>

要找到"另一台机器上的那个服务"，靠的是三样东西：

| 约定 | 作用 | 例子 |
| :--- | :--- | :--- |
| IP 地址 | 定位**哪一台机器** | `192.168.1.20` |
| 端口号 | 定位机器上的**哪一个服务** | SSH 默认 22，HTTP 默认 80 |
| 传输协议 | 规定字节怎么编号、怎么应答 | TCP 保证可靠、有序 |

> [!NOTE]
> 地址 + 端口 + 协议，合起来就是一个"套接字（socket）"。第 11 章会从 `socket()` 这个系统调用开始，亲手写一个客户端和服务器。

#### 一起算一遍

题目：你在本地 `telnet server`，敲下 `hi` 再回车。这 4 个字节到达服务器时，被套了几层"信封"？

约定：TCP 头 20 B（无选项）、IP 头 20 B、以太网头 14 B、帧尾 FCS 4 B，以太网 payload 最少 46 B。

| 步骤 | 动作 | 累计 | 新增了什么 |
| :-: | :--- | ---: | :--- |
| ① | 应用层：`h`、`i`、回车（Telnet 把回车编成 CR LF） | **4 B** | `68 69 0D 0A`，你真正想发的全部内容 |
| ② | TCP 加头：源端口 49152、目的 23、序号、确认号、标志位、窗口、校验和 | **24 B** | +20 B；TCP 只负责"可靠有序" |
| ③ | IP 加头：源/目的 IP、TTL=64、协议号 6、首部校验和 | **44 B** | +20 B；IP 只负责"送到哪台机器" |
| ④ | 以太网加头 14 B：目的 MAC、源 MAC、类型 0x0800 | **58 B** | +14 B；MAC 只负责"这一跳交给谁" |
| ⑤ | 填充到最小 payload 46 B（IP 包只有 44 B，补 2 B） | **60 B** | +2 B，接收方按 IP 头里的长度丢弃 |
| ⑥ | 加帧尾 FCS 4 B（CRC-32 校验） | **64 B** | +4 B，这就是以太网最小帧 64 B 的由来 |

```text
   应用数据 4 B
   ┌─ 以太头 14 B ─┬──────── IP 包 44 B ────────┬─ 填充 2 B ─┬─ FCS 4 B ─┐
   │               │ IP 头 20 B │ TCP 段 24 B   │            │           │
   │               │            │ TCP 头 20 B │ 数据 4 B     │           │
   └───────────────┴────────────┴─────────────┴────────────┴───────────┘
                              总共 64 B
```

*（每下一层多一个"只有这一层会看"的头；有效载荷占比 4/64 = 6.25%。）*

到服务器后**自下而上拆**：网卡看目的 MAC（是不是我）→ 校验 FCS → 去掉帧头帧尾；内核 IP 层看目的 IP 与 TTL → 去掉 IP 头，按协议号 6 交给 TCP；TCP 层看目的端口 23 与序号 → 去掉 TCP 头，按序排好；`telnetd` 读到 4 B `68 69 0D 0A`，交给 shell 解释成 `hi` 加回车。

三个可以直接记住的推论：**① 发 4 B 实际占 64 B，开销是数据的 15 倍；发 4 KB 时同一套头只占 1.5%**——这就是"批量发送"永远比"小包频繁发"划算的算术原因。**② 路由器只拆到 IP 层**：扔掉旧以太头、换新的、TTL 减 1、重算校验和，TCP 头原封不动；端到端靠 TCP，逐跳靠 IP/以太网。**③ 每跳的 MTU 可能变小**，超了要分片，任一片丢了整包重传。

> [!TIP]
> 小包传输里头部开销可以占 90% 以上。所以协议设计有一条通用经验：把很多小消息攒进一个缓冲区再发（Nagle 算法、`writev`、HTTP/2 多路复用），收益常常比换一块更快的网卡还大。

## 1.8.4 客户端-服务器模型

**先说它想解决什么问题**：两台机器要协作，谁先开口？双方都等 → 死锁；双方都抢 → 冲突。所以必须约定固定的角色：一方主动发起，另一方被动等待。这和点外卖一样：

```text
   点外卖                        客户端-服务器
   你主动打电话                  客户端主动 connect
   报地址 + 报菜名               目的 IP + 端口 + 请求内容
   餐厅不主动给你打电话          服务器只等请求，不主动连客户端
   一家餐厅服务很多顾客          一个服务器进程服务很多客户端
   你不需要知道厨房在哪          客户端不需要知道服务器内部实现
```

*（"服务器是被动的"不是因为弱，而是因为它必须先在众所周知的地址上等着。）*

这种协作方式有一个通用名字：**客户端-服务器模型（client-server model）**。

| 角色 | 职责 | 例子 |
| :--- | :--- | :--- |
| **客户端** | 发起请求、展示结果 | 你的浏览器、`ssh`、`ftp` |
| **服务器** | 等待请求、提供服务、返回结果 | Web 服务器、数据库、`sshd` |

```text
   客户端 A ──┐
   客户端 B ──┼──▶  服务器（一个进程服务多个客户端）
   客户端 C ──┘
```

这个模型有三个要点：

1. **服务器是被动的**：它不主动找人，只等请求；
2. **一对多**：一台服务器可以同时服务成百上千个客户端（第 12 章讲怎么做到）；
3. **位置无关**：客户端不需要知道服务器在哪，只要知道"地址 + 端口"。

把 1.7 的抽象拿来对照：**进程**让一台机器同时跑多个程序，**网络**让多台机器协同跑一个程序。第 11、12 章会把这两件事合起来——并发服务器。

<details>
<summary>✅ 检查点 3：客户端和服务器谁主动？如果服务器先崩溃，客户端会怎样？</summary>

客户端主动（`connect`），服务器被动（`bind` + `listen` + `accept`）。若端口没人监听，客户端 `connect` 会立刻收到 RST（连接被拒绝）或超时——**主动方承担"发现对方不在"的成本**，这是这套角色分工的必然结果。
</details>

> [!NOTE] 换个角度想
> 为什么不给 CPU 加一条"发送到 IP 地址 X"的指令，一步到位？因为那会把**网络协议焊死在指令集里**：IPv4 换 IPv6、以太网换 Wi-Fi、TCP 换 QUIC，都得改 CPU。把网络做成"一块普通 I/O 设备"之后，协议栈只是操作系统里的一段软件，换协议只换驱动和内核，CPU 一行不用动。**抽象的价值就在于让变化被关在某一层里**——这正是 1.9.3 要展开的主题。

## 📌 重点速记

```text
网络地位 : 一种 I/O 总线，网卡插在 I/O 总线上
网络作用 : 把信息从一台主机复制到另一台主机
典型路径 : 主机→适配器→局域网→路由器→广域网→路由器→局域网→适配器→主机
远程执行 : 输入/输出走网络，计算发生在服务器
五步流程 : 键盘→打包→传输→服务器执行→结果回传
模型     : 客户端-服务器（请求 / 响应，一对多）
类比     : 进程=单机并发；网络=多机协同
```

## ⚠️ 易错点

1. **以为"网络是特殊的硬件"。** 对 CPU 而言它和磁盘控制器一样，只是 I/O 总线上的一个设备。
2. **以为远程运行时"程序在本地跑，只是显示在远端"。** 恰恰相反：程序在服务器上跑，本地只是终端。
3. **把"局域网"和"广域网"混为一谈。** 局域网（LAN）覆盖小范围、延迟低；广域网（WAN）跨地域，靠路由器互联。
4. **以为路由器"转发"的是整个文件。** 它转发的是**数据包**，一个文件会被切成很多包分别传输。
5. **以为 SSH 和 telnet 只是名字不同。** telnet 明文传输（密码可被嗅探），SSH 加密；现在只用 SSH。

## ❓ 常见困惑

**Q：网络既然是 I/O 设备，为什么延迟比磁盘还大？不都是"写寄存器等中断"吗？**
A：差别在"等"的长度。磁盘等的是机械/闪存操作（0.1 ms 级），网络等的是**另一台机器的软件**，还要加上十几跳路由和光速传播（ms 到几百 ms 级），丢包时还要重传。接口一样，代价完全不是一个量级。

**Q：每层都加头，不是浪费带宽吗？**
A：分层买的是"可替换"：IP 层不关心底层是以太网还是 Wi-Fi，TCP 不关心上层是 HTTP 还是 SSH。代价是每层约 20 B 的头——对 1500 B 的包只占 3%，对 4 B 的按键却占 1500%。**大包时分层的成本可以忽略，小包才需要合并。**

**Q：路由器不是应该知道整个网络怎么走吗？**
A：不需要知道全局。每台路由器只维护"到某个网段走哪个口"的路由表，按目的 IP 做最长前缀匹配决定下一跳。像快递中转站只看面单上的城市，不关心具体门牌。

**Q：telnet 都被淘汰了，教材为什么还用它举例？**
A：因为它最简单：明文、无加密、无握手，正好把"字节怎么一层层流过去"讲清楚。真实环境必须用 SSH——telnet 的密码在网络上明文传输，同一个局域网里任何人抓包都能看到。

2. 亲手体验一次客户端与服务器：终端 A 跑 `python3 -m http.server 8000`，终端 B 跑 `curl -v http://127.0.0.1:8000/`。预期：A 打印 `"GET / HTTP/1.1" 200 -`（它收到了请求），B 打印响应头和网页内容；把 A 关掉再 curl，B 会立刻报 `Connection refused`。
3. 量一量"网络这一层 I/O"的延迟：`ping -c 3 8.8.8.8`。预期：输出 `time=xx ms`。对照本节表格——同城通常 < 10 ms，跨洲 100–200 ms；再想想这几十毫秒里 CPU 能跑几千万条指令。

## ✅ 自测

1. 为什么说"网络是一种 I/O 总线"？从 CPU 的角度看，网卡和磁盘控制器有什么共同点？
2. 写出一台主机到另一台主机的典型网络路径（至少 5 个环节）。
3. 用 `ssh` 远程运行 `hello` 时，程序到底在哪台机器上执行？客户端负责什么？
4. 客户端-服务器模型的两个角色各做什么？为什么说服务器是"被动"的？
5. 远程执行时，`hello` 的输出经过哪些环节才显示在你的屏幕上？

<details>
<summary>参考答案</summary>

1. 因为网卡（以太网适配器）插在 I/O 总线上，CPU 通过读写它的寄存器来收发数据，与操作磁盘控制器的方式没有本质区别；两者都是"往设备写数据、等它完成"。
2. 客户端主机 → 以太网适配器 → 局域网 → 路由器 → 广域网 → 路由器 → 局域网 → 以太网适配器 → 服务器主机。
3. 程序在**服务器**上执行；客户端只负责把键盘输入打包发出去，并把返回的字节显示在屏幕上。
4. 客户端发起请求并展示结果；服务器等待请求、处理并返回结果。因为服务器不主动发起通信，只在收到请求后才响应。
5. `hello` 把字节写到服务器进程的 stdout → 内核 → `sshd` 打包 → 服务器网卡 → 网络 → 客户端网卡 → 客户端 `ssh` 进程 → 客户端内核 → 显示适配器 → 屏幕。

</details>
