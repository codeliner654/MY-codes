# 3.7 过程

> **📖 本节定位**　第 3 章「程序的机器级表示」· 教材 P164–P176
> **一句话**：过程调用不是一条指令的事，而是**调用者与被调用者共同遵守的栈 + 寄存器契约**：参数怎么传、返回地址放在哪、哪些寄存器谁负责保存，全部有章可循。

> [!IMPORTANT] 本节要回答的三个问题
> 1. 函数一调用，栈上到底多了什么？`%rsp` 凭什么只降不升，`call` 和 `ret` 又凭什么能配对？
> 2. 参数有 8 个，为什么前 6 个走寄存器，第 7 个非要从 `8(%rsp)` 开始而不是 `(%rsp)`？
> 3. 寄存器是所有函数共用的，凭什么 `%rbx` 里的值能活过一次 `call`，`%rdi` 里的就不行？

**读之前你需要会**：`pushq`/`popq` 与 `subq`/`addq` 的等价关系，以及寄存器子名字 `%rdi`→`%edi`→`%di`→`%dil` 的来历（见 [3.4 访问信息](3.4%20访问信息.md)）。不会也没关系——本节会把用到的部分重讲一遍。

## 🎯 核心结论

| # | 结论 |
| :-: | :--- |
| 1 | 每次过程调用都在栈上有一段私有空间——**栈帧**；`%rsp` 指向栈顶，栈向**低地址**增长 |
| 2 | `call` = 压入返回地址 + 跳到目标；`ret` = 弹出返回地址送回 `%rip`；返回地址是 `call` 的**下一条指令**地址 |
| 3 | 前 6 个整型/指针参数依次用 `%rdi %rsi %rdx %rcx %r8 %r9`；第 7 个起放栈上，从 `8(%rsp)` 开始 |
| 4 | 参数在寄存器里按实际**宽度**取子寄存器名（`%edi`/`%di`/`%dil`），在栈上则一律按 **8 字节**占位 |
| 5 | 寄存器分两派：**caller-saved** 由调用者自己保命，**callee-saved**（`%rbx %rbp %r12–%r15`）由被调用者恢复 |
| 6 | 递归没有特殊机制：每层调用一个独立栈帧，各层的 `n` 存在自己的帧里 |

## 3.7.1 运行时栈

课件先把「过程」拆成三件事，每一件都直接落在机器指令上，没有运行时库替你做：

| 机制 | 要解决的问题 | 落到哪些指令 / 硬件 |
| :--- | :--- | :--- |
| **传递控制** | 调用时怎么跳到被调用者的入口，返回时怎么回到调用点 | `call` / `ret`，配合 `%rip` 和栈顶（3.7.2） |
| **传递数据** | 参数怎么交给被调用者，返回值怎么带回来 | 前 6 个参数走寄存器、其余走栈；返回值走 `%rax`（3.7.3） |
| **内存管理** | 过程运行期间的空间从哪来、返回时怎么还 | 栈帧：`subq`/`addq`、`pushq`/`popq`（3.7.4–3.7.5） |

C 的过程调用能一层套一层，靠的是一个**后进先出（LIFO）**的栈。P 调用 Q 时，P 以及整条调用链上更早的过程都处于挂起状态，现场必须原封不动地留在内存里；Q 结束后再逐个恢复。

**为什么非得是栈？** 因为 C、Pascal、Java 这类语言允许递归，同一段过程代码**同时**可以有多个没有跑完的实例（simultaneous instantiations）：`Q` 正在执行，又一层 `Q` 被调起来，两层各自的参数、局部变量、返回地址绝不能互相覆盖。这就要求代码是可**重入**（reentrant）的。这些现场的出现顺序是「后调用、先返回」，销毁顺序正好相反——LIFO 的栈与它天然匹配。

**先说它想解决什么问题**：函数调用真正难的不是"跳过去"，而是"跳回来时现场要恢复成一模一样"。每压一次栈，就像在账本上记一笔"我欠了 8 字节"；`%rsp` 就是账本当前的位置——**只往下记账，还清必须回到原位**。

```text
  函数调用的记账本（%rsp 只降不升的直觉）
  借：call -8 │ pushq -8 │ subq $16 → -16    ← %rsp 一路变小
  还：ret  +8 │ popq  +8 │ addq $16 → +16    ← 原样还清，回到进函数时
```

**形式化定义**：`%rsp` 的值 = 进入本函数时的 `%rsp` − 本函数累计压入的字节数；所谓「栈平衡」，就是要求这个累计值在 `ret` 之前归零。顺带记住一条：**帧里各段的次序就是压栈的先后次序**——`call` 先压返回地址，被调用者再 `push` 保存的寄存器、最后 `subq` 开局部空间，先压的自然落在高地址，所以从 `%rsp` 往上读，次序正好倒过来。

**栈帧（stack frame）** 就是过程在栈上占用的那块区域。当前正在执行的过程的帧总在**栈顶**，`%rsp`（stack pointer）指向它的最低地址；栈向**低地址方向**增长，所以压栈是 `%rsp` 减小，弹栈是 `%rsp` 增大。

![图 3-7-1 运行时栈与栈帧结构](images/3-7_runtime-stack.png)

*▲ 图 3-7-1：左列是整条调用链的栈，右列把 p、q 各自的帧展开。注意 p 的帧底部是「参数 7…n + 返回地址」，而 q 的帧里才是保存的寄存器、局部变量和它给更下层准备的参数构造区。*

```text
        高地址（栈底）
        ┌──────────────────────────────┐
        │        Earlier Frames        │  ← 更早的调用者（如 main）
        ├──────────────────────────────┤
        │  调用者 p 的栈帧             │
        │  ┌────────────────────────┐  │
        │  │ 参数构造区（参数 7…n） │  │  ← p 为调用 q 预留
        │  ├────────────────────────┤  │
        │  │ 返回地址（0x700）      │  │  ← call 压入
        │  ├────────────────────────┤  │
        │  │ 保存的寄存器           │  │
        │  ├────────────────────────┤  │
        │  │ 局部变量               │  │
        │  └────────────────────────┘  │
        ├──────────────────────────────┤
        │  被调用者 q 的栈帧（当前）   │
        │  ┌────────────────────────┐  │
        │  │ 保存的寄存器           │  │
        │  ├────────────────────────┤  │
        │  │ 局部变量               │  │
        │  ├────────────────────────┤  │
        │  │ 参数构造区（给 q 的）  │  │
        │  └────────────────────────┘  │
        ├──────────────────────────────┤ ← %rsp
        ▼
        低地址（栈增长方向）
```

一个帧从高地址到低地址通常包含：

| 组成部分 | 由谁写入 | 作用 |
| :--- | :--- | :--- |
| 参数构造区（argument build area） | 调用者 | 存放第 7 个及以后的参数 |
| 返回地址 | `call` 指令 | `call` 之后那条指令的地址，`ret` 靠它回家 |
| 保存的寄存器 | 被调用者 | 用到的 callee-saved 寄存器的旧值 |
| 局部变量 | 被调用者 | 寄存器放不下、被取地址、或是数组/结构体 |

上面那张表按「谁来写」分类；再按**地址从低到高**（也就是从 `%rsp` 往上）读一遍，就能和课件那张「x86-64/Linux 栈帧」图对上：

| 从 `%rsp` 往上 | 内容 | 写入者 | 说明 |
| :-: | :--- | :--- | :--- |
| 1 | 参数构造区（argument build area） | 调用者 | 给**下一次**调用准备的第 7+ 个参数，可选 |
| 2 | 局部变量 | 被调用者 | 寄存器放不下、被取地址、是数组/结构体时才出现 |
| 3 | 保存的寄存器 | 被调用者 | 用到哪些 callee-saved 就存哪些 |
| 4 | 旧 `%rbp` | 被调用者 | 仅在使用帧指针时出现（可选） |
| — | *—— 当前帧的起点 ——* | — | 帧的「底」 |
| 5 | **返回地址** | `call` 指令 | 硬件压进来的，不是编译器写的 |
| 6 | 本次调用的参数 7+ | 调用者 | 物理上属于**调用者**的帧，被调用者只读 |

第 6 层容易被忽略：它虽然紧挨在返回地址上面，但物理上属于调用者的帧，只是被调用者按 `8(%rsp)`、`16(%rsp)` 去读它。

**调用链一长，帧就一层层叠起来。** 课件用 `yoo → who → amI → amI → amI`（`amI` 自己递归）演示了帧的增长与回退：

```text
高地址
┌──────────────────────────────┐
│ main / 更早的调用者          │
├──────────────────────────────┤
│ yoo 的帧                     │
├──────────────────────────────┤
│ who 的帧                     │
├──────────────────────────────┤
│ amI #1 的帧（who 第一次调它）│
├──────────────────────────────┤
│ amI #2 的帧（#1 递归调它）   │
├──────────────────────────────┤
│ amI #3 的帧（正在执行）      │ ← %rsp
└──────────────────────────────┘
低地址
```

#3 `ret` 时它整块消失、`%rsp` 弹回 #2 的帧底；#2 再 `ret` 弹回 #1……最后 `who`、`yoo` 依次恢复。**帧的生死与 `call`/`ret` 一一对应**，不存在「单独释放中间某一层」这种事。

> [!NOTE]
> **帧指针 `%rbp`**：早期编译器固定用 `%rbp` 指向帧的起始处，方便调试器回溯调用链。开启优化（如 `-Og`）后，gcc 通常**省略帧指针**，把 `%rbp` 当普通通用寄存器用——本节 `P` 的例子正是如此，所以读汇编时不要假定 `%rbp` 一定是帧指针。

**参数超过 6 个怎么办？** 前 6 个走寄存器，第 7 个起由调用者写进自己的**参数构造区**（栈上、返回地址之上）。这就是图 3-7-1 里 p 的帧还要留一块「Argument 7…n」的原因。

> [!TIP]
> `pushq` 等价于 `subq $8, %rsp; movq 源, (%rsp)`，`popq` 等价于 `movq (%rsp), 目的; addq $8, %rsp`。记住这条等价式，后面所有栈帧图都能自己推出来。
>
> 两条指令的动作**顺序不能换**：`pushq` 先把 `%rsp` 减 8、再往新地址写；`popq` 先读 `%rsp` 处的值、再让 `%rsp` 加 8。另外 `popq` 的目的操作数**必须是寄存器**，`popq 8(%rsp)` 这种写法不存在——「读出值」和「调整 `%rsp`」被绑在了同一条指令里。课件里 `push`/`pushq`、`pop`/`popq` 混着写，`q` 只是 AT&T 语法的 64 位后缀，它们是同一条指令。

## 3.7.2 转移控制

过程调用与返回只靠两条指令：

| 指令 | 写法 | 做什么 |
| :--- | :--- | :--- |
| 调用 | `call Label` / `call *Operand` | ① 把**返回地址**压栈；② 把 `%rip` 设为被调过程入口 |
| 返回 | `ret` | 从栈顶弹出返回地址，送回 `%rip` |

`call` 的操作数写**标签**（函数名）还是 `*Operand`（间接，比如函数指针）都不影响压栈——汇编器/链接器会把函数名换成代码段里的入口地址，所谓「跳到函数」就是「把 `%rip` 设成这个地址」。反汇编里 `callq`/`retq` 的 `q` 只是 64 位后缀，和 `call`/`ret` 是同一条指令，课件里两种写法混着出现。

关键是**返回地址**：它是 `call` **下一条指令**的地址，而不是 `call` 自己的地址。这样 `ret` 回来时才能接着往下走。

![图 3-7-2 call 执行后的 %rip 与栈](images/3-7_call-rip.png)

*▲ 图 3-7-2：`callq 741 <multistore>` 位于 `0x6fb`，长 5 字节，所以下一条指令在 `0x700`；执行后 `%rip` 变成 `0x741`，栈顶压着返回地址 `0x700`。*

```text
调用前： %rip = 0x6fb，%rsp = 0x7fffffffe0a8
  0x6fb: e8 41 00 00 00   callq 741 <multistore>
  0x700: 48 8b 14 24      mov (%rsp), %rdx      ← 返回地址就是它
执行 callq：
  ① %rsp ← %rsp - 8 = 0x7fffffffe0a0
  ② M[0x7fffffffe0a0] ← 0x700
  ③ %rip ← 0x741
调用后： %rip = 0x741，栈顶 = 0x700
```

机器码 `e8 41 00 00 00` 里，`e8` 是 `call` 的操作码，后 4 字节是**相对位移** `0x41`：`0x700 + 0x41 = 0x741`，正好落到 `multistore` 的入口。反汇编器显示的 `741` 是绝对地址，机器码里存的却是相对量。

把 `call` 和 `ret` 展开成 RTL 式的动作序列，**顺序是有讲究的**：

```text
call Label                                    ret
────────────────────────────────────          ────────────────────────────────────
① R[%rsp] ← R[%rsp] − 8                       ① R[%rip] ← M[R[%rsp]]
② M[R[%rsp]] ← R[%rip] + sizeof(call 指令)    ② R[%rsp] ← R[%rsp] + 8
③ R[%rip] ← Label
```

- ① 必须先做：`%rsp` 减掉 8 之后，② 才知道该往哪个地址写；
- ② 写入的是「**下一条**指令的地址」——此刻 `%rip` 还指着 `call` 自己，所以要加上 `call` 的字节数；
- `ret` 反着来：先按**旧** `%rsp` 把返回地址读进 `%rip`，再让 `%rsp` 加 8。顺序颠倒就会先把栈顶挪走、读错地方；
- `ret` 只是把 `%rsp` 加 8，**不会清零**那块内存：返回地址还留在原处，只是「逻辑上出栈」了。缓冲区溢出正是利用这一点改写返回地址（见 3.10）。

课件用 `multstore` 调 `mult2` 把这一套走了一遍，可以逐条对着上面的 RTL 核：

```asm
0000000000400550 <mult2>:
  400550:  mov    %rdi, %rax        # a
  400553:  imul   %rsi, %rax        # a * b
  400557:  retq                     # return

0000000000400540 <multstore>:
  400540:  push   %rbx               # Save %rbx
  400541:  mov    %rdx, %rbx        # Save dest
  400544:  callq  400550 <mult2>    # mult2(x,y)
  400549:  mov    %rax, (%rbx)      # Save at dest
  40054c:  pop    %rbx               # Restore %rbx
  40054d:  retq                     # return
```

| 时刻 | `%rip` | `%rsp` | `M[0x118]` |
| :--- | :-: | :-: | :-: |
| `callq` 执行前 | `0x400544` | `0x120` | 旧数据 |
| `callq` 执行后（刚进 `mult2`） | `0x400550` | `0x118` | `0x400549` |
| 执行到 `mult2` 的 `retq` | `0x400557` | `0x118` | `0x400549` |
| `retq` 执行后（回到 `multstore`） | `0x400549` | `0x120` | `0x400549`（残留） |

`0x400544 + 5 = 0x400549`，正是 `callq` 后面那条 `mov %rax, (%rbx)` 的地址——`retq` 回到这里，而 `%rax` 里是 `mult2` 返回的积，紧接着就被存到 `(%rbx)` 指向的 `dest`。顺带注意开头的 `pushq %rbx` / `movq %rdx, %rbx`：`dest` 原本在 `%rdx` 里，而 `%rdx` 是 caller-saved，想让它活过 `call` 只能先换个地方——详细理由见 3.7.5。

> [!NOTE]
> **栈对齐：`call` 之前 `%rsp % 16 == 0`。** x86-64 ABI 要求执行 `call` 时 `%rsp` 是 16 的倍数（这样返回地址压栈后，进入被调用者时 `%rsp % 16 == 8`）。编译器为此会在帧里塞进用不到的填充字节，原因很实在：SSE 的 `movaps` 一类指令要求 16 字节对齐的地址，不对齐直接段错误。判断对齐只要记一条：**进入函数时 `%rsp % 16 == 8`，只要在 `call` 前累计 `push`/`sub` 的字节数是 8 的奇数倍（8、24、40…），`%rsp` 就落在 16 的倍数上。**
>
> | 例子 | 累计调整 | `call` 前 `%rsp % 16` |
> | :--- | :-: | :-: |
> | `P`：`pushq %rbp` + `pushq %rbx` + `subq $8` | 8+8+8 = 24 | 0 ✅ |
> | `call_incr2`：`pushq %rbx` + `subq $16` | 8+16 = 24 | 0 ✅ |
> | 若只 `subq $16`（没有 push） | 16 | 8 ❌ |

![图 3-7-3 ret 执行后的 %rip 与栈](images/3-7_ret-rip.png)

*▲ 图 3-7-3：`ret` 把栈顶的 `0x700` 弹回 `%rip`，`%rsp` 加 8 回到调用前的位置，箭头重新指向 `0x700` 那条 `mov`。*

```text
执行 ret（multistore 的 ret）：
  ① %rip ← M[0x7fffffffe0a0] = 0x700
  ② %rsp ← 0x7fffffffe0a8
返回后： %rip = 0x700，栈顶回到 0x7fffffffe0a8
```

`call`/`ret` 只负责「改 `%rip` + 动栈顶」这两件事，**不负责**保存任何通用寄存器。参数怎么传、寄存器谁保存，属于**调用约定**（3.7.3–3.7.5），不是硬件行为——把这两层分清，很多题就不会绕晕。

<details>
<summary>✅ 检查点 1：`call` 压栈那一刻 `%rip` 还指着 `call` 自己，为什么压进去的不是 `%rip`？</summary>

因为 `ret` 要回到 `call` 的**下一条**指令接着跑，而不是重新执行一次 `call`。所以硬件压入的是 `%rip + call 指令的字节数`——这也解释了为什么 `call` 的长短（这里是 5 字节）会直接决定栈里那个值。
</details>

## 3.7.3 数据传送

x86-64 规定：**前 6 个整型（整数、指针）参数**依次放在 6 个寄存器里，且这 6 个寄存器全是 **caller-saved**；更多的参数通过栈传递。

![图 3-7-4 六个参数寄存器](images/3-7_arg-registers.png)

*▲ 图 3-7-4：参数 1–6 与 `%rdi/%rsi/%rdx/%rcx/%r8/%r9` 一一对应。图里反复出现的 "Caller saved" 很关键：这些寄存器被调用者可以随便改，调用者想留就得自己事先存。*

> [!NOTE] 换个角度想
> 这 6 个参数寄存器为什么**清一色 caller-saved**，一点也不留给被调用者？因为绝大多数调用根本传不满 6 个参数，被调用者往往只碰 `%rdi`、`%rsi` 两三个。若把它们定成 callee-saved，**每个函数**都得为"可能用到"付一次 push/pop，哪怕一个都没碰；定成 caller-saved，就只有"真想把值留过 `call`"的调用者才付这笔钱。**把开销摊给真正需要的人**，是这套约定最核心的取舍。

### （1）参数宽度决定子寄存器名

参数是 `int` 就用 32 位名字，是 `short` 就用 16 位，是 `char` 就用 8 位——同一个物理寄存器，换一个名字就是换宽度：

![图 3-7-5 同一参数在 64/32/16/8 位下的寄存器名](images/3-7_arg-reg-sizes.png)

*▲ 图 3-7-5：四行分别是 64/32/16/8 位操作数对应的寄存器名。第 2 行第 1 列被红框标出的 `%edi`，就是「第 1 个参数按 32 位传」时的写法。*

| 宽度 | 参数 1 | 参数 2 | 参数 3 | 参数 4 | 参数 5 | 参数 6 |
| :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| 64 位 | `%rdi` | `%rsi` | `%rdx` | `%rcx` | `%r8` | `%r9` |
| 32 位 | `%edi` | `%esi` | `%edx` | `%ecx` | `%r8d` | `%r9d` |
| 16 位 | `%di` | `%si` | `%dx` | `%cx` | `%r8w` | `%r9w` |
| 8 位 | `%dil` | `%sil` | `%dl` | `%cl` | `%r8b` | `%r9b` |

### （2）第 7 个参数起：放到栈上

栈上参数从 `8(%rsp)` 开始编号，因为 `(%rsp)` 已经被返回地址占用了：

```text
  高地址
  ┌──────────────────────┐
  │ 参数 9               │  24(%rsp)
  ├──────────────────────┤
  │ 参数 8               │  16(%rsp)
  ├──────────────────────┤
  │ 参数 7               │   8(%rsp)
  ├──────────────────────┤
  │ 返回地址             │    (%rsp)  ← %rsp
  └──────────────────────┘
  低地址
```

**每个栈上参数都按 8 字节对齐占位**，哪怕它只是个 `char`。这样参数地址统一成 `8 + 8k`，也便于维持 `%rsp` 的 16 字节对齐。

**这块栈参数区在调用者自己的帧里**，行话叫**参数构造区**（argument build area）。写它的时候用调用者的 `%rsp` 做基准；`call` 把返回地址一压，同一块内存就被被调用者看成 `8(%rsp)`、`16(%rsp)` 了：

```text
       调用者视角（call 之前）              被调用者视角（call 之后）
       高地址                               高地址
       ┌──────────────────────┐             ┌──────────────────────┐
       │ …                    │             │ …                    │
       ├──────────────────────┤             ├──────────────────────┤
       │ 参数 8               │ 8(%rsp)     │ 参数 8               │ 16(%rsp)
       ├──────────────────────┤             ├──────────────────────┤
       │ 参数 7               │ (%rsp)      │ 参数 7               │ 8(%rsp)
       ├──────────────────────┤             ├──────────────────────┤
       │ 调用者自己的数据     │ ← 原 %rsp   │ 返回地址             │ (%rsp) ← 新 %rsp
       └──────────────────────┘             └──────────────────────┘
       低地址                               低地址
```

所以「第 7 个参数在 `8(%rsp)`」这句话**只在被调用者里成立**；在调用者里它是 `(%rsp)`。同一块内存、两个视角，差的正是那条被压进来的返回地址。参数超过 6 个时谁写、写在哪，全由这张图决定：调用者按序号**从低到高**把第 7、8、9… 个参数写进自己的参数构造区，`call` 之后被调用者按固定偏移去读。

### （3）完整例子：8 个不同类型的参数

```c
void proc(long a1, long *a1p, int a2, long *a2p,
          short a3, long *a3p, char a4, long *a4p)
{
    a1p += a1;
    a2p += a2;
    a3p += a3;
    a4p += a4;
}
```

![图 3-7-6 八参数 proc 的寄存器/栈映射](images/3-7_proc-params.png)

*▲ 图 3-7-6：前 6 个参数占满 6 个寄存器，`a4`（`char`）和 `a4p`（指针）溢出到 `8(%rsp)`、`16(%rsp)`。右下栈图特意画出：两个栈槽都占满 8 字节，图中 8、16 是相对 `%rsp` 的偏移。*

![图 3-7-7 proc 八参数映射的课堂原始帧](images/3-7_proc-params-raw.png)

*▲ 图 3-7-7：同一页的第一次截取，画面上还留着弹幕和任务栏。与上一张是同一幅图，留它是因为底部字幕把结论说全了——所有数据大小都向 8 的倍数对齐。这就是 `char a4` 只有 1 字节却仍占满 `8(%rsp)` 一整个槽的原因。*

| 参数 | 类型 | 位置 | 宽度 |
| :--- | :--- | :--- | :-: |
| `a1` | `long` | `%rdi` | 64 |
| `a1p` | `long *` | `%rsi` | 64 |
| `a2` | `int` | `%edx` | 32 |
| `a2p` | `long *` | `%rcx` | 64 |
| `a3` | `short` | `%r8w` | 16 |
| `a3p` | `long *` | `%r9` | 64 |
| `a4` | `char` | `8(%rsp)` | 8（占 8 字节） |
| `a4p` | `long *` | `16(%rsp)` | 64 |

```asm
proc:
    movq    16(%rsp), %r10      # a4p
    movsbq  8(%rsp), %rax       # a4（char 符号扩展到 64 位）
    addq    %rax, (%r10)        # a4p += a4
    movq    (%rdi), %rax        # a1
    addq    %rax, (%rsi)        # a1p += a1
    movslq  %edx, %rax          # a2（int 符号扩展到 64 位）
    addq    %rax, (%rcx)        # a2p += a2
    movswq  %r8w, %rax          # a3（short 符号扩展到 64 位）
    addq    %rax, (%r9)         # a3p += a3
    ret
```

> [!IMPORTANT]
> 「不同类型也各占一个参数位」：`a2` 是 `int`、`a3` 是 `short`、`a4` 是 `char`，但它们不会挤进同一个寄存器，也不会因为窄就省掉一个栈槽。参数位由**声明顺序**决定，宽度只决定用哪个子寄存器、以及要不要扩展。

### （4）返回值走哪个寄存器

参数怎么进来是约定，返回值怎么回去也是约定：

| 返回类型 | 寄存器 | 保存责任 |
| :--- | :--- | :--- |
| 整数、指针（≤ 64 位） | `%rax`（`int` 用 `%eax`） | caller-saved |
| 浮点（`float`/`double`） | `%xmm0` | caller-saved |

整型返回值在 `%rax` 里，这是本节反复用到的；浮点返回值在 `%xmm0` 里，**不在 `%rax`**——读浮点函数的反汇编时别去 `%rax` 里找结果。两者都是 caller-saved：过程一返回，调用者就得赶紧用掉或存起来，下一次 `call` 会覆盖它们。另外，返回值只有在放得下时才用寄存器；`struct` 这类大对象由调用者在自己的帧里留好空间，把这块空间的地址当隐藏参数传进去。

### （5）数据流全景：叶子过程 `incr` 一条栈指令都没有

课件用一个「只读、只加、只写」的小函数说明参数和返回值怎么在寄存器里转一圈：

```c
long incr(long *p, long val)
{
    long x = *p;
    long y = x + val;
    *p = y;
    return x;
}
```

```asm
incr:
    movq    (%rdi), %rax        # x = *p
    addq    %rax, %rsi          # %rsi = val + x = y
    movq    %rsi, (%rdi)        # *p = y
    ret                         # 返回 %rax 里的旧值 x
```

| 寄存器 | 一开始装什么 | 后来装什么 | 说明 |
| :--- | :--- | :--- | :--- |
| `%rdi` | 参数 1 `p` | 一直是 `p` | 指针参数，取值用 `(%rdi)` |
| `%rsi` | 参数 2 `val` | `y = x + val` | `val` 用完就被就地复用成局部变量 |
| `%rax` | 空 | `x`，最后是返回值 | 同一个寄存器先当局部变量、再当返回值 |

`incr` 不调用别的过程（**叶子过程**，leaf procedure），所以它既不用保存返回地址、也没有局部变量需要开栈——参数和返回值全在寄存器里完成，整个函数没有一条 `push`/`subq`/`pop`。这就解释了 3.7.4 的前提：**栈帧不是每个过程都非有不可，只有「真的需要内存」时才开**。还要注意 `*p = y` 只改了调用者的变量，`ret` 返回的仍是最初的 `x`——这种「先取旧值、再写新值」的语义在 `call_incr`、`call_incr2` 里还会用到。

3.7.2 里 `mult2`/`multstore` 是同一件事的另一个例子：`a` 在 `%rdi`、`b` 在 `%rsi`，`s` 和返回值都在 `%rax`；`multstore` 拿到返回值后立刻 `mov %rax, (%rbx)` 存进 `dest`，参数进、结果出，就这么直白。

## 3.7.4 栈上的局部存储

寄存器只有 16 个，很多局部变量躲不开内存。但反过来也成立：**只有需要时才申请栈空间**——3.7.3 里的叶子过程 `incr` 一条 `subq` 都没有，参数和返回值全在寄存器里转完就 `ret`。真正会把变量逼进栈的，是下面这几种情况：

1. **寄存器不够用**——活跃变量多于可用寄存器；
2. **对局部变量取地址**（如 `&arg1`）——寄存器没有地址，被取地址的变量必须有内存位置；
3. **局部变量是数组或结构体**——只能通过内存寻址访问；
4. **必须跨调用保持**——调用别人时 caller-saved 寄存器会被覆盖，只有栈（或 callee-saved 寄存器）能保住它。

### （1）标准例子：caller 里的 arg1 / arg2

```c
long caller()
{
    long arg1 = 534;
    long arg2 = 1057;
    long sum  = swap(&arg1, &arg2);
    long diff = arg1 - arg2;
    return sum * diff;
}
```

因为 `&arg1`、`&arg2` 被取地址，两个变量只能放栈上，编译器一次性分配 16 字节：

![图 3-7-8 caller 的汇编：分配、写入、调用、释放](images/3-7_local-storage-asm.png)

*▲ 图 3-7-8：`subq $16, %rsp` 一次性分配两个 8 字节槽；`movq $534, (%rsp)` 写 arg1、`movq $1057, 8(%rsp)` 写 arg2；再用 `leaq 8(%rsp), %rsi` 和 `movq %rsp, %rdi` 把两个**地址**作为参数传给 `swap`。*

```asm
caller:
    subq    $16, %rsp           # 分配 16 字节局部空间
    movq    $534, (%rsp)        # arg1 = 534
    movq    $1057, 8(%rsp)      # arg2 = 1057
    leaq    8(%rsp), %rsi       # 参数 2 = &arg2
    movq    %rsp, %rdi          # 参数 1 = &arg1
    call    swap
    movq    (%rsp), %rdx        # 取回交换后的 arg1
    subq    8(%rsp), %rdx       # diff = arg1 - arg2
    imulq   %rdx, %rax          # sum * diff（%rax 是 swap 的返回值）
    addq    $16, %rsp           # 释放局部空间
    ret
```

![图 3-7-9 caller 栈帧中 arg1/arg2 的位置](images/3-7_local-frame.png)

*▲ 图 3-7-9：`subq $16` 之后，`(%rsp)` 是 arg1 = 534，`8(%rsp)` 是 arg2 = 1057。**先分配的变量在低地址**，这与「栈向低地址增长」一致：`%rsp` 下移 16 字节，新空间的最低字节就是 arg1 的起点。*

`swap` 返回后两数已互换：`arg1 = 1057`、`arg2 = 534`，所以 `diff = 1057 - 534 = 523`。若 `swap` 返回两数之和 1591，则结果为 `1591 × 523 = 832093`。

`movq %rsp, %rdi` 这条指令顺带说明了「指针就是地址这个整数」：传给 `swap` 的 `&arg1` 不是别的东西，就是 `%rsp` 的**数值**。栈上的变量和全局变量在这一点上毫无区别，区别只在这个地址是怎么算出来的。也正因为变量有了地址，`swap` 才能通过 `(%rdi)`、`(%rsi)` 反过来改调用者栈帧里的内容。

#### 一起算一遍

设进入 `caller` 时 `%rsp = 0x7fffffffe0b8`，`call swap` 位于 `0x4005a1`、长 5 字节，逐格走一遍：

| 步骤 | 发生了什么 | `%rsp` | 关键内存 / 寄存器 |
| :-: | :--- | :-: | :--- |
| ① | 刚进入 `caller` | `0x…e0b8` | 栈顶是 `caller` 的返回地址 |
| ② | `subq $16, %rsp` | `0x…e0a8` | 一口气借 16 字节 |
| ③ | `movq $534, (%rsp)` | `0x…e0a8` | `M[e0a8] = 534`（arg1） |
| ④ | `movq $1057, 8(%rsp)` | `0x…e0a8` | `M[e0b0] = 1057`（arg2） |
| ⑤ | `movq %rsp,%rdi`；`leaq 8(%rsp),%rsi` | `0x…e0a8` | `%rdi = e0a8`、`%rsi = e0b0`（传的是**地址**） |
| ⑥ | `call swap`：`%rsp − 8`、写入返回地址、`%rip ← swap` | `0x…e0a0` | `M[e0a0] = 0x4005a6`（`0x4005a1 + 5`）；进入时 `%rsp % 16 == 8` |
| ⑦ | `swap` 内读改写 `(%rdi)`、`(%rsi)` | `0x…e0a0` | `M[e0a8] = 1057`、`M[e0b0] = 534` |
| ⑧ | `swap` 的 `ret`：`%rsp + 8` | `0x…e0a8` | `M[e0a0]` 里的 `0x4005a6` 残留不清 |
| ⑨ | `caller` 的 `addq $16, %rsp` | `0x…e0b8` | 回到 ①，账还清 |

- **两笔偏移账**（本节所有"偏移"的来源）：`0x…e0a8 − 0x…e0a0 = 8`，`caller` 里 `(%rsp)` 的 arg1 到 `swap` 里就成了 `8(%rsp)`——同一块内存，两个视角差的正是 ⑥ 压进去的返回地址；
- `0x…e0b0 − 0x…e0a0 = 16`：arg2 在 `swap` 里是 `16(%rsp)`。**变量离"当前 `%rsp`"的偏移 = 在它之后又压了几层 × 8**。这条规则对局部变量、保存的寄存器、栈上参数一视同仁。

### （2）分配与释放：一条 sub，一条 add

![图 3-7-10 subq 分配与 addq 释放的前后对照](images/3-7_rsp-alloc.png)

*▲ 图 3-7-10：`subq $16, %rsp` 把栈顶向下推，圈出 16 字节；返回前 `addq $16, %rsp` 把栈顶推回原位。**成对出现、数值相同**，这是编译器保证栈平衡的基本手法。*

忘记 `addq $16, %rsp`，或加错数值，`ret` 就会从错误的位置取返回地址，程序直接跑飞；只 `subq $8` 却按 `8(%rsp)` 写第二个变量，则是越界写进了别人的帧。

### （3）8 个参数的调用：前 6 个寄存器，后 2 个落栈

```c
long call_proc()
{
    long  x1 = 1;
    int   x2 = 2;
    short x3 = 3;
    char  x4 = 4;
    proc(x1, &x1, x2, &x2, x3, &x3, x4, &x4);
    return (x1 + x2) * (x3 - x4);
}
```

四个变量都被取了地址，全部放栈上；同时第 7、8 个参数（`x4`、`&x4`）也要占两个栈槽：

![图 3-7-11 call_proc 调用 8 参数 proc 的栈布局](images/3-7_call-proc-frame.png)

*▲ 图 3-7-11：从高地址往下依次是返回地址、x1、x2/x3/x4 挤在一个 8 字节槽里、`arg8 = &x4`、`arg7 = x4`；`%rsp` 指向最底下的 arg7 槽。前 6 个参数则分别进 `%rdi %rsi %edx %rcx %r8w %r9`。*

| 参数 | 值 | 传递位置 |
| :--- | :--- | :--- |
| 1 `x1` | 1 | `%rdi` |
| 2 `&x1` | 栈地址 | `%rsi` |
| 3 `x2` | 2 | `%edx` |
| 4 `&x2` | 栈地址 | `%rcx` |
| 5 `x3` | 3 | `%r8w` |
| 6 `&x3` | 栈地址 | `%r9` |
| 7 `x4` | 4 | `(%rsp)` |
| 8 `&x4` | 栈地址 | `8(%rsp)` |

```asm
call_proc:
    subq    $32, %rsp           # x1/x2/x3/x4 + 两个栈参数
    ...                         # x1–x4 写入 24/16/20/22(%rsp)，前 6 个参数装入 %rdi…%r9
    movq    $4, (%rsp)          # 参数 7：x4 落栈（仍占 8 字节）
    leaq    22(%rsp), %rax      # &x4
    movq    %rax, 8(%rsp)       # 参数 8：&x4 落栈
    call    proc
```

**同一变量 `x4` 在栈上出现两次**：一份是它作为局部变量的家（`22(%rsp)`，供 `&x4` 指向），一份是它作为第 7 个参数的副本（`(%rsp)`）。这是「被取地址」和「参数超过 6 个」两条规则叠加的结果。

### （4）再一个例子：`call_incr` 与用不到的 8 字节

3.7.3 的叶子过程 `incr` 不需要栈，但它的调用者仍要给它准备一个「有地址的变量」——因为要传 `&v1`：

```c
long call_incr()
{
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return v1 + v2;
}
```

```asm
call_incr:
    subq    $16, %rsp           # 16 字节局部空间（实际只用一个槽）
    movq    $15213, 8(%rsp)     # v1 = 15213，放在 8(%rsp)
    movl    $3000, %esi         # 参数 2 = 3000
    leaq    8(%rsp), %rdi       # 参数 1 = &v1
    call    incr
    addq    8(%rsp), %rax       # %rax = v1（已被改） + v2
    addq    $16, %rsp           # 释放局部空间
    ret
```

```text
① 刚进入 call_incr                ② subq $16; movq $15213, 8(%rsp)
   高地址                            高地址
   ┌────────────────┐                ┌────────────────┐
   │ …              │                │ …              │
   ├────────────────┤                ├────────────────┤
   │ 返回地址       │ ← %rsp         │ 返回地址       │
   └────────────────┘                ├────────────────┤
   低地址                             │ v1 = 15213     │  8(%rsp)
                                      ├────────────────┤
                                      │ Unused         │ ← %rsp
                                      └────────────────┘
                                      低地址

③ call incr 执行后（站在 incr 里往回看）
   高地址
   ┌──────────────────────────────┐
   │ call_incr 的返回地址         │  24(%rsp)
   ├──────────────────────────────┤
   │ v1 = 15213                   │  16(%rsp)
   ├──────────────────────────────┤
   │ Unused                       │   8(%rsp)
   ├──────────────────────────────┤
   │ incr 的返回地址 → call_incr  │    (%rsp) ← %rsp
   └──────────────────────────────┘
   低地址
```

数值走一遍：`v1` 进栈时是 15213；`incr` 把 `*p` 写成 `15213 + 3000 = 18213`，返回的却是**旧值** 15213，所以 `%rax = 15213`（即 `v2`）；`addq 8(%rsp), %rax` 再把已经变成 18213 的 `v1` 加上去，函数返回 `18213 + 15213 = 33426`。**同一个 8 字节槽在 `call` 前后被两个过程按不同偏移访问**（`call_incr` 里是 `8(%rsp)`，`incr` 里是 `16(%rsp)`），差的就是 `call` 压进去的那条返回地址。

> [!TIP]
> **帧大小 ≠ 变量大小。** 这里只有一个 `long` 局部变量，却 `subq $16`，`(%rsp)` 那 8 字节从头到尾没人读写（课件图上直接标成 Unused）。编译器分配帧时要同时照顾栈对齐（见 3.7.2 的对齐提示框）和生成代码的方便，多留槽很常见。读汇编时按 `subq`/`pushq` 的**实际字节数**算栈平衡，不要按变量个数去猜。

## 3.7.5 寄存器中的局部存储空间

寄存器是**所有过程共享**的资源：P 正在用 `%rbx`，它调用的 Q 也可能想用。没有约定，P 的值就会被 Q 悄悄改掉。课件用一段最小的代码把问题摆出来：`yoo` 把一个临时值放进 `%rdx`，随后调用 `who`，`who` 出于自己的需要又改了 `%rdx`：

```asm
yoo:
    ...
    movq    $15213, %rdx        # 调用前放进 %rdx 的临时值
    call    who
    addq    %rdx, %rax          # 期望还是 15213——其实早被改掉了
    ...
    ret

who:
    ...
    subq    $18213, %rdx        # 覆盖了调用者的 %rdx
    ...
    ret
```

`%rdx` 是 caller-saved，`who` 完全有权改它；`yoo` 想保住 15213，只能调用前自己存起来（存进自己的栈帧，或换一个 callee-saved 的寄存器）。到底谁负责保存，需要调用者和被调用者事先**约定**——这就是 x86-64 的调用约定把通用寄存器分成两派的原因：

| 类别 | 寄存器 | 谁负责保存 | 直观理解 |
| :--- | :--- | :--- | :--- |
| **caller-saved**（调用者保存） | `%rax` `%rdi` `%rsi` `%rdx` `%rcx` `%r8` `%r9` `%r10` `%r11` | **调用者** | 谁用谁存：被调用者可以随便改 |
| **callee-saved**（被调用者保存） | `%rbx` `%rbp` `%r12` `%r13` `%r14` `%r15` | **被调用者** | 借了要还：改之前先存，返回前恢复 |
| 特殊 | `%rsp` | 全体 | 永远指向栈顶，由 `call`/`ret`/`push`/`pop` 维护 |

`%rsp` 的「被调用者保存」是**特殊形式**：它不靠一对 `pushq`/`popq` 保存，而是要求返回时 `%rsp` 与 `call` 之前**一模一样**——所以 `subq` 与 `addq` 必须成对、数值相同，`push` 与 `pop` 必须数量相同（3.7.4 说的栈平衡就是这个）。课件把它单列成一条：「离开过程时恢复为原始值（CALL 之前的值）」。`%rsp` 一旦对不上，`ret` 就会从错误的位置取返回地址，栈直接崩掉。

![图 3-7-12 整数寄存器按调用约定分类](images/3-7_callee-integer-regs.png)

*▲ 图 3-7-12：红框标出 callee-saved 的 6 个寄存器（`%rbx %rbp %r12–%r15`）；下面才是 caller-saved：`%r10 %r11`、返回值 `%rax`、以及 6 个参数寄存器。这张图的划分与 ABI 一致。*

![图 3-7-13 课件中 Caller-saved / Callee-saved 对照页](images/3-7_caller-callee-saved.png)

*▲ 图 3-7-13：⚠️ **这张课件截图把两栏的寄存器清单标反了**：左栏「Caller-saved」列出的 `%rbx %rbp %r12–%r15` 实际是 callee-saved，右栏「Callee-saved」列出的 `%rdi %rsi %rdx %rcx %r8 %r9 %rax %r10 %r11` 实际是 caller-saved。请以图 3-7-12 和上表为准。*

<details>
<summary>✅ 检查点 2：`P` 里省掉 `pushq %rbp`、直接 `movq %rdi, %rbp`，谁会出问题？</summary>

**`P` 的调用者**出问题，`P` 自己毫无察觉。`%rbp` 是 callee-saved，`P` 改了它却不还，调用者手里那个 `%rbp` 就悄悄换了值。反过来，若 `P` 只是用了 caller-saved 的 `%rdx`，则谁都不欠——责任落在"谁动了不该动的寄存器"，而不是"谁用了哪个寄存器"。
</details>

### （1）P 两次调用 Q：把 x 存进 callee-saved 寄存器

```c
void P(long x, long y)
{
    long u = Q(y);
    long v = Q(x);
    return u + v;
}
```

`x` 要活过第一次 `call Q`，而 `%rdi` 是 caller-saved，调用后不可信了。于是 P 选 callee-saved 的 `%rbp` 来存 x：

![图 3-7-14 P 用 pushq %rbp / movq %rdi,%rbp 跨调用保存 x](images/3-7_save-across-calls.png)

*▲ 图 3-7-14：开头的 `pushq %rbp`、`pushq %rbx` 先把两个 callee-saved 寄存器的旧值存进栈；`movq %rdi, %rbp` 把参数 x 搬进 `%rbp`（图右侧手写 "Save x"），之后才 `call Q`。这样 Q 无论怎么折腾，`%rbp` 里的 x 都还在。*

```asm
P:
    pushq   %rbp                # 保存旧的 %rbp
    pushq   %rbx                # 保存旧的 %rbx
    subq    $8, %rsp            # 让 %rsp 在 call 前 16 字节对齐
    movq    %rdi, %rbp          # x → %rbp（callee-saved）
    movq    %rsi, %rdi          # 参数 = y
    call    Q
    movq    %rax, %rbx          # u → %rbx（callee-saved）
    movq    %rbp, %rdi          # 参数 = x（从 %rbp 取回）
    call    Q
    addq    %rbx, %rax          # 返回值 = u + v
    addq    $8, %rsp            # 撤销对齐用的 8 字节
    popq    %rbx                # 后进先出：先恢复 %rbx
    popq    %rbp                # 再恢复 %rbp
    ret
```

### （2）恢复顺序必须与保存顺序相反

![图 3-7-15 返回前 popq %rbx / popq %rbp 恢复](images/3-7_restore-regs.png)

*▲ 图 3-7-15：红框里的 `popq %rbx` 必须在 `popq %rbp` 之前。因为栈是 LIFO：最后压入的 `%rbx` 在栈顶，必须最先弹出；顺序写反会把旧 `%rbp` 装进 `%rbx`、旧 `%rbx` 装进 `%rbp`，两个寄存器一起错位。*

```text
pushq %rbp  →  栈顶：[ 旧 %rbp ]
pushq %rbx  →  栈顶：[ 旧 %rbx ][ 旧 %rbp ]
popq  %rbx  →  栈顶：[ 旧 %rbp ]          ← 取走最上面那个，正好是 %rbx
popq  %rbp  →  栈顶：[       ]           ← 再取 %rbp
```

### （3）双方都要守约：func_A 与 func_B

![图 3-7-16 func_A 调 func_B 时 %rbx 的保存与恢复责任](images/3-7_callee-save-example.png)

*▲ 图 3-7-16：`func_A` 把 123 放进 `%rbx`，随后 `call func_B`；`func_B` 想用 `%rbx`，于是先 save、加 456、再 restore 才 `ret`。回到 `func_A` 后，`addq %rbx, %rax` 里的 `%rbx` 仍是 123——这就是 callee-saved 的意义。*

> [!IMPORTANT]
> 责任是**双向**的：被调用者若用了 callee-saved 寄存器，**必须**在返回前恢复原值；调用者若想让 caller-saved 寄存器里的值活过调用，**必须**自己提前保存。只记住「callee-saved 安全」不够——安全的前提是被调用者真的执行了 push/pop。

### （4）完整实例：`call_incr2` 借 `%rbx` 跨调用保存 `x`

把 3.7.4 的 `call_incr` 改个版本——多一个参数 `x`，而 `x` 要活过 `call incr`：

```c
long call_incr2(long x)
{
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return x + v2;
}
```

```asm
call_incr2:
    pushq   %rbx                # 保存调用者的 %rbx
    subq    $16, %rsp           # 局部空间：v1 在 8(%rsp)，(%rsp) 空着
    movq    %rdi, %rbx          # x → %rbx（callee-saved）
    movq    $15213, 8(%rsp)     # v1 = 15213
    movl    $3000, %esi         # 参数 2 = 3000
    leaq    8(%rsp), %rdi       # 参数 1 = &v1
    call    incr
    addq    %rbx, %rax          # x + v2：%rbx 里还是本层的 x
    addq    $16, %rsp           # 先释放局部空间
    popq    %rbx                # 再把 %rbx 还给调用者
    ret
```

```text
   高地址
   ┌──────────────────────────┐
   │ call_incr2 的返回地址    │  ← call 压入
   ├──────────────────────────┤
   │ 保存的 %rbx（旧值）      │  ← pushq %rbx
   ├──────────────────────────┤
   │ v1 = 15213               │  8(%rsp)
   ├──────────────────────────┤
   │ Unused                   │  ← %rsp
   └──────────────────────────┘
   低地址
```

三个要点：

1. **`x` 没有进栈。** 它只是一个 8 字节值、又要跨调用存活，放进 callee-saved 的 `%rbx` 比占一个栈槽更省事——`addq %rbx, %rax` 在 `call` 之后照样能取到本层的 `x`。
2. **`pushq %rbx` 必须在 `subq` 之前、`popq` 必须在 `addq` 之后**，否则恢复时 `%rsp` 会差 8 字节。
3. **`pushq`(8) + `subq $16` = 24 字节**，累计调整是 8 的奇数倍，所以 `call incr` 前 `%rsp % 16 == 0`（对照 3.7.2 的对齐提示框）；返回时 `addq $16` + `popq` 一步一步还原。

返回值是 `x + 15213`：`v2` 是 `incr` 返回的旧值 15213，而 `v1` 在栈上虽已被改成 18213，这个例子里没人再去读它。

## 3.7.6 递归过程

递归看起来特殊，其实**没有任何特殊指令**：每次调用都走一遍 `call`，都在栈上压一个新帧，各层的局部变量互不干扰。教材用 `rfact` 演示：

```c
long rfact(long n)
{
    long result;
    if (n <= 1)
        result = 1;              // 基准情形
    else
        result = n * rfact(n - 1);
    return result;
}
```

![图 3-7-17 rfact 的 C 代码与汇编对照](images/3-7_rfact-asm.png)

*▲ 图 3-7-17：左边 C，右边汇编。注意 `pushq %rbx` + `movq %rdi, %rbx` 这一对——先把当前层的 n 存进 callee-saved 的 `%rbx`；`cmpq $1, %rdi` 与 `jle .L35` 处理基准情形；`leaq -1(%rdi), %rdi` 算好 n-1 再 `call rfact`。*

```asm
rfact:
    pushq   %rbx                # 保存 %rbx（callee-saved，借了要还）
    movq    %rdi, %rbx          # 本层的 n 存进 %rbx
    movl    $1, %eax            # result = 1（先按基准情形准备好）
    cmpq    $1, %rdi            # 比较 n 与 1
    jle     .L35                # n <= 1 → 直接返回 1
    leaq    -1(%rdi), %rdi      # 参数 = n - 1
    call    rfact               # 递归
    imulq   %rbx, %rax          # result = n * rfact(n-1)
.L35:
    popq    %rbx                # 恢复 %rbx
    ret                         # 返回 result（在 %rax 中）
```

**为什么必须存进 `%rbx`？** 因为 `%rdi` 是 caller-saved：`call rfact` 返回后，`%rdi` 里早已不是本层的 n（被更深的调用改掉了）。而 `%rbx` 是 callee-saved，递归调用会替我们保存并恢复它，所以 `imulq %rbx, %rax` 拿到的仍是**本层**的 n。

**返回值的传递**：`%rax` 是返回值寄存器。基准情形下 `%eax = 1`；递归返回后 `%rax` 里是 `rfact(n-1)`，再乘 `%rbx` 里的 n，结果仍放回 `%rax` 交给上一层。

![图 3-7-18 rfact 递归调用时各层栈帧保存的 n](images/3-7_rfact-stack.png)

*▲ 图 3-7-18：右侧栈图从上往下是 `rfact(n)`、`rfact(n-1)`、`rfact(n-2)` 的帧，格里的 3、2 就是 `pushq %rbx` 保存下来的父层 n。注意每层 `pushq` 存的是**上一层**的 n，本层的 n 此刻正放在自己的 `%rbx` 里。*

```text
   rfact(4) 的调用链（栈向低地址增长）

   高地址
   ┌──────────────────────────────┐
   │ rfact(4)：返回地址 → main    │
   │           保存的 %rbx = 旧值 │
   ├──────────────────────────────┤
   │ rfact(3)：返回地址 → 4 的 imul│
   │           保存的 %rbx = 4    │
   ├──────────────────────────────┤
   │ rfact(2)：返回地址 → 3 的 imul│
   │           保存的 %rbx = 3    │
   ├──────────────────────────────┤
   │ rfact(1)：返回地址 → 2 的 imul│
   │           %rbx = 1，存父层 2 │
   └──────────────────────────────┘  ← %rsp
   低地址

   逐层返回、逐层相乘：1 → 2×1=2 → 3×2=6 → 4×6=24
```

每层帧里都有一份**独立的 n**：深度为 n 时栈上同时存在 n 份现场，空间开销 O(n)。递归太深（n 大到几十万）会把默认 8 MB 的栈撑爆——这不是递归本身的错，而是栈空间有限。

### 课件例题：`pcount_r`——递归数 1 的个数

教材拿 `rfact` 演示，课件换了一个更「整型」的递归：统计无符号数二进制里 1 的个数。

```c
/* Recursive popcount */
long pcount_r(unsigned long x)
{
    if (x == 0)
        return 0;
    else
        return (x & 1) + pcount_r(x >> 1);
}
```

```asm
pcount_r:
    movl    $0, %eax            # 返回值先置 0（基准情形）
    testq   %rdi, %rdi          # x == 0 ?
    je      .L6                 # 是 → 直奔出口
    pushq   %rbx                # 保存 %rbx（callee-saved）
    movq    %rdi, %rbx          # 本层的 x 存进 %rbx
    andl    $1, %ebx            # %rbx = x & 1（本层这一位）
    shrq    %rdi                # 参数 = x >> 1（无符号，用逻辑右移）
    call    pcount_r            # 递归
    addq    %rbx, %rax          # 返回值 = 本层位 + 低位部分 1 的个数
    popq    %rbx                # 恢复 %rbx
.L6:
    rep; ret
```

| 寄存器 | 本层存什么 | 为什么要它 |
| :--- | :--- | :--- |
| `%rdi` | 递归前是 `x`，`shrq` 之后变成 `x >> 1` 当**递归实参** | 参数寄存器，就地复用 |
| `%rbx` | 本层的 `x & 1` | callee-saved，能活过 `call pcount_r` |
| `%rax` | 返回值：先置 0，递归回来后加本层这一位 | 返回值寄存器 |

和 `rfact` 对比着看，几个细节值得记：

- **`%rbx` 存的是「本层那一位」，不是整个 `x`。** 参数已经换成 `x >> 1` 往下传了，本层只需要记住 `x & 1`，回来加到子问题的结果上。
- **`andl $1, %ebx` 故意用 32 位名字。** `andl` 写 `%ebx` 时会自动把 `%rbx` 的高 32 位清零，所以 `%rbx` 里正好是 0 或 1，后面 `addq %rbx, %rax` 直接可用。
- **单出口**：`movl $0, %eax` 提前把返回值置 0，基准情形（`je .L6`）和递归情形都汇合到 `.L6` 的 `ret`，只留一个出口。
- **`pushq`/`popq` 必须都落在 else 分支里**：基准情形 `je .L6` 跳过 `pushq`，所以它也不能执行 `popq`——`popq %rbx` 写在 `.L6` 标签之前，两条路径正好各自配平。
- **`shrq %rdi` 是单操作数形式**，等于右移 1 位；`x` 是 `unsigned long`，所以用逻辑右移 `shrq`，而不是会按符号补 1 的 `sarq`。

`pcount_r` 的递归深度是 `x` 的二进制位数（最多 64），栈开销可以忽略；不像 `rfact` 那样能靠 n 把栈压爆。

> [!NOTE]
> **`rep; ret` 里的 `rep` 是什么？** `rep` 本是字符串指令的前缀，加在 `ret` 前面**没有任何语义**，执行效果就是一条普通 `ret`（`repz retq` 同理）。这是 gcc 的习惯写法：在 `ret` 前垫一个字节，避免它正好成为条件跳转的目标时，在部分处理器上多付一次取指代价。读反汇编时见到它，直接当 `ret` 看即可。

### 互递归：`P` 调 `Q`，`Q` 又调 `P`

递归不一定自己调自己。两个过程互相调用（**互递归**，mutual recursion）时，栈上就是 `P Q P Q …` 一层层交替叠上去，返回时仍严格按 LIFO 逐层弹回：

```text
P → Q → P → Q → P（当前）
栈：[P][Q][P][Q][P]   ← 交替增长，逐层按相反顺序弹回
```

整个过程没有任何新机制：每个函数各自遵守同一套调用约定（参数走寄存器/栈、返回值走 `%rax`、callee-saved 自己保存恢复），栈帧就自然各归各的。课件把递归的要点归纳成四条：

1. 递归**不需要特殊处理**，用的还是同一套 `call`/`ret`；
2. 栈帧意味着每次调用有**私有的存储**：保存的寄存器、局部变量、返回地址各一份；
3. 寄存器保存约定保证过程互相调用时**不破坏对方的数据**——除非 C 代码自己越界写（如缓冲区溢出，见 3.10）；
4. 栈的使用严格遵循「调用/返回」的后进先出模式，对互递归同样成立。

```text
栈帧     : %rsp 指栈顶；栈向低地址增长；帧 = 参数构造区 + 返回地址 + 保存寄存器 + 局部变量

参数寄存器: 1 %rdi  2 %rsi  3 %rdx  4 %rcx  5 %r8  6 %r9   （全部 caller-saved）
第 7 个起 : 8(%rsp), 16(%rsp), 24(%rsp) …   每个占 8 字节
子寄存器 : %rdi→%edi→%di→%dil；%rsi→%esi→%si→%sil
栈偏移   : 局部变量用 (%rsp)、8(%rsp)…；先分配的在低地址
caller-saved: %rax %rdi %rsi %rdx %rcx %r8 %r9 %r10 %r11
callee-saved: %rbx %rbp %r12 %r13 %r14 %r15
栈平衡   : subq $16 分配 → addq $16 释放；push 与 pop 逆序配对
递归     : 每层一个帧；n 存 callee-saved；返回值走 %rax
栈层次   : 从 %rsp 往上：参数构造区(可选) → 局部变量 → 保存的寄存器 → 旧 %rbp(可选) → 返回地址 → 参数 7+
栈对齐   : 进入函数 %rsp%16==8；call 前 %rsp%16==0；push/sub 累计 8 的奇数倍(8/24/40…)
返回值   : 整型/指针 → %rax；浮点 → %xmm0；两者都是 caller-saved
ret 细节 : 只把 %rsp 加 8，栈顶内存不清零（返回地址可被缓冲区溢出改写）
叶子过程 : 不调别人、不用栈，参数和返回值全走寄存器（如 incr）
互递归   : P→Q→P 也只有栈帧交替增长，无特殊机制
```

## ⚠️ 易错点

1. **把返回地址当成 `call` 自己的地址**——`0x6fb` 处的 `callq 741` 压入的是下一条指令地址 `0x700`，不是 `0x6fb`。
2. **以为第 7 个参数在 `(%rsp)`**——`(%rsp)` 是返回地址，第 7 个参数在 `8(%rsp)`。
3. **以为 `char` 参数在栈上只占 1 字节**——栈上每个参数都按 8 字节对齐占位。
4. **把 caller-saved 与 callee-saved 记反**——`%rbx %rbp %r12–%r15` 是 callee-saved；参数寄存器、`%rax`、`%r10/%r11` 是 caller-saved。课件截图也标反了。
5. **`push`/`pop` 顺序写反**——先 `pushq %rbp` 再 `pushq %rbx`，就必须先 `popq %rbx` 再 `popq %rbp`。
6. **返回前忘记恢复 `%rsp`**——`subq $16` 必须配 `addq $16`，否则 `ret` 取错返回地址。
7. **递归里直接用 `%rdi` 参与乘法**——`call` 之后 `%rdi` 已被改，必须把 n 存进 `%rbx`（或栈）里。
8. **以为 `%rax` 里的返回值能跨调用保留**——`%rax` 也是 caller-saved，`call` 别人的时候会被覆盖；想留着必须自己压栈或换 callee-saved 寄存器。
9. **只按变量个数估帧大小**——`subq $16` 里可能只用了 8 字节（`call_incr` 的 Unused），对齐填充也算在帧里；算栈平衡只能按字节数。
10. **把 `call` 前的对齐当可有可无**——进入函数时 `%rsp % 16 == 8`，`call` 前必须是 0；`push`/`sub` 的累计字节数要凑成 8 的奇数倍，否则 `movaps` 一类指令会崩。
11. **看到 `rep; ret` 以为多了一条指令**——`rep` 对 `ret` 没有语义影响，就是一条 `ret`。

## ❓ 常见困惑

**Q：为什么第 7 个参数从 `8(%rsp)` 开始，而不是 `(%rsp)`？**
A：`%rsp` 指的是"被调用者刚进来时的栈顶"，而 `call` 已经把返回地址压在这一格上了。第 7 个参数是调用者写在返回地址**上面**的，所以站在被调用者的角度看，它比 `%rsp` 高 8 字节；第 8 个在 `16(%rsp)`。一句话：**偏移从返回地址往上一格一格数，每格 8 字节**。

**Q：`push` 之后 `%rsp` 变小了，可栈不是变"长"了吗？**
A：栈向**低地址**增长：栈底在高地址、栈顶在低地址，`push` 是把数据写到更低的地方，所以指针数值变小。图的画法习惯把高地址画在上面，于是"数值变小"看起来就是"往下长"。记一句：**`%rsp` 变小 = 栈变长**。

**Q：callee-saved 到底谁负责保存？**
A：**被调用者**。`saved` 修饰的是"由谁来保"，不是"为谁保"：`%rbx` 是 callee-saved，意思是 `Q` 想用它就得先 `push`、返回前 `pop`，让 `P` 看到的还是原值。反过来 `%rdi` 是 caller-saved，`Q` 随便改，`P` 想留就自己在 `call` 前存。

## ✅ 自测

1. `call` 指令压入栈的返回地址是什么？若 `call` 位于 `0x6fb`、长 5 字节，返回地址是多少？
2. 某函数有 9 个 `long` 参数，第 7、8、9 个分别从哪里取？为什么不从 `(%rsp)` 开始？
3. `subq $16, %rsp` 与 `addq $16, %rsp` 各起什么作用？`caller` 中 arg1、arg2 分别在什么位置？
4. 下面这段恢复代码错在哪：`pushq %rbp; pushq %rbx; ...; popq %rbp; popq %rbx; ret`？
5. `rfact` 为什么必须 `pushq %rbx`？若把 n 留在 `%rdi` 里、返回后用 `imulq %rdi, %rax` 会怎样？
6. 课件例子：`0x400544: callq 400550 <mult2>`（5 字节），执行前 `%rsp = 0x120`。分别写出 `callq` 执行后、`mult2` 的 `retq` 执行前、`retq` 执行后这三个时刻的 `%rip`、`%rsp`，以及 `0x118` 处存的值。
7. `P` 里 `pushq %rbp`、`pushq %rbx` 之后为什么还要 `subq $8, %rsp`？这 8 字节存了什么？

<details>
<summary>参考答案</summary>

1. 返回地址是 `call` **下一条指令**的地址；`0x6fb + 5 = 0x700`。
2. 分别从 `8(%rsp)`、`16(%rsp)`、`24(%rsp)` 取；因为 `(%rsp)` 存的是返回地址，栈参数从它上面一格开始。
3. `subq $16` 分配 16 字节局部空间，`addq $16` 在返回前释放、恢复栈平衡；arg1 在 `(%rsp)`、arg2 在 `8(%rsp)`，且 `swap` 之后两者已互换。
4. `pop` 顺序必须与 `push` 相反：应先 `popq %rbx`、再 `popq %rbp`，否则两个寄存器的值互相装反。
5. 因为 `%rdi` 是 caller-saved，递归调用会覆盖它，返回后拿到的不是本层的 n；`%rbx` 是 callee-saved，递归调用会负责恢复。改成 `imulq %rdi, %rax` 会乘上一个已被改写的值，结果错误。
6. ① `callq` 执行后：`%rip = 0x400550`、`%rsp = 0x118`、`M[0x118] = 0x400549`；② `retq` 执行前：`%rip = 0x400557`、`%rsp = 0x118`、`M[0x118]` 仍是 `0x400549`；③ `retq` 执行后：`%rip = 0x400549`、`%rsp = 0x120`、`M[0x118]` 残留 `0x400549`——弹栈只移动指针，不清内存。
7. 为了栈对齐。进入 `P` 时 `%rsp % 16 == 8`，两次 `pushq` 共 16 字节后仍是 8；而 `call Q` 前要求 `%rsp % 16 == 0`，再 `subq $8` 使累计调整达到 24 字节（8 的奇数倍），`%rsp` 正好对齐。这 8 字节不存任何数据，纯属填充，返回前的 `addq $8, %rsp` 就是把它还回去。

</details>
